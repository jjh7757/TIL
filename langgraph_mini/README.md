# langgraph_mini — 계좌 이체 서비스 설계/구현

코드: [jjh7757/langgraph_mini](https://github.com/jjh7757/langgraph_mini)

Spring(Java) 개발 경험을 바탕으로 계좌 이체 서비스를 직접 설계하고, Python(3.13, `typing.Protocol`)으로 옮겨 구현 중인 미니 프로젝트. 도메인/Repository/Service 계층 분리와 TDD를 실습하는 게 목적이라, 기능 자체보다 설계 결정 하나하나에 근거를 남기는 데 집중했다.

## 초기 설계 리뷰 — God Object와 화살표 의미

손으로 그린 첫 다이어그램은 `AccountServiceImpl` 하나가 계좌 조회·잔액 합산·거래 내역 조회·즉시/조건부/분할 이체·별명 변경 7개 메서드를 전부 구현하는 구조였다. 여기서 두 가지를 지적하고 고쳤다.

- **인터페이스 분리(ISP)와 구현체 분리는 별개 문제**: `AccountService` 인터페이스를 Query/Transfer/Manage 셋으로 쪼개도, 구현체가 여전히 `AccountServiceImpl` 하나면 클래스 응집도는 그대로 낮다. 구현체도 인터페이스별로 3개(`AccountQueryServiceImpl` 등)로 나눠야 실제로 테스트 독립성·병렬 개발이 가능해진다.
- **"Use"와 "Implements"는 다른 화살표**: 구현 클래스가 인터페이스를 구현하는 관계(속 빈 삼각형)와 한 클래스가 다른 걸 그냥 갖다 쓰는 의존 관계(열린 화살표)를 같은 점선 화살표로 뭉뚱그리면 나중에 구분이 안 된다.
- **Repository 1개 : Service 3개는 문제가 아님**: 여러 서비스가 같은 Repository를 참조하는 건 Repository 책임이 "Account 하나를 영속화하는 것"으로 좁고 명확하면 정상. 반대로 Repository가 서비스별 전용 메서드로 계속 커지면 그때 CQRS 스타일 분리를 고려.

## Java 인터페이스를 Python으로 그대로 옮기면 안 되는 이유

Python엔 `interface` 키워드가 없고, 목적에 따라 세 가지 방식이 있다.

| | Java `interface` | `abc.ABC` | `typing.Protocol` |
|---|---|---|---|
| 강제 시점 | 컴파일 타임 | 런타임(인스턴스화 시) | 정적 타입 검사기(선택) |
| 명시적 상속 필요 | O | O | X (메서드 시그니처만 맞으면 됨) |

`Protocol`을 쓰면 `class DefaultAccountQueryService(AccountQueryService):`처럼 상속을 선언하지 않아도 되고, 구현체 이름에 Java식 `Impl` 접미사를 붙이는 관행도 버렸다(`DefaultAccountQueryService`, `SqlAccountRepository`처럼 역할이 드러나는 이름 사용). 구현 관계는 `implements` 대신 `satisfies`(구조적으로 만족)로 표현.

## 계층별 책임 — Domain / Repository / Service

- **Domain(`Account`)**: 자기 상태를 스스로 검증하며 바꾼다(`withdraw`/`deposit`/`rename`). 저장소를 몰라야 하고, 필드 직접 대입 대신 이 메서드들을 통해서만 상태가 바뀌어야 한다는 불변식.
- **Repository**: 순수 저장/조회만. `save()` 안에서 도메인 메서드(`withdraw` 등)를 호출하면 안 된다 — 반대로 도메인 로직을 먼저 실행하고 그 결과를 Repository가 그대로 저장하는 순서.
- **Service**: 위 둘을 조합하는 흐름만 지휘 (`repo.find_by_id` → domain 메서드 호출 → `repo.save`). 여러 계좌를 다루는 이체 같은 로직도 여기서 순서를 정한다.

## TDD로 실제로 잡은 버그들

구현하면서 겪은 버그와 pytest가 어떻게 잡아냈는지 기록.

- `find_by_id(self._accounts["{account_id}"])`처럼 f-string을 빼먹고 변수명을 문자 그대로의 문자열로 취급 — dict에 없는 고정 키를 찾으니 항상 `KeyError`
- `save()`가 존재 여부를 먼저 확인하려고 자기 자신인 `find_by_id`를 호출 — 신규 계좌 저장 시 `AccountNotFoundError`로 항상 실패 (dict 대입 한 줄이면 되는 걸 복잡하게 만든 사례)
- `self._accounts.get(account.id) = account` — 함수 호출 결과에 대입하려 해서 `SyntaxError`
- `self.get_account(self, account_id)` — 인스턴스 메서드를 호출할 때 `self`를 또 넘김. `obj.method(args)`는 `type(obj).method(obj, args)`와 같다는 걸 헷갈린 경우
- 이체 로직에서 `from_account.deposit()` / `to_account.withdraw()`처럼 출금·입금이 뒤바뀜 — 방향이 반대인 이체가 조용히 성공하는 버그
- `withdraw`/`deposit`에 음수를 넣으면 부호가 뒤집혀 반대 효과가 나는 경우 — 두 메서드 모두 `amount <= 0` 검증 추가로 막음

일부러 예전 버그 버전으로 되돌려서 `uv run pytest`를 다시 돌려보고, 통과하던 테스트가 바로 빨간불로 바뀌는 걸 확인 — 테스트가 "코드가 맞다"를 증명하는 게 아니라 "이 시나리오는 이 결과가 나온다"를 계속 지켜주는 안전망이라는 걸 체감.

## 요구사항 필드 하나에도 설계 의도가 있다

`Account`에 `id` 대신 `account_id`+`owner_id`를 요구하는 스펙을 보고, 단순 필드 추가가 아니라 이후 요구사항의 전제 조건이라고 분석했다:

1. 계좌:소유자가 1:N이라는 관계 모델링을 강제
2. "이 요청자가 이 계좌 주인이 맞는가" 권한 검증을 나중에 넣을 여지
3. "내 계좌 총 잔액" 같은 조회가 계좌 id 목록을 미리 알 필요 없이 `owner_id` 하나로 가능해짐

실제로 뒤이어 받은 전체 요구사항(계좌 조회/잔액 합산/거래 내역 조회/이체 3종/별명 변경)에서 이 분석이 대부분 들어맞아서, `get_total_balance`·`get_accounts`를 `account_ids` 목록이 아니라 `owner_id` 하나로 받도록 다시 설계했다.

## 요구사항 반영 — Transaction/Card 재설계

"거래 내역 조회(카드 결제 시 사용 카드 표시)" 요구사항을 보고 `Transaction(from_id, to_id, amount)` 하나로는 부족하다는 걸 확인. 이체 한 건이 계좌마다 다른 관점(출금/입금)의 내역으로 보여야 해서, 이체 1건당 `TRANSFER_OUT`/`TRANSFER_IN` 두 줄을 계좌별로 남기는 구조로 바꾸고, `Card` 도메인과 `CardRepository`를 별도로 분리했다. Repository는 여전히 필터링을 하지 않고 전체 조회만 담당하며, 기간·금액·유형 필터링과 최근순 정렬은 Service 계층 책임으로 남겼다 — "이번 달"/"이번 주" 같은 자연어를 실제 날짜로 바꾸는 것도 이 서비스가 아니라 LangGraph 기반 상위 에이전트가 할 일로 경계를 그었다.

조건부 이체는 "승인 후 처리 + 실행 전 잔액이 달라지면 재승인"이라는 요구사항을 만족시키려면 계산과 실행 사이에 시간차가 있어야 한다는 점에서, 단일 메서드 호출이 아니라 `calculate_conditional_transfer`(계산만, 잔액 스냅샷 포함) → `confirm_conditional_transfer`(실행 시점 잔액이 스냅샷과 다르면 재승인 요구) 2단계로 설계했다.

## 문서에 적은 숫자는 "세어보면" 다르다

REST API 엔드포인트 개수를 "조회 5개 + 실행 6개"라고 README와 설계 문서에 적어뒀는데, 최종 제출 전에 다시 훑어보다가 실제로 `grep -n '@app\.\(get\|post\)' api/app.py`로 세어보니 실행형이 7개였다(카드 상태 변경 4개를 한 줄로 묶어 적다가 개수를 헷갈렸다). 테스트 개수도 마찬가지로, 중간에 기능을 추가할 때마다 "247개 전부 통과" 같은 문장을 손으로 고쳐 적다가 실제 `pytest --collect-only` 결과(253개)와 어긋난 채로 방치된 곳이 있었다. 문서에 숫자를 적을 땐 감으로 세지 말고 매번 실제로 세는 명령을 다시 돌려서 확인해야 한다는 걸 깨달았다 — 특히 레지스트리(액션 목록, 엔드포인트 목록)처럼 항목이 하나씩 늘어나는 구조는 사람이 손으로 개수를 맞춰 적기 시작하는 순간부터 어긋날 확률이 생긴다.

## 테스트 이름도 문서다 — 코드가 바뀌면 이름도 같이 바뀌어야 한다

`orchestration/actions.py`의 액션 레지스트리에 REST 전용 조회 액션(`account.list_recipients`) 하나를 추가했더니, 그 전부터 있던 테스트 `test_build_tools_returns_22_tools_matching_actions`(에이전트가 노출하는 tool 개수를 검증)의 **이름 자체**가 거짓말이 됐다. tool 개수(22개)는 여전히 맞는 assert였지만, "actions와 1:1 매칭"이라는 이름의 전제가 깨진 것 — 새 액션이 REST 전용이라 tool로 안 만들었기 때문이다. assert 값만 보고 "테스트 통과하니까 문제없다"고 넘어갈 뻔했는데, 테스트 함수 이름·docstring도 코드가 검증하는 불변식의 일부라서 구조가 바뀌면 같이 리팩터링해야 한다는 걸 다시 확인했다.

## 이미 배포된 시드 데이터를 마이그레이션 도구 없이 안전하게 고치기

데모용으로 만들어둔 이체 상대방 계좌 이름이 알고 보니 실제 지인 이름이라 바꿔야 했는데, 문제는 그 계좌가 **이미 실제 프로덕션 DB에 생성돼 있었다**는 것 — 시드 함수(`ensure_demo_data`)는 "owner_id가 없으면 만들고, 있으면 아무것도 안 함" 방식이라 코드의 이름만 바꿔서는 이미 떠 있는 서버에 반영이 안 됐다. Alembic 같은 별도 마이그레이션 도구 없이, 시드 함수 자체를 "이미 있어도 이름이 코드와 다르면 그 계좌 자체(닉네임)만 동기화하고 잔액처럼 실사용으로 바뀐 값은 안 건드림" 방식으로 고쳐서 다음 배포 때 자동으로 맞춰지게 했다. 로컬에서 Memory 레포지토리로 "이미 예전 이름으로 존재하는 상태"를 흉내 내서 이름만 바뀌고 잔액은 그대로인 것까지 확인한 뒤 배포하니 실제로 그렇게 반영됐다. 시드/데모 데이터를 만드는 함수는 "최초 1회 생성"만 상정하지 말고, 나중에 그 데이터 자체를 고쳐야 할 상황까지 염두에 두고 재실행 안전(idempotent)하게 짜두면 이런 상황에서 별도 스크립트 없이 해결된다는 걸 배웠다.

## 문서를 여러 폴더로 쪼개면, 문서끼리 주고받던 참조도 전부 따라와야 한다

제출 형식(설계 초안 / 최종 설계 자료 / 회고)에 맞춰 문서를 `설계초안/`·`최종설계자료/`·`회고/` 세 폴더로 나눴는데, 파일을 옮기는 것 자체보다 그 파일들을 "OO.md 참고" 식으로 가리키던 다른 문서·소스 코드 docstring(`db/__init__.py` 등)을 전부 찾아 새 경로로 고치는 게 더 큰 일이었다. `grep -rn`으로 파일명을 저장소 전체에서 찾아 하나씩 확인하고 나서야 다 옮겼다고 확신할 수 있었다 — 문서 재구성도 코드 리팩터링처럼 "이름을 바꾸면 그 이름을 쓰던 곳을 전부 찾아 고쳐야 하는" 작업이라는 걸 새삼 느꼈다.

## 2026-09-30 — Agent 품질을 LangSmith로 평가하기

배포까지 끝낸 뒤 "테스트는 다 통과하는데 실제 모델은 제대로 판단하는가?"를 확인하려고 강의에서 배운 LangSmith 평가 방식을 이 프로젝트에 옮겼다. 사례 설계는 [평가/평가_목록.md](https://github.com/jjh7757/langgraph_mini/blob/main/평가/평가_목록.md), 실행 코드는 저장소의 `evals/`.

### pytest와 평가는 검증하는 대상이 다르다

`tests/`의 pytest는 가짜 LLM이 미리 정한 `AIMessage`를 돌려주게 해서 "모델이 이렇게 답했다고 가정하면 그 뒤 로직이 맞는가"를 결정론적으로 검증한다(승인 전 실행 차단, 멱등성, 재시작 복구). 모델이 Tool을 올바르게 고르는지, 답변을 정확하게 하는지는 애초에 검증 대상이 아니다. 평가는 반대로 **실제 Gemini**를 돌려서 그 부분을 채점한다. 둘은 대체 관계가 아니라 보완 관계라서, API 비용과 키가 필요한 평가는 `tests/`와 폴더·의존성 그룹(`uv add --group eval`)을 분리했다 — pytest에 섞으면 CI가 불안정해지고 Docker 이미지에도 들어가 버린다.

### 강의 예제를 그대로 옮기면 안 맞는 지점

강의 노트북의 평가 구조(Golden set → target 함수 → evaluator → Experiment)는 그대로 쓰되, 이 프로젝트의 구조가 달라서 세 가지를 바꿔야 했다.

- **거절해도 실행형 Tool은 호출된다.** 예제는 거절하면 `transfer_money`가 실행되지 않는다고 봤지만, 이 프로젝트는 Tool이 항상 "제안"을 만들고 그 안의 승인 루프에서 거절을 처리한다. 그래서 "Tool 호출 없음"을 금지 조건으로 쓰면 정상 동작을 실패로 채점한다. 대신 **실제 저장소 상태를 읽어서 잔액이 그대로인지** 비교하는 evaluator(`state_check`)를 새로 추가했다.
- **승인이 자연어다.** 예제는 `approve`/`reject` 값을 넘기지만 여기서는 "아니 5만 원으로 바꿔줘" 같은 문장을 분류 LLM이 해석한다. 그래서 사례의 승인 입력은 문장 목록이고, 분류기의 오류도 평가 대상에 들어간다.
- **답변 채점만으로는 부족하다.** 답변이 "이체 완료"라고 해도 실제 잔액이 안 바뀌었거나, 거절했는데 바뀌었을 수 있다. 그래서 채점을 6가지로 나눴다 — 답변 정확성(LLM judge), 필수 Tool·인자 포함(`superset`), 허용 밖 Tool 금지(`subset`), 승인 중단 횟수, 저장소 상태, 금지 문구(타인 잔액 유출 등). 뒤의 다섯은 LLM 없이 결정론적으로 판정한다.

### 평가 도구도 먼저 검증해야 한다

평가 코드를 실제 Gemini에 붙이기 전에 가짜 LLM으로 하네스부터 테스트했더니 강의 방식을 그대로 쓰면 틀리는 지점이 둘 나왔다.

- **interrupt ID는 같은 Tool 안에서 다시 물을 때 재사용된다.** "5만 원으로 바꿔줘" → "응" 처럼 수정을 거치면 중단이 2번인데, ID로 개수를 세면 1로 나왔다. 처리한 중단마다 한 번씩 세도록 바꿨다.
- **Tool 안에서 interrupt가 걸리면 같은 Tool 실행 기록이 두 번 남는다.** 중단 시점 한 번, 재개 후 재실행 한 번. `(이름, 인자)`가 같은 기록은 첫 번째만 남겨야 호출 횟수가 부풀려지지 않는다.

이런 동작은 문서에 안 적혀 있어서 작은 스크립트로 직접 찍어 보고서야 알았다.

### 평가가 찾아낸 진짜 버그 — LLM은 자기가 만든 Tool 호출 인자를 믿는다

승인 전에 "아니 5만 원으로 바꿔줘"라고 수정하는 사례(`transfer_revise`)를 반복 실행하니 5회 중 2회, 최종 답변이 **"10만 원 이체 완료"** 라고 나왔다. 실제 이체와 잔액은 5만 원으로 정확했다(상태 검사는 항상 통과). 원인은 대화 안에 남는 Tool 호출 인자가 수정 전 값(`amount=100000`) 그대로여서, Tool 결과에 실제 금액이 있어도 LLM이 자기 호출 인자를 따라 말했기 때문이다. 결과에 "처음 요청 amount=100000, 실제 실행 amount=50000, 안내할 때는 실제 값을 쓸 것"을 명시하도록 고쳤고, 같은 사례를 5회 다시 돌려 5/5로 통과했다.

두 가지를 배웠다. 첫째, **돈은 맞는데 안내가 틀리는 버그는 상태 검사도 답변 검사도 따로는 못 잡고, 둘을 함께 봐야 보인다.** 둘째, LLM 동작은 한 번 돌려서는 판단할 수 없다 — 이 버그도 1~2번 실행에서는 통과해서, `--repeat`으로 반복해서야 재현됐다. 5회 5/5도 "해결됐다"는 증거가 아니라 개선됐다는 정황일 뿐이라 진행 기록에는 그렇게 적었다.

### 조회 Tool은 예외를 던지지 말고 결과로 돌려준다

필수 15개를 처음 돌리자 `NotOwnerError`로 한 사례가 실행 오류가 났다. 남의 계좌 잔액을 물으면 조회 Tool의 예외가 그래프 밖으로 그대로 터졌고, 그러면 Agent가 사용자에게 "조회할 수 없습니다"라고 설명할 기회조차 없다(웹은 채팅 응답 대신 403 JSON이, CLI는 대화 루프가 종료). 실행형 Tool은 이미 `실패(에러타입): 메시지` 문자열로 결과를 돌려주고 있었는데 조회형만 빠져 있었다. 같은 방식으로 맞추되 **잡는 예외를 명시적인 목록으로 한정**했다 — `MissingParamsError` 같은 프로그래밍 오류까지 `except Exception`으로 삼키면 버그가 가려지기 때문이다. 코드를 읽다 보니 같은 문제가 견적을 직접 조회하던 조건부 이체와 날짜 파싱에도 있어서 함께 고쳤다. 새 테스트가 수정 전 코드에서 실제로 실패하는지도 확인했다(7개 실패) — 통과하는 테스트만으로는 그 테스트가 무언가를 검증한다는 보장이 없다.

### LLM judge는 재판관이 아니라 또 하나의 측정 도구다

필수 15개 × 3회 결과, 결정론적 검사 네 가지는 45/45였는데 LLM judge(`answer_correct`)만 41/45였다. 실제 답변을 LangSmith에서 읽어 실패 4건을 나눠 보니 절반은 Agent가 아니라 judge의 문제였다.

- 실제로 납부됐고 상태 검사도 통과한 사례를 judge가 "사용자는 의도만 말했는데 납부됐다고 단정한다"며 감점했다 — judge는 질문과 답변만 보고 **승인 후 실제로 실행됐다는 사실을 모른다.**
- "생활비 카드"라는 요청에 "생활비 체크카드"라고 답했다고 "체크카드라고 가정했다"며 감점했다 — 그 카드의 실제 이름이 "생활비 체크카드"인데 judge는 그걸 모른다.
- 같은 사례가 실행마다 통과와 실패를 오간다(사실은 맞고 설명이 덜 자세하다는 경계선 판정).

그래서 판단 기준을 세웠다. **안전과 직결된 판정(돈이 움직였는가, 허용 밖 Tool이 실행됐는가)은 결정론적 검사에 맡기고, judge는 표현의 완결성 같은 부드러운 기준에만 쓴다.** 그리고 점수만 보지 않고 실제 답변과 감점 사유를 읽어서 Agent 문제인지 기준 문제인지 나눈다. Agent와 judge가 같은 모델이라는 점도 변동에 섞여 있다.

이 과정에서 하나 더 확인했다. LangSmith UI에 저장된 채점 기록이 45회 중 2회에서 누락/중복돼 있어서 콘솔 요약과 어긋났다(같은 시각 접두사의 run ID가 겹친 것으로 추정하지만 원인은 미확정). 도구가 보여주는 숫자도 원본과 대조해 볼 수 있어야 한다.

프롬프트에 "실행 뒤 처리한 핵심 내용을 함께 안내하고 내부 ID는 보여주지 말라"는 규칙을 추가한 뒤 같은 평가를 다시 돌려서, 재발급 답변에 배송지가 들어간 비율(1/3 → 3/3)과 UUID 노출(1건 → 0건)이 실제로 바뀐 것을 확인했다. 프롬프트 수정은 다른 사례를 나쁘게 만들 수 있어서 **전체를 같은 Dataset으로 다시 돌려 비교**해야 한다 — Dataset 이름을 사례 내용의 해시로 만든 이유다.

### 코드 리뷰는 병렬로 맡기고, 결론은 직접 재현해서 확인한다

도메인·저장소·서비스 코드 2,500줄을 Account / Card·Billing / Orchestration 셋으로 나눠 동시에 리뷰시켰다. 리뷰 결과는 그대로 믿지 않고 돈·안전장치에 직결된 항목은 직접 재현했다.

- `pay_bills`에 같은 청구서 ID가 두 번 들어가면 이중 출금(잔액 100,000 → 80,000). 루프 안의 원본 객체가 저장 뒤에도 미납 상태로 남아 중복 검사를 통과한다.
- 승인·거절·수정이 요청자를 확인하지 않아서, 다른 사용자가 남의 대기 요청을 자기 계좌 기준으로 수정한 뒤 승인하면 실행된다.
- 재현으로 확정 못 한 항목(동시 승인, 데드락)은 "코드상 타당하지만 미재현"으로 나눠서 적었다 — 확인한 것과 추정을 섞으면 나중에 뭘 믿어야 할지 모르게 된다.

가장 인상 깊었던 건 **테스트의 맹점**이다. Memory 저장소는 `find_by_id`가 저장소 내부 객체와 같은 참조를 돌려주고 SQL은 매번 새 객체를 만든다. 그래서 같은 계좌를 대상으로 두 번 입금하는 분할 이체는 Memory에서는 정상(B=600)이고 SQL식으로 돌리면 입금이 유실된다(B=300). 테스트가 전부 Memory 기반이라 통과하는 상태로 배포됐다. "테스트가 통과한다"는 그 테스트가 쓰는 대역이 실제 구현과 같게 동작할 때만 의미가 있다.

또 하나, 리뷰에서 **내가 이번 세션에 넣은 수정도 결함이 있다**는 게 나왔다. 수정 여부를 비교하는 코드가 요청 값(튜플)과 JSON/Postgres에서 읽은 값(리스트)을 다르다고 판정해서, 분할 이체를 수정 없이 승인해도 "수정됨" 안내가 붙는다. Memory 저장소에서는 안 나타나서 테스트로는 못 잡고 프로덕션 저장소에서만 나타난다. 방금 고친 코드도 리뷰 대상이라는 것, 그리고 위의 테스트 맹점이 같은 종류라는 것을 함께 확인했다.

### `main` 푸시가 곧 배포다

이 저장소는 `main`에 푸시하면 GitHub Actions가 이미지를 빌드해서 서버에 배포한다. 런타임 코드가 바뀐 커밋을 푸시하기 전에 파이프라인이 실제로 무엇을 올리는지 확인했다 — Dockerfile이 `uv sync --no-dev`에 `src`만 복사하므로 새로 만든 `evals/`와 평가용 의존성은 이미지에 들어가지 않는다. 푸시한 뒤에는 워크플로가 `success`로 끝난 것까지 확인했지만, 프로덕션 챗봇이 새 동작을 실제로 하는지는 별도로 호출해 봐야 확인되는 것이라 "배포 성공"과 "동작 확인"을 구분해서 적어 뒀다.
