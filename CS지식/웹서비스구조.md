# 웹 서비스 구조

수업 중 손글씨 판서를 정리한 내용입니다.

## 전체 흐름

```
Client(Web Browser) ──http(요청/응답)──▶ ┌─ Server ────────────┐
                     ◀──────────────────  FE(동적 웹페이지) ◀─API─▶ BE
                                          └─────────────────────┘
```

1. **Client (Web Browser)**: 사용자가 웹페이지를 요청하는 주체
2. **Server**: FE와 BE를 함께 담고 있는 서버
   - **FE**: 클라이언트의 요청에 맞춰 **동적 웹페이지**를 만들어 HTML로 응답하는 영역
   - **BE**: FE의 요청을 받아 실제 데이터 처리를 담당하는 영역
3. **Client ↔ FE**: **HTTP(요청/응답)** 로 통신 — 브라우저가 요청을 보내면 FE가 웹페이지(HTML)로 응답
4. **FE ↔ BE**: **API** 로 통신 — FE가 필요한 데이터를 BE에 요청하고 응답받음

## FE는 어떻게 동적 웹페이지를 만드는가

FE는 **JS Code**로 이루어져 있고, 이 코드가 실행되며 화면을 만들어낸다.

- **Web 통신**: FE가 BO(BE)와 **Data**를 주고받음 (Data ⇄ BO)
- 주고받은 Data를 바탕으로 JS Code가 최종 화면(문서)을 **만들어냄**

## 브라우저의 렌더링 과정 (V8 → HTML)

이 JS Code가 실제로 **실행**되는 곳은 Client의 **Browser**다.

- Browser 안에는 **V8**이라는 **JS 엔진**이 있고, 이 엔진이 JS Code를 해석·실행한다
- JS 엔진이 JS를 실행한 결과로 **html**이 생성됨
- 생성된 html이 화면에 그려져(렌더링) 사용자에게 보임

즉 "화면을 실제로 만들어내는 것은 누구인가?"에 대한 답은 **브라우저의 V8 JS 엔진**이다 — FE가 짠 JS Code를 브라우저가 실행해서 html을 만들고, 그 html이 화면에 나타난다.

## 배포 구조 — FE/BE는 도메인이 분리된다

- **FE**: `woojae.com` 같은 도메인으로 배포
- **BE(Server)**: `api.woojae.com` 처럼 별도 도메인(서브도메인)으로 배포되고, 그 안에 **Rest API**가 있음
- 즉 FE와 BE는 같은 서비스라도 각자 다른 주소에 **배포**되어 서로 API로 통신한다

## 요청 → 렌더링까지의 전체 순서 (①~⑥)

브라우저에 실제 화면이 뜨기까지의 순서를 번호로 정리하면 다음과 같다.

1. **① 요청**: Client(Web Browser)가 FE(`woojae.com`)에 페이지를 요청
2. **② 응답**: FE가 그 요청에 대해 **JS**를 응답으로 내려줌
3. **③ 서버 → 브라우저**: 브라우저가 서버로부터 받은 그 **JS**를 실행
4. **④ 요청**: 실행된 JS가 필요한 데이터를 얻기 위해 Server(BE, `api.woojae.com`)에 요청
5. **⑤ 응답**: Server(BE)가 요청받은 데이터로 응답
6. **⑥ 렌더링**: 브라우저가 받은 데이터를 가지고 JS로 화면을 **렌더링**해서 사용자에게 보여줌

즉 브라우저는 처음에 "빈 껍데기 JS"만 받아서(①②③), 그 JS가 스스로 BE에 데이터를 요청·응답받아(④⑤) 최종 화면을 그려낸다(⑥).

## CSR vs SSR

위 "①~⑥ 순서"는 **CSR(Client Side Rendering)** 방식이다. 렌더링 시점과 위치에 따라 CSR과 SSR로 나뉜다.

### CSR (Client Side Rendering)
- 브라우저가 **빈 껍데기(JS만 있는 HTML)** 를 먼저 받는다
- 브라우저가 그 JS를 **실행**하면서 BE에 데이터를 요청하고, 응답받은 데이터로 화면을 그린다 (위 ①~⑥ 과정 그대로)
- 장점: 최초 페이지 로드 이후에는 필요한 데이터만 API로 주고받으면 되어 화면 전환이 빠르고 서버 부담이 적음
- 단점: 화면이 완성되기까지(JS 실행 + 데이터 요청/응답) 시간이 걸려 **첫 화면이 늦게 보임**, 검색엔진이 처음 받는 HTML에는 내용이 비어 있어 **SEO에 불리**

### SSR (Server Side Rendering)
- **서버(FE)** 가 요청을 받은 시점에 필요한 데이터까지 미리 채운 **완성된 HTML**을 만들어서 응답
- 브라우저는 그 완성된 HTML을 받아서 바로 화면에 그리기만 하면 됨 — JS가 실행되어야 화면이 뜨는 CSR과 달리, HTML 자체에 내용이 이미 들어있음
- 장점: **첫 화면이 빨리 보임**, HTML에 내용이 이미 있어 **SEO에 유리**
- 단점: 요청이 올 때마다 서버가 매번 HTML을 새로 만들어야 해서 **서버 부담이 큼**

### 비교
| 구분 | CSR | SSR |
|------|-----|-----|
| HTML을 완성하는 곳 | 브라우저(클라이언트) | 서버 |
| 최초 화면 표시 속도 | 느림 (JS 실행 후 데이터까지 받아야 함) | 빠름 (완성된 HTML을 바로 받음) |
| 서버 부담 | 적음 | 큼 (매 요청마다 렌더링) |
| SEO | 불리 | 유리 |

## SEO란

**SEO(Search Engine Optimization, 검색엔진 최적화)**: 구글·네이버 같은 검색엔진이 내 웹페이지를 잘 찾고, 검색 결과에서 상위에 노출되도록 만드는 작업.

- 검색엔진은 크롤러(봇)가 웹페이지의 HTML을 읽어서 내용을 파악하고 색인(index)에 등록한다
- **CSR**은 크롤러가 처음 받는 HTML이 거의 비어있어(JS가 실행돼야 내용이 채워짐) 크롤러가 내용을 못 읽거나 놓칠 수 있음 → SEO에 불리
- **SSR**은 서버가 이미 내용이 채워진 완성된 HTML을 주기 때문에 크롤러가 바로 내용을 읽을 수 있음 → SEO에 유리

즉 블로그·쇼핑몰처럼 검색 유입이 중요한 서비스는 SSR을 선호하고, 로그인 후 쓰는 대시보드·관리자 페이지처럼 검색 노출이 중요하지 않은 서비스는 CSR을 써도 무방한 경우가 많다.

## robots.txt

도메인 루트(`example.com/robots.txt`)에 두는 텍스트 파일로, 검색엔진 크롤러에게 "어디는 긁어가도 되고 어디는 긁어가지 말라"고 알려주는 규칙 파일.

```
User-agent: *
Disallow: /admin/
Allow: /

Sitemap: https://example.com/sitemap.xml
```

- **User-agent**: 규칙을 적용할 크롤러 (구글봇, 네이버봇 등, `*`는 전체)
- **Disallow**: 크롤링을 막을 경로
- **Allow**: 명시적으로 허용할 경로
- **Sitemap**: 사이트맵 위치 안내 (SEO에 도움)

주의할 점:
- **강제성이 없는 "권고"**임 — 착한 크롤러(구글봇 등)는 지키지만 악성 봇은 무시할 수 있어 보안 목적으로 쓰면 안 됨(막고 싶은 경로를 적으면 오히려 "여기 뭐가 있다"고 알려주는 꼴)
- 로그인 페이지, 관리자 페이지처럼 검색 노출을 원치 않는 곳을 막는 용도로 주로 사용
- 크롤러가 어디를 색인해도 되는지 정하는 1차 관문이고, 그 이후 실제 내용이 잘 읽히는지는 CSR/SSR 여부가 영향을 준다

## GEO란

**GEO(Generative Engine Optimization, 생성형 엔진 최적화)**: ChatGPT, Perplexity, Google AI Overview 같은 AI 챗봇/생성형 검색엔진이 답변을 만들 때 내 콘텐츠를 인용·참조하도록 최적화하는 작업. SEO의 다음 세대 개념으로, 사람들이 검색창 대신 AI에게 바로 질문하는 경우가 늘면서 등장했다.

- **SEO와의 차이**:
  - SEO: 검색 결과 "링크 목록"에서 상위 노출되는 게 목표 (사용자가 클릭해서 들어옴)
  - GEO: AI가 답변을 생성할 때 그 답변 안에 내 콘텐츠가 인용·근거로 쓰이는 것이 목표 (사용자가 사이트에 안 들어와도 브랜드/정보가 노출됨)
- **최적화 방법 예시**:
  - 명확한 사실·통계·정의를 문단 단위로 구조화 (AI가 발췌하기 쉽게)
  - 질문-답변(Q&A) 형식, FAQ 구조 활용
  - 출처·저자·최신성이 명확해야 AI가 신뢰도 있는 소스로 인식
  - `llms.txt`(아직 표준은 아니지만 일부 사이트가 도입 중인, robots.txt와 비슷한 AI 크롤러용 안내 파일) 같은 새로운 시도도 등장
- **CSR/SSR과의 연결**: AI 크롤러도 결국 HTML을 읽어야 하므로, CSR로 내용이 비어있는 페이지는 GEO 관점에서도 불리하고 SSR이 유리하다

## 정리
브라우저(Client)가 HTTP로 요청을 보내면 서버 안의 FE가 이를 받아, 필요하면 API를 통해 BE와 데이터를 주고받은 뒤 동적 웹페이지(HTML)를 만들어 브라우저에 응답한다. 이때 FE가 만든 JS Code는 Web 통신으로 BO와 Data를 주고받고, 실제로는 브라우저의 V8 JS 엔진이 이 JS Code를 실행해서 html을 생성·렌더링함으로써 화면에 보여준다. 실제 배포 시에는 FE(`woojae.com`)와 BE(`api.woojae.com`)가 서로 다른 도메인에 배포되며, 브라우저는 ①요청 → ②JS 응답 → ③JS 실행 → ④BE에 데이터 요청 → ⑤데이터 응답 → ⑥렌더링 순서로 화면을 완성한다.
