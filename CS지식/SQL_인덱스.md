# SQL 인덱스(Index)

테이블의 검색 속도를 높이는 자료구조인 인덱스의 개념, 생성·삭제, 자동 생성 규칙, 효율적인 경우와 비효율적인 경우를 정리했습니다.

> PostgreSQL 기준.

## 인덱스란

- 테이블의 **검색 속도를 향상**시키기 위한 자료구조다. 보통 B-tree 같은 구조로 만든다.
- 대신 비용이 있다.
  - 데이터를 입력·수정·삭제할 때 **인덱스도 함께 관리**해야 해서 처리 비용이 늘어난다.
  - 인덱스를 저장할 **추가 공간**이 필요하다.

## 생성과 삭제

```sql
CREATE INDEX index_name
ON table_name (column_name);

DROP INDEX index_name;
```

## 자동으로 생성되는 인덱스

| 지정 | 인덱스 자동 생성 |
|------|------------------|
| `PRIMARY KEY` | 생성됨 |
| `UNIQUE` | 생성됨 |
| `FOREIGN KEY` | **생성되지 않음** (참조하는 쪽 외래키 컬럼) |

- 외래키 컬럼은 `JOIN` 조건으로 자주 쓰이므로 필요하면 직접 `CREATE INDEX`로 만든다.

## 인덱스가 효율적인 경우

- `WHERE` 조건으로 전체 중 **일부만 자주 조회**하는 경우
- `JOIN`의 연결 조건으로 자주 쓰는 컬럼
- `ORDER BY`, `GROUP BY`에 쓰는 컬럼 (인덱스의 도움을 받을 수 있다)
- **카디널리티가 높은** 컬럼

### 카디널리티(Cardinality)

특정 컬럼이 가지는 **고유한 값의 수**다.

| 구분 | 의미 | 예 |
|------|------|-----|
| 높음 | 고유한 값이 많음 | 주민등록번호, 이메일, id |
| 낮음 | 고유한 값이 적음 | 성별, 결제 여부, 등급 |

- 카디널리티가 높으면 일반적으로 유리하지만, **실제 효과는 값의 분포와 조회 조건에 해당하는 행의 비중**에 따라 달라진다.

## 인덱스가 비효율적인 경우

- **데이터가 적은** 테이블
- 조회보다 **변경이 많아** 인덱스 유지 비용이 큰 경우
- 조회 조건에 해당하는 행이 **테이블의 상당 부분**을 차지하는 경우 (결국 대부분을 읽어야 해서 이득이 작다)

## 정리

- 인덱스는 조회를 빠르게 하는 대신 쓰기 속도와 저장 공간을 내준다.
- PK·UNIQUE는 자동, **FK는 직접** 만들어야 한다.
- "많이 조회하고, 일부만 골라내며, 값이 다양한 컬럼"이 인덱스 후보다. 무조건 많이 만드는 것이 아니라 조회 패턴을 보고 정한다.
