# 컨테이너 기반 배포 기초

컨테이너는 애플리케이션과 그 실행에 필요한 모든 것(코드, 런타임, 라이브러리, 환경 설정)을 하나의 패키지로 묶은 것입니다. 어디서 실행하든 컨테이너 안의 환경은 동일하므로, "내 컴퓨터에서는 되는데 서버에서는 안 되는" 문제를 크게 줄여줍니다. Docker가 사실상 표준 도구로 쓰입니다.

## 컨테이너 vs 가상머신(VM)

가상머신은 운영체제 전체를 통째로 가상화하는 반면, 컨테이너는 **호스트의 커널을 공유**하면서 애플리케이션 계층만 격리합니다. 그래서 훨씬 가볍고 시작 속도도 빠릅니다.

## 전체 흐름

| 단계 | 내용 |
|---|---|
| 1. Dockerfile 작성 | 베이스 이미지(`node:20`, `python:3.12` 등), 복사할 파일, 의존성 설치·서버 실행 명령을 텍스트로 정의 |
| 2. 이미지 빌드 | `docker build`로 Dockerfile을 바탕으로 실행 가능한 이미지 생성 |
| 3. 로컬 테스트 | `docker run`으로 컨테이너를 띄워 로컬에서 동작 확인 |
| 4. 이미지 푸시 | Docker Hub, GitHub Container Registry, AWS ECR, GCP Artifact Registry 등 레지스트리에 업로드 |
| 5. 배포 | 클라우드나 서버에서 이미지를 받아 실행 |

## 간단한 예시 (Node.js Express 서버)

**Dockerfile**

```dockerfile
FROM node:20-alpine
WORKDIR /app
COPY package*.json ./
RUN npm install --production
COPY . .
EXPOSE 3000
CMD ["node", "server.js"]
```

**빌드 및 실행**

```bash
docker build -t my-server .
docker run -p 3000:3000 my-server
```

> 실제로 로컬에서 Docker로 서버(n8n)를 띄우고 외부 서비스(Telegram)와 웹훅으로 연동해본 사례는 [Docker로 n8n 셀프호스팅하고 Telegram 웹훅 연동하기](../n8n실습/Docker로n8n셀프호스팅하기.md) 참고.

## 이미지를 어디에 배포할지

| 방식 | 특징 |
|---|---|
| 관리형 컨테이너 서비스 | AWS ECS/Fargate, GCP Cloud Run, Azure Container Apps — 인프라 관리 없이 이미지만 올리면 실행. Cloud Run은 트래픽에 따라 스케일이 0까지 줄어들어 비용 효율이 좋음 |
| 쿠버네티스(Kubernetes) | 여러 컨테이너를 대규모로 운영하며 자동 복구·스케일링·롤링 업데이트가 필요할 때 사용. AWS EKS, GCP GKE, Azure AKS 등이 관리형 쿠버네티스. 러닝커브가 높음 |
| 직접 관리하는 VM/서버 | EC2 등에 Docker를 설치하고 직접 컨테이너 실행. `docker-compose`로 여러 컨테이너(서버+DB+캐시)를 한 번에 정의·실행 가능 |
| PaaS형 컨테이너 배포 | Railway, Render, Fly.io — Dockerfile만 있으면 자동 빌드·배포. Git 저장소 연결 시 푸시할 때마다 자동 배포되는 CI/CD도 쉽게 구성 가능 |

## 여러 컨테이너를 함께 쓸 때 — Docker Compose

서버 하나만이 아니라 데이터베이스나 캐시 서버(Redis 등)도 같이 필요한 경우가 많다. `docker-compose.yml` 파일로 여러 서비스를 한 번에 정의한다.

```yaml
services:
  web:
    build: .
    ports:
      - "3000:3000"
    depends_on:
      - db
  db:
    image: postgres:16
    environment:
      POSTGRES_PASSWORD: example
```

`docker compose up`으로 전체 스택을 한 번에 띄울 수 있다.

## 알아두면 좋은 점

- 이미지 크기를 줄이려면 `alpine` 같은 경량 베이스 이미지를 쓰거나, 멀티스테이지 빌드(빌드용 단계와 실행용 단계 분리)를 활용한다.
- 환경 변수(DB 비밀번호, API 키 등)는 이미지에 직접 넣지 말고 실행 시점에 주입하는 것이 보안상 안전하다.
- CI/CD 도구(GitHub Actions 등)와 연결하면 코드를 푸시할 때마다 자동으로 빌드-푸시-배포가 이루어지도록 만들 수 있다.
