# RAG Golden Set 작성 가이드

RAG 평가의 기준이 되는 **질문·기준 답변·원문 근거 모음**인 Golden Set을 어떻게 설계·작성·검수·관리하는지 정리했습니다.
평가 지표(Hit@k, Recall@k, Faithfulness 등)와 LLM-as-Judge는 [RAG 평가](RAG_평가.md), 평가를 반복 실행하는 구조는 [RAG 실험 스크립트](RAG_실험스크립트.md)를 참고하세요.

```
평가 범위 정하기 → 원문·근거 선택 → 질문·기준 답변 작성 → 검수 → 버전 관리·저장
```

- 평가할 **사용자 질문의 범위**와 **문서·버전 기준**을 먼저 정한다.
- 답변 가능한 문항의 근거는 **검색 대상 문서에 실제로 포함**되어 있어야 하고, **문서 버전도 일치**해야 한다.

## 1. 문항마다 작성할 내용

먼저 평가 대상 원문을 준비하고 **제목, 본문, 출처, 버전**을 기록한다. 아래 항목은 예시이며, 평가 목적과 사용하는 도구에 맞게 구성하고 필요하면 추가한다. (필드 이름·저장 형식도 사용하는 평가 도구에 맞춘다.)

| 항목 | 작성할 내용 | 필요한 이유·비고 |
|------|-------------|------------------|
| 질문 | RAG에 입력할 사용자 질문 | |
| 기준 답변 | 답변에 **반드시 포함되어야 할 핵심 내용과 조건** | RAG의 생성 결과가 아니라, 원문 검수로 확정한 **비교 기준** |
| 관련 문서 | 필요한 문서를 확인할 수 있는 파일명·URL·문서 ID | 검색기가 필요한 문서를 찾아왔는지 확인 |
| 근거 구절 | 기준 답변을 뒷받침하는 원문을 **그대로 인용** | 기준 답변 검수, 검색된 청크에 실제 근거가 있는지 확인 |
| 근거 위치 | 인용한 내용의 페이지·절·조항 등 | 원문에서 다시 찾고, **청크 구성이 바뀌어도 같은 근거를 추적** |
| 답변 가능 여부 | 평가 대상 원문 **전체**로 답할 수 있는지 | 검색 실패와 "원문에 답이 없는 경우"를 구분, 답변 불가 안내가 적절한지 평가 |
| 질문 유형 | 사실 확인, 조건 비교, 답변 불가 등 | 특정 유형에 편중되지 않게 구성, 유형별 취약점 확인 |

- **기준 답변은 출력 문장을 그대로 지정하는 것이 아니라 포함되어야 할 내용을 정하는 것**이다. 표현이 달라도 핵심 내용과 원문의 조건이 유지되면 된다.
- 여러 문서가 필요하면 관련 문서와 근거를 모두 작성한다. 문항 ID와 평가셋 버전을 함께 관리하고, 관련성 점수는 평가 목적에 따라 추가한다.

### 선택적으로 추가하는 항목

평가 결과를 자료 형태나 질문 특성별로 나눠 보고 싶을 때 추가한다.

| 항목 | 작성할 내용 | 필요한 이유 |
|------|-------------|-------------|
| 근거 형태 | 본문 텍스트, 표, 이미지·도표, 혼합 등 | 어떤 자료 형태에서 검색·이해가 어려운지 확인 ([PDF 표·이미지 추출](RAG_PDF표이미지추출.md)과 연결) |
| 난이도 | 쉬움·보통·어려움 | 난이도별 성능 비교, 쉬운 문항 편중 방지 |
| 복수 출처 필요 여부 | 한 문서로 가능한지, 여러 문서 근거를 종합해야 하는지 | 여러 출처를 검색·종합하는 능력 평가 |

- 난이도는 필요한 정보의 수, 조건·예외 해석, 여러 근거의 종합 여부 등으로 **미리 기준을 정해** 구분한다.
- 복수 출처는 **같은 문서의 여러 청크**를 쓰는 경우와 구분한다.

### 문서·근거 위치 vs 청크 ID

- 원문 문서와 **근거 위치**를 연결해 두면 청크 크기를 바꿔도 **같은 기준으로 비교**할 수 있다.
- **청크 ID를 정답으로 지정**하면 필요한 근거를 검색했는지 더 세밀하게 평가할 수 있지만, 재청킹할 때마다 청크 ID가 달라지므로 **평가셋도 갱신**해야 한다.

## 2. 질문과 기준 답변 작성하기

답변 가능한 문항은 **먼저 확인할 사실과 근거를 고른 뒤**, 그 내용을 묻는 질문과 기준 답변을 쓴다. 실제 사용자 질문이나 기존 실패 사례에서 시작해도 원문 근거를 확인한다.

- 질문만 읽어도 무엇을 묻는지 알 수 있게 쓴다.
- **질문에 정답을 노출하지 않고**, 실제 사용자가 쓸 법한 표현을 쓴다.
- 기준 답변에는 필요한 **조건·수치·예외**를 포함하고, **원문 밖의 내용을 추가하지 않는다.**
- 사실 확인, 조건 비교, 여러 문서를 함께 봐야 하는 질문, 유사한 용어를 구별하는 질문 등을 구성한다.
- **답변 불가 질문**, 실제 사용자 질문, **기존 RAG가 잘못 답한 질문**도 포함한다.
- 같은 사실을 표현만 바꿔 반복하거나 특정 문서에 편중되지 않게 한다. 유형과 비중은 실제 사용 상황과 확인하려는 실패 유형에 맞춘다.

## 3. 문항 작성 예시

가상의 도서관 안내 문서가 검색 대상의 전부라고 가정한다.

- 문서 제목: 도서 대출 안내 / 문서 ID: `library-guide` / 버전: `v1` / 근거 위치: 대출 기간과 연장 절

> 일반 회원은 도서를 최대 3권까지 14일 동안 대출할 수 있다. 예약자가 없는 도서는 1회에 한해 7일 연장할 수 있다.

| 항목 | 답변 가능한 문항 | 답변 불가 문항 |
|------|------------------|----------------|
| 문항 ID | `loan-extension` | `overdue-fee` |
| 질문 | 일반 회원이 빌린 도서는 어떤 조건에서 얼마나 연장할 수 있나요? / 며칠 더 빌릴 수 있어요? | 도서 반납이 늦어지면 연체료는 하루에 얼마인가요? / 반납 늦으면 얼마 내요? |
| 기준 답변 | 예약자가 없는 도서에 한해 1회, 7일 연장할 수 있다. | 제공된 문서에는 연체료 정보가 없어 하루 금액을 확인할 수 없다고 안내한다. |
| 관련 문서 | `["library-guide"]` | `[]` |
| 근거 구절 | 예약자가 없는 도서는 1회에 한해 7일 연장할 수 있다. | `[]` |
| 근거 위치 | 대출 기간과 연장 절 | 해당 없음 |
| 답변 가능 여부 | 가능 | 불가 |
| 질문 유형 | 사실 확인 | 답변 불가 |

- 첫 문항의 기준 답변은 **예약자 유무, 연장 횟수, 연장 기간을 모두** 포함해야 한다.
- 두 번째 문항은 연체료를 **추측하거나 "무료"라고 단정하지 않고** 정보가 없음을 안내해야 한다.
- 질문 칸의 `/` 뒤는 같은 질문의 **구어체 변형**이다. 같은 의도를 다른 표현으로 묻는 사례를 함께 두면 질문 표현에 대한 견고함을 볼 수 있다.

## 4. LLM으로 초안 만들기

답변 가능한 문항 초안을 LLM에게 만들게 할 때는 **원문, 문서 ID, 질문 유형, 기존 질문, 원하는 응답 항목**을 함께 제공하고, 프롬프트에 작성 기준을 명시한다.

- 제공된 원문으로 답할 수 있는 질문을 쓴다.
- 질문은 단독으로 이해할 수 있어야 하며, 기존 질문과 같은 사실을 반복하지 않는다.
- 기준 답변에 원문에 없는 조건이나 수치를 추가하지 않는다.
- 기준 답변의 **모든 핵심 내용을 뒷받침하는 원문 구절을 그대로 인용**한다.
- 질문·기준 답변·근거를 구분해서 반환한다.

주의할 점:

- 출처는 **준비한 문서와 연결**한다.
- 응답 형식(JSON 등)을 고정해도 **내용의 정확성은 보장되지 않는다.**
- 생성 결과는 **초안**일 뿐이다. 원문 검수를 거친 문항만 평가에 사용한다.

## 5. 원문과 대조하여 검수하기

| 확인 방식 | 확인할 내용 |
|-----------|-------------|
| 자동 검사 | 문항 유형별 **필수 항목 누락**, ID·질문 **중복**, **존재하지 않는 출처**, 근거 구절이 원문에 **포함되는지** |
| 사람 검수 | 질문의 자연스러움, 답변의 **정확성·완전성**, 조건·예외 누락, 출처 누락, 의미상 중복 |

- **"근거 구절이 원문에 있는가"와 "그 근거가 기준 답변을 뒷받침하는가"를 모두** 확인한다. 수치·조건·적용 범위가 원문과 일치하고 필요한 예외가 빠지지 않았는지 본다.
- 관련 문서를 찾았더라도 **검색된 청크에 답변에 필요한 근거가 없을 수 있다.** 문서 일치 여부와 실제 근거 포함 여부를 구분한다.
- 오류가 있는 문항은 수정하거나 제외하고, **수정한 문항은 다시 원문과 대조**한다.

## 6. 답변 불가 문항 구성하기

- 답변 가능 여부는 일부 청크가 아니라 **평가 대상 원문 문서 모음 전체**를 기준으로 판단한다. 검색기가 근거를 못 찾은 경우와 원문에 답이 없는 경우를 구분한다.
- 기대하는 응답 방식을 기록한다. 예: "제공된 문서로는 확인할 수 없습니다."
- 정답 근거가 없으므로 **관련 문서와 근거 목록은 비워 두고, 없는 정답이나 근거를 만들어 넣지 않는다.**
- 관련 문서 목록이 비어 있으면 **Recall@k의 분모가 0**이 된다. 해당 문항은 이 지표의 **평균에서 제외하고 제외 수를 기록**한다.
- 응답은 **별도로 평가**한다. 근거 부족을 안내하는지, 없는 사실을 지어내 답하지 않는지 확인한다.

## 7. 평가셋 분리와 버전 관리

| 구분 | 용도 |
|------|------|
| 개발셋 | 청크 크기, 검색 방식, 프롬프트를 바꾸며 **반복 비교**할 때 |
| 테스트셋 | 개선 과정에 **쓰지 않고**, 설정을 확정한 뒤 **최종 성능 확인**에만 |

- 같은 문항의 결과만 보며 개선하면 **그 문항에 맞춰질 수 있으므로** 최종 확인용 문항을 분리한다.
- 검수한 문항은 JSON·JSONL 등으로 저장한다.
- **원문과 평가셋의 버전을 함께 기록**하고, 작성 당시의 원문을 확인할 수 있도록 보관한다. 질문·정답·근거가 바뀌면 **새 버전**으로 관리한다.

## 8. RAG 평가에 연결하기

RAG에 평가 질문을 넣고 실제 검색 결과와 생성 답변을 기록해, 준비해 둔 기준과 비교한다.

| 미리 준비하는 기준 | 실행 후 기록하는 결과 |
|--------------------|------------------------|
| 관련 문서 ID와 원문 근거 | 실제 검색한 문서·청크, 출처 ID, 검색 순위 |
| 기준 답변 | RAG가 실제로 생성한 답변 |

- 기준 근거를 실제 검색 결과 **대신 넣지 않는다.**
- 질문·정답 파일을 **검색 대상 원문에 추가하지 않는다.** (평가 데이터가 검색 대상에 섞이면 정답을 그대로 찾아 점수가 부풀려진다)
- 비교할 때는 **같은 버전의 Golden Set**을 쓰고, 평가 결과에도 그 버전을 기록한다.

## 정리

- Golden Set은 질문만이 아니라 **기준 답변 + 근거 구절 + 근거 위치 + 답변 가능 여부**까지 갖춰야 검색 평가와 답변 평가를 모두 할 수 있다.
- 기준 답변은 **문장이 아니라 포함할 내용**이고, 반드시 **원문 대조**로 확정한다. LLM이 만든 문항은 초안이다.
- **답변 불가 문항**을 일부러 넣어 "모르면 모른다고 하는가"를 본다. 근거를 지어내 채우지 않고, Recall@k 평균에서는 제외한다.
- 근거는 청크 ID보다 **문서+근거 위치**로 연결해 두면 청킹 설정을 바꿔도 같은 평가셋을 재사용할 수 있다.
- 개발셋과 테스트셋을 **분리**하고, 평가셋·원문 **버전을 함께 기록**한다.
