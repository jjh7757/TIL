# LangGraph 병렬 처리 — Fan-out/Fan-in과 Voting

## 왜 병렬화하는가

하나의 문서를 법률·재무·기술 3개 관점으로 분석한다고 하면, 순차 처리는 `3초+3초+3초=9초`가 걸리지만 세 분석이 서로 독립적이라면 동시에 실행해서 `3초+α`로 줄일 수 있다. **판단 기준은 딱 하나** — "각 작업이 다른 작업의 결과 없이 시작할 수 있는가?" 그렇다면 병렬화할 수 있고, B가 A의 결과를 입력으로 써야 한다면 `A → B` 순서를 지켜야 한다. 전체 파이프라인 중 독립적인 구간만 부분적으로 병렬화하는 것도 가능하다.

## 기본 병렬 노드 (Fan-out / Fan-in)

하나의 노드 뒤에 여러 노드를 연결하면 LangGraph가 **자동으로 병렬 실행**한다.

```
START ─┬→ legal_analysis     ─┐
       ├→ financial_analysis ─┼→ summarize → END
       └→ technical_analysis ─┘
```

핵심은 State 필드에 `Annotated[list, operator.add]`를 써서 각 노드의 결과를 **하나의 리스트로 누적**하는 것 — reducer가 없으면 여러 노드가 같은 State 키를 동시에 갱신할 때 값을 서로 덮어써버린다.

**결과 순서는 보장되지 않는다.** 병렬 노드는 어떤 게 먼저 끝나느냐에 따라 리스트에 쌓이는 순서가 매번 달라질 수 있다. 순서가 의미 있는 경우(예: 법률→재무→기술 순으로 보고서에 싣고 싶을 때)에는 결과에 **식별자(순번)를 포함**시켜서 반환하고, 후처리(`summarize` 같은 Fan-in 노드)에서 그 식별자로 정렬하면 된다 — 실행 순서와 논리적 순서를 분리해서 다루는 패턴이다.

## Voting 패턴

하나의 질문에 대해 **여러 LLM 응답을 동시에 생성**하고 그중 최선을 고른다.

```
START ─┬→ generate_1 ─┐
       ├→ generate_2 ─┼→ vote → END
       └→ generate_3 ─┘
```

같은 모델에 서로 다른 프롬프트(접근 방식)를 줘서 다양한 후보를 만들거나, 서로 다른 모델을 동시에 호출해서 후보를 모을 수도 있다. 평가(judge) 역할의 LLM은 **후보 생성과 평가 기준을 분리**해서 최대한 객관적으로 고르게 구성한다. 마케팅 카피, 코드 생성, 번역처럼 결과 품질 편차가 큰 작업에 잘 맞는다.

## 그래프로 안 짜도 될 때 — batch()

작업 종류·개수가 미리 정해져 있고 각 작업을 그래프에서 개별적으로 관리(재시도, 로깅 등)해야 한다면 여러 노드를 연결하는 게 맞다. 하지만 **같은 모델에 여러 입력을 보내고 결과만 한꺼번에 받으면 충분한 경우**엔 굳이 그래프 노드를 여러 개 만들 필요 없이 한 노드에서 `llm.batch([...])`를 쓰는 게 더 간단하다 — 병렬화를 항상 그래프 구조로 표현할 필요는 없다는 실용적인 판단 기준이다.

## 병렬 실행 시 주의점

- 병렬 요청이 많으면 API의 **Rate Limit**에 걸리기 쉽다 (동적 병렬화·실행 수 제한은 [LangGraph Orchestrator-Worker](LangGraph_OrchestratorWorker.md)에서 다룬다).
- 작업 완료 순서는 보장되지 않으므로, 순서가 중요하면 결과에 식별자를 넣고 나중에 정렬한다.
- **병렬화해도 전체 시간이 가장 오래 걸리는 작업의 실행 시간보다 짧아지지는 않는다** — 병렬화는 "합"을 "최대"로 바꿔주는 것이지 마법처럼 없애주는 게 아니다.

## 실습: 병렬 번역

하나의 문장을 영어·일본어·스페인어로 동시에 번역하는 그래프를 처음부터 구현했다. 세 번역을 병렬로 실행한 뒤 결과를 정해진 언어 순서로 출력하고, 같은 작업을 순차로도 실행해서 소요 시간을 직접 비교했다 — Fan-out/Fan-in을 손으로 짜보고 "순차보다 빠르다"를 눈으로 확인하는 게 실습의 목적이었다.
