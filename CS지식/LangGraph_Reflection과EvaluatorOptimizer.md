# LangGraph Reflection과 Evaluator-Optimizer — Agent가 자기 출력을 검토하는 패턴

## Reflection 패턴

가장 단순한 자기 개선 루프다.

```
START → generate → should_continue? → END (종료)
          ↑                │ continue
          └──── reflect ←──┘
```

1. **generate**가 초안을 작성한다
2. **should_continue**가 반복 횟수를 체크한다 — 상한 도달 시 최종 초안을 남기고 종료
3. 종료 전이면 **reflect**가 초안을 읽고 피드백(톤, 빠진 정보, 길이 등)을 준다
4. 피드백을 반영해 다시 generate로

State에 `messages`를 누적하므로 generate는 이전 피드백을 자연스럽게 참고한다. 실습(사과 이메일 초안)에서는 반복할수록 실제로 품질이 올라가는 걸 확인했지만, 동시에 이 패턴의 한계도 뚜렷하게 드러났다.

**Reflection의 한계**:
- 피드백이 **자연어**라서 "얼마나 좋아졌는지" 정량화가 안 된다
- "충분히 좋다"의 기준이 없어서 결국 항상 `max_iterations`까지 반복하게 된다
- 반복할수록 피드백이 점점 미세해져서 표현 수준 차이만 지적하게 되는데, 이게 실질적 개선인지는 별도로 판단해야 한다
- 반복이 많아지면 원래 의도에서 벗어나거나 과하게 수정될 수 있다 — **반복 = 항상 품질 향상이 아니다**

## Evaluator-Optimizer 패턴

구조는 Reflection과 비슷하지만 "얼마나 좋은지"를 구조화된 점수로 판정한다.

```
START → generate → evaluate → pass → END
          ↑            │ fail
          └── optimize ←┘
```

| | Reflection | Evaluator-Optimizer |
|---|---|---|
| 평가 결과 | 자유 형식의 자연어 피드백 | 항목별 점수와 근거를 구조화해 반환 |
| 종료 조건 | 주로 고정 횟수 | 합격 기준 달성 또는 최대 횟수 도달 |
| 개선 범위 | 전체적인 피드백 | 기준에 미달한 항목을 우선 개선 |
| 판정 특성 | 종료 판단이 명시적이지 않음 | 기준은 명시적이지만 LLM 점수는 달라질 수 있음 |

점수는 "품질을 객관적으로 보장하는 값"이 아니라 **흐름을 제어하기 위한 구조화된 판단**으로 쓰는 것 — 이 관점 차이가 중요하다. 점수 자체가 진리가 아니라, 언제 멈추고 무엇을 우선 고칠지 결정하기 위한 신호일 뿐이다.

## 루브릭(Rubric) 설계가 진짜 핵심이다

루브릭은 평가 항목과 점수 기준을 정리한 채점표다. **구체적이고 측정 가능해야** 쓸모가 있다.

| 나쁜 루브릭 | 좋은 루브릭 |
|------------|------------|
| "매력적인가?" | "감정을 자극하는 단어가 1개 이상 포함되어 있는가?" |
| "적절한 길이인가?" | "50자 이상 150자 이하인가?" |
| "좋은 카피인가?" | "행동 유도(CTA)가 포함되어 있는가?" |

루브릭이 모호하면 Evaluator-Optimizer도 결국 Reflection과 다를 바 없어진다(점수가 들쭉날쭉해서 신호로 쓸모가 없어짐). 루브릭 설계 순서는: ①도메인의 핵심 품질 기준 정의 → ②각 기준을 측정 가능한 형태로 변환 → ③점수 척도와 합격 기준 설정. 도메인마다 완전히 달라진다 — 마케팅 카피라면 "감정 자극/CTA/글자 수", 기술 문서라면 "정확성/재현 가능성/코드 포함" 같은 식.

## 자기 평가 편향(self-evaluation bias) 주의

같은 LLM이 생성과 평가를 모두 수행하면, 합격 규칙을 코드로 고정해도 **점수 자체가 실행마다 달라질 수 있다**. 실무에서는 평가에 더 강한 모델을 쓰거나, 생성 모델과 평가 모델을 아예 분리해서 자기 평가 편향을 줄이기도 한다.

## 실습: 제품 리뷰 요약을 두 패턴으로 각각 구현

같은 과제(리뷰를 3~5문장으로 요약)를 Reflection(`generate → should_continue → reflect`)과 Evaluator-Optimizer(`generate → evaluate → optimize`, 루브릭 4항목 각 1~10점·8점 이상 통과) 양쪽으로 구현해서 비교했다. 실무에서 Evaluator-Optimizer를 쓸 때 **루브릭 설계가 가장 중요한 단계**라는 게 이 실습 전체의 결론이다 — 루브릭이 모호하면 Reflection과 다를 게 없고, 구체적이면 개선 방향이 명확해진다.
