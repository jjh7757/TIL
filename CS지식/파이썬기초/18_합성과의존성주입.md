# 합성(Composition)과 의존성 주입

## 상속(is-a) vs 합성(has-a)

상속은 "자식은 부모의 한 종류다(is-a)"라는 관계를 표현한다. 하지만 관계가 "A는 B를 가지고 있다(has-a)"에 가깝다면 상속보다 **합성**이 더 적합하다 — 한 클래스가 다른 클래스의 인스턴스를 속성으로 가지고, 그 객체의 기능을 빌려 쓰는 방식이다.

```python
class Computer:
    def use(self):
        print("컴퓨터 사용!")

class Person:
    def __init__(self):
        self.tool = None

person = Person()
person.tool = Computer()   # "사람은 컴퓨터를 쓸 수 있다"를 상속이 아니라 합성으로 표현
person.tool.use()
```

`Person`이 컴퓨터를 쓸 수 있다고 해서 `PersonUsingComputer(Person)`처럼 상속으로 풀면, 컴퓨터를 쓰는 사람이 늘어날 때마다 클래스가 계속 늘어나 확장성이 떨어진다. 합성으로 풀면 필요한 객체를 속성에 갈아 끼우기만 하면 된다.

```python
class Engine:
    def __init__(self, horsepower):
        self.horsepower = horsepower
    def start(self):
        return f"{self.horsepower}마력 엔진이 가동됩니다."

class Car:
    def __init__(self, model, horsepower):
        self.model = model
        self.engine = Engine(horsepower)   # Car가 Engine을 "가지고" 있음

    def drive(self):
        return f"{self.model} 모델이 {self.engine.start()} 주행을 시작합니다."

print(Car("전기차", 300).drive())
```

`Person`이 `Address`를 속성으로 갖는 경우처럼, 합성은 "여러 데이터를 하나로 묶은 객체"를 다른 객체 안에 중첩할 때도 자연스럽게 쓰인다.

## 의존성 주입(Dependency Injection) — 객체를 밖에서 넣어주기

합성할 객체를 클래스 내부에서 직접 만드는 대신 생성자의 인자로 **밖에서 넣어주면(주입)**, 그 클래스는 구체적으로 어떤 구현체가 들어올지 몰라도 동작할 수 있다.

```python
class Logger:
    def log(self, message):
        print(f"[시스템 로그]: {message}")

class AdvancedLogger:
    def log(self, message):
        print(f"--- [상세 분석 로그] --- 내용: {message}")

class Service:
    def __init__(self, logger):
        self.logger = logger   # 어떤 로거를 쓸지는 Service가 정하지 않는다

    def perform_action(self):
        self.logger.log("작업이 완료되었습니다.")

Service(Logger()).perform_action()
Service(AdvancedLogger()).perform_action()
```

`Service`는 `logger`가 `Logger`인지 `AdvancedLogger`인지 알 필요가 없다 — `log(message)`만 호출할 수 있으면 된다. 전원 공급 방식이 다른 `Battery`/`PlugIn`을 `ElectronicDevice`에 갈아 끼우는 것도 같은 패턴이다. 이렇게 두면 새로운 구현체(새 로거, 새 전원 방식)가 추가돼도 `Service`나 `ElectronicDevice`의 코드는 건드릴 필요가 없다.

## 실전 예제 1 — 게임 캐릭터 시스템 (추상 클래스 + 합성)

직업(`Job`)과 무기(`Weapon`)를 각각 추상 클래스로 두고, 캐릭터(`Character`)가 이 둘을 속성으로 합성한다. 무기를 착용할 때는 "이 직업이 이 무기를 허용하는지"를 `type()`으로 검사한다.

```python
# job.py
class Job(ABC):
    @abstractmethod
    def attack(self):
        pass

class Warrior(Job):
    allow_weapon_list = {Sword}
    def attack(self):
        print("검을 휘두른다!")

# character.py
class Character:
    def __init__(self, name, job: Job):
        self.name = name
        self.job = job
        self.weapon: Weapon | None = None

    def equip_weapon(self, weapon: Weapon):
        if type(weapon) in self.job.allow_weapon_list:   # 허용 목록에 있는 무기 종류인지 확인
            self.weapon = weapon
        else:
            print("장비할 수 없습니다.")
```

`Character`는 `Job`이 전사인지 마법사인지, `Weapon`이 검인지 지팡이인지 구체적으로 알 필요 없이 정해진 인터페이스(`attack()`, `skill()`)만 호출한다 — 다형성과 합성이 함께 쓰인 예다.

## 실전 예제 2 — 스마트홈 허브 (프로토콜 호환성 체크)

기기(`Device`)마다 통신 프로토콜(`Protocol`)을 가지고 있고, 허브(`SmartHub`)는 자신과 **같은 프로토콜을 쓰는 기기만** 등록받는다. 타입 비교는 `type(a) is type(b)`보다 상속 관계까지 고려하는 `isinstance`가 더 안전하다.

```python
class SmartHub:
    def __init__(self, name, protocol: Protocol, devices: list[Device] = []):
        self.name = name
        self.protocol = protocol
        self.devices = devices

    def register_device(self, device: Device):
        if isinstance(device.protocol, type(self.protocol)):
            self.devices.append(device)
            print("연결 완료")
        else:
            print("연결 실패")   # 프로토콜이 다른 기기는 등록 거부

    def run_all(self):
        for device in self.devices:
            device.protocol.start_connection()
            device.run()   # Device의 실제 서브클래스가 무엇이든 동일하게 호출 (다형성)
```

`Device`, `Protocol` 모두 `abstractmethod`로 최소한의 인터페이스(`run`/`check_status`/`stop`, `start_connection`)만 강제하고, 실제 동작은 `SmartLight`, `AirConditioner`, `WiFiProtocol`, `ZigbeeProtocol` 등 구체 클래스가 각자 구현한다.

## 실전 예제 3 — 자판기 (합성 + 사용자 정의 예외)

`VendingMachine`은 상품(`Product`)들과 결제 수단(`Payment`)을 합성으로 가지고 있다. 결제 성공/실패 판단은 `VendingMachine`이 아니라 각 `Payment` 구현체(`CashPayment`/`CardPayment`)가 스스로 내리고 `bool`만 돌려준다 — [의존성 주입](#의존성-주입dependency-injection--객체를-밖에서-넣어주기)에서 본 것과 같은 방식으로, `VendingMachine`은 현금인지 카드인지 몰라도 동작한다.

```python
class Payment(ABC):
    @abstractmethod
    def pay(self, price: int) -> bool: ...

class CashPayment(Payment):
    def __init__(self, cash):
        self.cash = cash
    def pay(self, price):
        if self.cash >= price:
            self.cash -= price
            return True
        return False
```

"상품이 없음", "재고가 없음"은 프로그램 문법 오류가 아니라 **정상적으로 일어날 수 있는 상황**이다. 이런 상황도 [사용자 정의 예외](14_예외처리.md#사용자-정의-예외)로 표현해두면, 발생시킨 곳(`choose_product`)과 처리하는 곳(`run`)을 분리해 호출부에서 상황별로 다르게 대응할 수 있다.

```python
class NotFoundException(Exception):
    pass

class OutOfStockException(Exception):
    pass

def choose_product(self):
    user_input = input()
    if user_input not in self.products:
        raise NotFoundException("없는 상품입니다.")

    product = self.products[user_input]
    if product.stock == 0:
        raise OutOfStockException("재고가 없습니다.")
    return product

def run(self, payment):
    try:
        product = self.choose_product()
        if self.process_payment(product, payment):
            print(f"물건 나옵니다. {product.name}")
    except NotFoundException:
        print("그런 상품 없습니다.")
    except OutOfStockException as e:
        print(e)
```

`choose_product`는 "예외적인 상황이 있었다"는 사실만 던지고, 그 상황을 사용자에게 어떻게 보여줄지는 `run`이 결정한다 — 데이터를 가져오는 로직과 실패 처리를 분리한다는 점에서 [requests 실습](../requests실습.md#예외-처리)의 `raise_for_status()` 패턴과 같은 흐름이다.
