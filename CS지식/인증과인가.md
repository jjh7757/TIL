# 인증과 인가 — 쿠키, 세션, 토큰, JWT

로그인 상태가 어떻게 유지되는지를 **인증(Authentication)과 인가(Authorization)**, **쿠키·세션·토큰·JWT**의 관계로 정리했습니다. FastAPI 구현은 [FastAPI JWT 회원가입과 로그인](FastAPI_JWT회원가입로그인.md), [FastAPI 작성자가 있는 게시글](FastAPI_작성자게시글.md)에 이어집니다. 요청·응답 기초는 [HTTP 기초](HTTP기초.md)를 참고하세요.

## 인증과 인가

| 구분 | 의미 | 예 |
|------|------|-----|
| 인증 (Authentication) | 사용자·장치의 **신원을 확인** | 로그인 |
| 인가 (Authorization) | 요청한 작업을 **수행할 권한**이 있는지 확인해 허용·거부 | 관리자는 공지사항 작성 가능, 일반 사용자는 불가 |

술집에 빗댄 비유:

| 인증 | 권한 | 결과 |
|------|------|------|
| X | - | 민증을 놓고 와서 못 들어감 |
| O | X | 고등학교 학생증을 들고 가서 못 들어감 (신원은 확인됐지만 입장 권한 없음) |
| O | O | 민증을 들고 가서 들어감 |

- 인증이 먼저, 인가가 그다음이다. 인증 실패는 보통 **401**, 인가 실패는 **403**이다. ([HTTP 상태 코드](HTTP상태코드.md))

## HTTP와 로그인 상태

- HTTP는 **무상태(Stateless)** 프로토콜이다. 각 요청은 독립적으로 처리되고, HTTP 자체가 이전 요청의 로그인 상태를 유지해 주지는 않는다.
- 그런데도 로그인 후 페이지를 이동하거나 새로고침해도 로그인이 유지되는 것은, 매 요청에 **"나는 로그인한 그 사용자"임을 증명하는 값**을 함께 보내기 때문이다. 그 수단이 쿠키·세션·토큰이다.

### 쿠키, 세션, 토큰, JWT의 관계

| 개념 | 역할 |
|------|------|
| 쿠키 | 브라우저가 데이터를 저장하고, 조건에 맞는 요청에 **자동으로 전송**하는 수단 |
| 세션 | **서버**에 사용자 상태를 저장하고, 전달받은 세션 ID로 조회하는 방식 |
| 토큰 | 인증이나 접근 권한을 확인할 때 **제시하는 값** |
| JWT | 사용자 식별자 등의 정보를 담을 수 있는 **토큰 형식**의 하나 |

- 서로 같은 층위가 아니다. 쿠키는 **전달·저장 수단**, 세션은 **서버 저장 방식**, 토큰은 **제시하는 값**, JWT는 **토큰의 형식**이다.
- 쿠키에는 세션 ID를 담을 수도 있고 JWT를 담을 수도 있다.

## 쿠키와 세션

### 쿠키(Cookie)

웹 브라우저에 저장되는 작은 데이터 조각이다. 브라우저는 조건에 맞는 요청에 쿠키를 **자동으로 포함**해 서버로 보낸다.

| 속성 | 의미 |
|------|------|
| `Expires` / `Max-Age` | 만료 시각 / 남은 유효 시간(초) |
| `HttpOnly` | JavaScript에서 쿠키에 **직접 접근하는 것을 차단** (XSS로 인한 탈취 완화) |
| `Secure` | 쿠키를 **HTTPS로만** 전송 |

### 세션(Session)

여러 요청에 걸쳐 사용자 상태를 유지하는 방식이다.

- 사용자 식별자, 로그인 상태 등 **세션 정보는 서버**의 DB, 메모리, Redis 등에 저장한다.
- 클라이언트에는 **세션 ID만** 전달하고, 서버는 요청에 포함된 ID로 세션 정보를 조회한다.
- 웹 브라우저에서는 보통 쿠키에 세션 ID를 저장한다.
- 서버가 세션을 **삭제하거나 만료**시킬 수 있다. (서버가 통제권을 가진다)

## 토큰(Token)

인증이나 접근 권한을 확인하는 데 쓰는 값이다.

1. 로그인에 성공하면 서버가 토큰을 **발급**하고, 클라이언트는 이를 **저장**한다.
2. 인증이 필요한 요청에 저장한 토큰을 **함께 보낸다.**
3. 서버가 토큰을 **검증**해 사용자를 확인한다.

## JWT(JSON Web Token)

JSON 형태의 정보를 담아 전달하는 표준 토큰 형식이다. 주로 인증과 정보 교환에 쓰이고, 쿠키에 저장해 요청에 포함할 수도 있다. ([jwt.io](https://www.jwt.io/)에서 디코딩해 볼 수 있다.)

- **자가 수용성(Self-contained)**: 토큰 자체에 사용자 식별자 등의 정보를 담을 수 있다.
- **확장성(Scalability)**: 서버의 세션 저장소를 조회하지 않고도 토큰을 검증할 수 있어, **여러 서버로 확장**할 때 유리하다.

### 구성

일반적으로 쓰는 서명형 JWT는 **헤더 · 페이로드 · 서명** 세 부분이다.

| 부분 | 내용 |
|------|------|
| 헤더 | 서명 알고리즘, 토큰 타입 등의 메타데이터 |
| 페이로드 | 사용자 식별자, 만료 시각 등의 정보(**claim**) |
| 서명 | 토큰 내용의 **위변조 여부 검증**에 사용 |

페이로드의 대표 claim:

| claim | 의미 |
|-------|------|
| `sub` | 토큰의 주체. 사용자 인증에서는 사용자 ID 등 |
| `exp` | 만료 시각 |
| `iat` | 발급 시각 |

### 보안상 알아둘 점

- **Base64URL 인코딩은 암호화가 아니다.** 누구나 디코딩해 읽을 수 있으므로 **비밀번호 등 민감한 정보를 넣지 않는다.**
- 서명은 내용을 **숨기는** 것이 아니라 **바뀌지 않았음을 증명**한다. 내용을 읽을 수 있어도 서명 키 없이 내용을 바꿔 유효한 서명을 만들 수는 없다.
  - 예: HS256은 서버의 **비밀 키**로 서명을 생성·검증한다. 비밀 키는 토큰에 넣지 않는다.
- **디코딩해서 읽는 것과 검증하는 것은 다르다.** 서버가 허용한 알고리즘과 키로 서명을 검증해야 한다.
- 인증용 토큰에는 만료 시각 등 필요한 claim을 넣고, 서버에서 **그 존재 여부와 값을 검증**한다.
- **검증되지 않은 페이로드의 사용자 ID나 권한을 신뢰하지 않는다.**

### 단점

- 일반적으로 세션 ID보다 **크기가 크다.**
- 발급된 토큰은 **만료 전에 개별적으로 무효화하기 어렵다.**
- 토큰에 담긴 권한만 확인하면, 서버에서 바꾼 사용자 권한이 **기존 토큰에 즉시 반영되지 않는다.**

## Access Token과 Refresh Token

토큰의 **역할에 따른 구분**이고, JWT는 토큰의 **형식**이다. (둘 다 JWT일 수 있다.)

| 구분 | 용도 | 유효기간 | 비고 |
|------|------|----------|------|
| Access Token | 인증이 필요한 API·리소스에 접근 | 비교적 **짧게** (탈취됐을 때 쓸 수 있는 시간을 줄이려고) | |
| Refresh Token | Access Token **재발급** | 일반적으로 Access보다 **길게** | 서버가 유효 여부를 확인·폐기할 수 있도록 DB 등에 관리하기도 함. **선택 사항** |

## 로그아웃과 만료

| 방식 | 로그아웃 처리 |
|------|---------------|
| 세션 | 서버의 세션을 **무효화**하고 브라우저의 세션 ID 쿠키도 삭제 |
| JWT | 클라이언트에 저장된 **토큰을 삭제**하고 이후 요청에 보내지 않음 |

- Refresh Token을 폐기하면 그 토큰으로의 재발급을 막을 수 있다. 다만 **이미 발급된 Access Token이 함께 무효화되지는 않는다.** (만료까지 유효)

## 세션 vs JWT 한눈에 보기

| | 세션 | JWT |
|---|------|-----|
| 상태 저장 위치 | 서버(DB·메모리·Redis) | 토큰 자체(클라이언트가 보관) |
| 클라이언트가 보내는 값 | 세션 ID | 토큰 |
| 서버 조회 | 매 요청 세션 저장소 조회 | 서명·claim 검증(저장소 조회 불필요) |
| 즉시 무효화 | 쉬움 (서버에서 삭제) | 어려움 (만료 전 개별 무효화 곤란) |
| 확장 | 세션 저장소 공유 필요 | 서버 여러 대에서 검증 용이 |

## 정리

- 인증 = **누구인가**, 인가 = **무엇을 할 수 있는가**. 401과 403으로 나뉜다.
- HTTP는 무상태라서, 매 요청에 신원 증명(세션 ID나 토큰)을 실어 보낸다.
- 쿠키는 수단, 세션은 서버 저장 방식, JWT는 토큰 형식이다. 서로 조합할 수 있다.
- JWT 페이로드는 **읽을 수 있다.** 민감 정보를 넣지 말고, 서명·만료·필수 claim을 **검증한 값만** 신뢰한다.
- JWT는 서버 조회 없이 확장하기 좋지만 **즉시 무효화가 어렵다.** 그래서 Access Token은 짧게, 필요하면 Refresh Token으로 재발급한다.
