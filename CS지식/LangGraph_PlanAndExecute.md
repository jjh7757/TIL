# LangGraph Plan-and-Execute — 계획을 먼저 세우고 재계획하기

## ReAct와 뭐가 다른가

ReAct는 매 순간 "다음에 뭘 할지"만 결정한다. Plan-and-Execute는 **전체 계획을 먼저 세운 뒤** 단계별로 실행하고, 중간 결과를 보고 필요하면 남은 계획을 다시 짠다.

| 구분 | ReAct | Plan-and-Execute |
|---|---|---|
| 계획 범위 | 매 순간 다음 행동 결정 | 전체 계획을 먼저 수립 |
| 장점 | 단순하고 빠름 | 복잡한 목표와 제약 조건 처리에 유리 |
| 단점 | 전체 흐름을 놓칠 수 있음 | 계획과 재계획 비용 발생 |
| 적합한 작업 | 단일 조회, 간단한 질의 | 조사, 비교, 일정 설계, 보고서 작성 |

```
입력 → Planner → Executor → Replanner → Executor → ... → 최종 응답
```

- **Planner**: 실행할 단계 목록을 만든다
- **Executor**: 현재 계획의 첫 단계를 수행한다
- **Replanner**: 실행 결과가 충분한지 판단해서 종료하거나 남은 계획을 교체한다

"단일 조회"에는 ReAct로 충분하고, "여러 조건을 동시에 만족해야 하는 조사·비교·일정 설계"처럼 **중간에 실패하면 다른 경로를 다시 짜야 하는 작업**에 Plan-and-Execute가 맞는다는 구분 기준이 명확했다.

## State 설계 — 언제 reducer를 쓰고 언제 안 쓰는가

| 필드 | 타입 | 역할 | reducer |
|---|---|---|---|
| `input` | `str` | 사용자의 원래 요청 | 없음(덮어쓰기) |
| `plan` | `list[str]` | 앞으로 실행할 단계 | 없음(덮어쓰기) |
| `past_steps` | `list[tuple]` | 완료한 단계와 결과 | `operator.add`(누적) |
| `response` | `str` | 최종 응답 | 없음(덮어쓰기) |

`past_steps`는 실행 이력이라 절대 잃으면 안 되니까 누적(`operator.add`)해야 하고, `plan`은 정반대로 **Replanner가 남은 계획 전체를 통째로 교체할 수 있어야 하니까 reducer 없이 덮어쓰기**로 둔다. 같은 그래프 안에서도 필드마다 "이 값은 누적돼야 하는가, 아니면 통째로 갈아치워야 하는가"를 따로 판단해야 한다는 게 핵심 — [LangGraph 기초](LangGraph_기초.md)의 Reducer 선택 기준(최신 값만 필요하면 덮어쓰기, 이력이 필요하면 누적)이 여기서도 그대로 적용된다.

## Replanner의 출력 타입 설계: Union[Plan, Response]

Replanner는 한 번의 호출에서 **"남은 계획을 다시 반환"하거나 "최종 응답을 반환"하거나 둘 중 하나만** 한다 — 동시에 둘 다 필요한 상황은 없다. 그래서 `ReplanDecision.decision` 필드를 `Union[Plan, Response]`로 선언해서 "둘 중 하나만 선택"을 타입 레벨에서 강제한다.

다만 그래프의 State 자체에서는 실행 중 쓰는 `plan`과 종료 시 쓰는 `response`의 **역할이 다르므로 별도 필드로 관리**한다 — Replanner의 출력(하나만 있으면 되는 판정 결과)과 State의 필드 설계(역할이 다르면 나눠야 하는 데이터)는 다른 문제라는 걸 구분해서 보여주는 예였다.

## 완료된 단계를 계획에서 빼지 않으면 무한 반복

완료된 단계를 새 계획에서 제거하지 않으면 Replanner가 **같은 검색을 계속 반복**시킬 수 있다. 이걸 막는 이중 장치:

1. 프롬프트에서 "완료된 단계는 반복하지 말라"고 명시
2. `recursion_limit`으로 안전장치를 건다 — 한 번의 그래프 실행에서 허용하는 **최대 노드 실행 횟수**(같은 노드를 여러 번 도는 것도 포함해서 카운트). `recursion_limit=20`이면 21번째 노드 실행에서 `GraphRecursionError`가 난다.

프롬프트로 유도하는 것과 코드로 강제하는 것을 같이 쓴다는 점이 [LangGraph 가드레일](LangGraph_가드레일.md)에서 봤던 "중요한 규칙은 LLM 판단에만 맡기지 않는다"는 원칙과 같은 맥락이다.

## 실습: Replanner 없는 Plan-and-Execute

Replanner는 필수 구성 요소가 아니다 — 실행 결과와 무관하게 **처음 계획을 그대로 다 수행해도 되는 작업**이라면 Replanner 없이 Planner → Executor 반복 → Finalizer로 충분하다. 실습에서는 기존 여행 계획 그래프에서 Replanner를 빼고, Executor가 `{"plan": state["plan"][1:]}`을 반환해서 완료한 단계를 직접 `plan`에서 제거하며(`plan`이 남아있으면 Executor를 다시 실행, 다 떨어지면 Finalizer가 `past_steps`로 최종 응답 작성) 더 단순한 버전을 만들어보는 게 과제였다 — "재계획이 필요한가?"라는 질문 하나로 그래프 복잡도를 크게 줄일 수 있다는 걸 보여주는 실습이었다.
