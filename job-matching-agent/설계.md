# Job-Matching Agent 설계

> 작성일: 2026-09-30 · 상태: 설계 완료, 코드 미작성 (v1은 직접 구현)

내 스킬과 실제 채용 공고(원티드 API)를 비교해 주는 AI 에이전트.
서비스 자체보다 **최근 배운 LangGraph 패턴을 얼마나 잘 보여주는가**가 목표다.

## 1. 범위

### v1 (이 문서의 대상)

실패 지점을 쉽게 좁히려고 아래 세 가지로만 제한한다.

1. **Supervisor + Handoff 멀티에이전트** — `Command(goto=...)` 기반 직접 구현
2. **Postgres Checkpointer** — 대화/검색 이력이 세션을 넘어 유지
3. **Redis 캐시** — 원티드 API 응답 캐싱 (반복 호출, rate limit 회피)

### v2로 미룬 것

Agentic RAG(저장한 공고 코퍼스), HITL 승인(검색 알림 저장 등), Time Travel, 장기 Store(사용자 프로필 기억).
v1에 넣으면 실패 원인을 분리하기 어렵다.

### 인터페이스

웹 채팅. FastAPI 백엔드 + 단순 정적 프런트, SSE 스트리밍.
AWS 환경에 직접 배포한다 (langgraph_mini와 같은 방식).

## 2. 전체 구조

```
[웹 채팅] ──SSE──> [FastAPI  /chat]
                      │  thread_id 로 세션 구분
                      ▼
              [LangGraph  Supervisor]
              ┌────────┼─────────┐
          research   analysis   matching
            │
      [Redis 캐시] ← [Wanted API]

  상태 저장: PostgresSaver (공유 postgres 컨테이너)
```

## 3. 에이전트

| 에이전트 | 책임 | 도구 |
|---|---|---|
| supervisor | 의도 파악, 라우팅, 최종 응답 조합 | handoff (`Command(goto=...)`) |
| research | 공고 검색, 목록/상세 조회 | `search_jobs`, `get_job_detail` (Redis 경유) |
| analysis | 공고 본문에서 필수/우대 스킬, 연차 등을 구조화 추출 | 없음 (구조화 출력) |
| matching | 사용자 스킬과 비교해 매칭 점수, 부족 스킬 산출 | `get_user_profile` |

### 직접 구현을 택한 이유

`langgraph-supervisor` 라이브러리를 쓰면 handoff가 내부로 숨어서 어떤 패턴인지 드러나지 않는다.
`Command(goto=..., update=...)`로 직접 노드를 이동시키면 Supervisor/Handoff의 동작 원리가 코드에 그대로 보인다.
쇼케이스 목적에 맞다.

## 4. State

```python
class State(MessagesState):
    user_profile: dict         # 보유 스킬, 연차, 희망 직군
    postings: list[dict]       # research 결과
    analyses: dict[str, dict]  # posting_id -> 추출된 요구사항
    matches: list[dict]        # 점수 + 부족 스킬
```

- 에이전트끼리 **메시지가 아니라 state 필드**로 데이터를 넘긴다. 어느 단계에서 값이 깨졌는지 바로 보인다.
- 사용자 프로필은 v1에서 직접 입력(또는 설정 파일)으로 받는다. 이력서 파싱은 하지 않는다.

## 5. 저장소

### Postgres Checkpointer
- `thread_id` 단위로 대화 유지.
- 공유 `postgres` 컨테이너를 쓰고, 새 DB/유저를 만드는 절차는 `AWS배포환경/DB환경구성.md`의 "새 프로젝트에 DB 붙이기"를 따른다.

### Redis 캐시
- 공유 `redis` 컨테이너, DB index `1` 사용 (`AWS배포환경/환경정보.md`에 기록).
- 키: `jm:wanted:{endpoint}:{params_hash}`
- TTL: 검색 1시간, 상세 24시간 (초안, 운영하며 조정)

## 6. 디렉터리 (별도 저장소)

```
job-matching/
├─ app/

│  ├─ tools/wanted.py  # API 호출 + 캐시 래퍼

```

## 7. 구현 순서

실패 지점을 분리하기 위한 순서다. 앞 단계가 검증되기 전에는 다음으로 넘어가지 않는다.

1. `tools/wanted.py` + 캐시 — 단독 실행으로 검증 (캐시 hit/miss 확인)
2. research 에이전트 하나로 그래프 구성 + Checkpointer 연결 (재시작 후 대화 복원 확인)
3. analysis, matching 추가 후 supervisor로 묶기
4. FastAPI + SSE + 웹 UI
5. Docker화 후 AWS 배포 (`AWS배포환경/새앱배포절차.md`)
