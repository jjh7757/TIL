# 금융 뉴스 자동 브리핑 시스템 기획서

| 항목 | 내용 |
|---|---|
| 프로젝트명 | 리서치팀 아침 금융 브리핑 자동화 |
| 요청 부서 | 자산운용사 리서치팀 |
| 구현 도구 | n8n Cloud |
| LLM | Google Gemini (n8n Google Gemini Chat Model 노드) |
| 작성일 | 2026-08-05 |

---

## 1. 배경과 목적

### 1.1 현재 문제

리서치팀원은 매일 아침 출근 전 개인적으로 뉴스 사이트를 순회하며 시장 기사를 읽는다. 여기서 세 가지 문제가 발생한다.

| # | 문제 | 결과 |
|---|---|---|
| P1 | 팀원마다 보는 매체가 다름 | 같은 팀인데 아는 뉴스가 제각각 → 회의 시 정보 비대칭 |
| P2 | 전체 기사 중 금융 기사 비중이 낮음 | 연예·스포츠를 걸러내는 데 시간 소모 |
| P3 | 어제 읽은 기사를 오늘 다시 읽음 | 중복 열람으로 시간 낭비 |

### 1.2 목표

매일 아침 **8시 30분**, 복수 매체의 뉴스 중 **금융 관련 기사만** 골라 요약하고, **중요한 것만 추려** 하나의 디스코드 메시지로 발송한다. 팀원은 이 메시지 하나만 확인하면 된다.

### 1.3 성공 기준

- 팀원이 아침에 아무것도 누르지 않아도 브리핑이 도착한다
- 브리핑에 연예·스포츠·날씨 기사가 포함되지 않는다
- 어제 발송된 기사가 오늘 다시 나오지 않는다
- 중요 기사가 없는 날에도 "없음"을 알리는 메시지가 도착한다 (침묵하지 않는다)

### 1.4 이 문서의 범위

본 문서는 워크플로우 설계와 설계 근거를 다룬다. RSS 피드는 2026-08-05 실제 요청으로 응답을 검증했으며 결과를 부록 A에 남겼다. LLM은 Google Gemini를 사용한다(n8n의 Structured Output Parser는 모델에 구애받지 않는 방식이라 Gemini로도 4개 필드 JSON 강제가 동일하게 동작함을 확인했다). API 키, 디스코드 채널 ID 등 나머지 환경값은 구현 단계에서 확정한다.

## 2. 전체 아키텍처

### 2.1 파이프라인 개요

```
[08:30 Schedule Trigger]
        │
        ▼
  ┌─────────────────┐
  │ RSS 피드 A      │──┐
  │ RSS 피드 B      │──┼──▶ Merge(Append) ──▶ 정규화 + article_id 생성
  │ RSS 피드 C      │──┘        (각 피드 실패해도 계속 진행)
  └─────────────────┘
        │
        ▼
  실행 내 중복 제거 (같은 기사를 두 피드가 보도한 경우)
        │
        ▼
  ★ 발송 이력 대조 (Google Sheets) ── 이미 처리한 기사 제거   ← REQ-03
        │
        ▼
  ★ 금융 키워드 필터 ── 비금융 기사 제거                      ← REQ-04
        │
        ▼
  [IF] 남은 기사 0건? ──── Yes ──▶ "수집 결과 없음" 브리핑 발송
        │ No
        ▼
  본문 추출 ── 원문 페이지에서 기사 본문 확보 (실패 시 폴백)
        │
        ▼
  LLM 요약 + 중요도 분류 (JSON 구조화 출력)                    ← REQ-05
        │
        ▼
  스키마 검증 → 실패 시 needs_review = true
        │
        ▼
  importance >= 4 필터
        │
        ├── 0건 ──▶ "오늘은 중요 기사 없음" 브리핑 발송        ← REQ-06 빈 경로
        │
        ▼
  메시지 1건으로 병합 → 디스코드 발송                          ← REQ-06
        │
        ▼
  Google Sheets에 처리 이력 누적                               ← REQ-07
```

`★` 표시된 두 단계는 **반드시 LLM 호출 앞에** 위치한다. 근거는 3.3, 3.4에서 설명한다.

## 3. 요구사항별 설계

### 3.1 REQ-01 :: 수집 (RSS)

#### 설계

서로 다른 매체의 RSS 피드를 **3개** 연결한다. 요구사항은 최소 2개지만, 한 곳이 장애일 때 남은 두 곳으로 브리핑이 유지되도록 여유분을 둔다.

아래 피드는 2026-08-05 실제 요청으로 응답을 검증했다. (검증 상세는 부록 A)

| 피드 | 매체 | URL | 기사 수 | 검증 결과 |
|---|---|---|---|---|
| A | 연합뉴스 경제 | `https://www.yna.co.kr/rss/economy.xml` | 120 | 채택. 건수가 가장 많고 `guid`가 원문 URL |
| B | 매일경제 경제 | `https://www.mk.co.kr/rss/30100041/` | 50 | 채택 |
| C | 조선일보 경제 | `https://www.chosun.com/arc/outboundfeeds/rss/category/economy/?outputType=xml` | 100 | 채택 |
| 예비 | 이데일리 전체 | `https://rss.edaily.co.kr/edaily_news.xml` | 50 | 예비. 경제 전용이 아니라 사회·연예 기사가 섞임 |

**후보에서 제외한 피드**

| 매체 | URL | 제외 사유 |
|---|---|---|
| 한국경제 | `https://www.hankyung.com/feed/economy` | 응답은 정상(50건)이나 **`description` 필드 자체가 없다.** 제공 필드가 `title, link, author, pubDate`뿐이라 요약에 넣을 본문이 없다 |
| SBS Biz | `https://biz.sbs.co.kr/rss/news_finance.xml` | User-Agent를 지정해도 403 차단 |

> **주의 — User-Agent**: 매일경제는 기본 UA로 요청하면 403을 반환하고, 일반 브라우저 UA를 지정하면 정상 응답한다. n8n RSS Read 노드가 403을 받으면 **피드 URL이 틀린 것으로 오판하기 쉬우므로**, 403이 나면 HTTP Request 노드로 대체하고 헤더에 `User-Agent: Mozilla/5.0`을 지정한 뒤 XML을 파싱한다.

#### 본문(snippet) 확보 — RSS만으로는 부족

검증 결과 RSS가 주는 본문은 어느 매체든 100자 안팎에 그친다.

| 매체 | `description` 평균 | `content:encoded` |
|---|---|---|
| 조선일보 | 118자 | 있으나 평균 126자 (100건 중 87건이 200자 미만) |
| 매일경제 | 100자 | 없음 |
| 연합뉴스 | 80자 | 없음 |
| 한국경제 | 0자 | 없음 → 제외 |

조선일보는 `content:encoded`를 제공하지만 실측 평균이 126자로 `description`과 사실상 차이가 없다. **즉 4개 매체 모두 RSS 필드만으로는 3문장 요약의 근거가 부족하다.** 100자짜리 리드 문장만 보고 요약하면 LLM이 사실상 제목을 바꿔 쓰게 되고, 중요도 판정도 리드 문단에만 의존하게 된다.

따라서 원문 페이지에서 본문을 확보하는 단계를 파이프라인에 추가한다. 상세 설계는 **3.5 본문 추출**을 참고한다.

#### 피드를 2개 이상 쓰는 이유

1. **커버리지**: 매체마다 다루는 기사가 다르므로 P1(팀원 간 정보 비대칭)을 해소하려면 복수 소스가 필요하다.
2. **장애 격리**: 한 피드가 응답하지 않거나 빈 결과를 반환해도 브리핑 전체가 멈추면 안 된다.

#### 장애 격리 구현

- 각 RSS 노드의 오류 처리를 **`Continue (using error output)`** 으로 설정한다. 한 노드가 실패해도 워크플로우는 다음 노드로 진행된다.
- Merge 노드는 살아있는 피드의 결과만 받는다.
- 실패한 피드 수를 카운트해 브리핑 하단에 **수집 상태 푸터**로 노출한다. (예: `수집: 연합 42 / 한경 0(실패) / 매경 31`)
  → 받는 사람이 "오늘 기사가 적은 이유"를 알 수 있고, 조용한 실패(silent failure)를 방지한다.
- 3개 피드가 **전부** 실패한 경우에만 장애 알림 경로(3.6)로 보낸다.

#### 수집 후 표준화 필드

| 필드 | 출처 | 설명 |
|---|---|---|
| `title` | RSS `title` | 기사 제목 |
| `url` | RSS `link` | 원문 링크 |
| `published_at` | RSS `pubDate` | 발행 시각 (KST 변환) |
| `source` | 노드별 하드코딩 | 매체명 |
| `snippet` | RSS `contentSnippet` / `description` | 요약용 본문 일부 (HTML 태그 제거, 1,000자 절단) |

### 3.2 REQ-02 :: 트리거 (스케줄)

#### 설계

- **Schedule Trigger** 노드, Cron 표현식 `30 8 * * *`
- 워크플로우 설정의 타임존을 **`Asia/Seoul`** 로 명시한다. n8n 인스턴스 기본 타임존이 UTC인 경우 09:30 발송 사고가 나므로 반드시 확인한다.
- 워크플로우를 **Active** 상태로 저장해야 스케줄이 동작한다. (비활성 상태에서는 수동 실행만 가능)

#### 검증 방법

다음 날 아침까지 기다리지 않고 아래 순서로 확인한다.

| 단계 | 방법 | 확인 사항 |
|---|---|---|
| 1 | `Execute Workflow` 수동 실행 | 전체 경로가 끝까지 흐르는가 |
| 2 | Cron을 `*/5 * * * *` 로 임시 변경 후 Active | 스케줄러가 실제로 워크플로우를 깨우는가 |
| 3 | 5분 뒤 Executions 탭 확인 | 자동 실행 기록이 남았는가, 타임존이 KST로 찍히는가 |
| 4 | Cron을 `30 8 * * *` 로 복원 | 최종 설정 반영 |

> 2단계에서 중복 방지(REQ-03)가 함께 검증된다. 5분 간격 실행 시 두 번째 실행부터는 신규 기사만 남아야 정상이다.

### 3.3 REQ-03 :: 중복 발송 방지

#### 고유값 설계 — 정규화된 URL의 SHA-256 해시

```
article_id = SHA256(normalize(url))
```

`normalize(url)` 처리 내용:

| 처리 | 예시 |
|---|---|
| 프로토콜·호스트 소문자화 | `HTTPS://Www.Yna.co.kr` → `https://www.yna.co.kr` |
| `www.` 접두어 제거 | `www.yna.co.kr` → `yna.co.kr` |
| **추적 파라미터만 선별 제거** (아래 목록에 해당하는 키만) | `?newsId=045296&utm_source=rss` → `?newsId=045296` |
| 남은 쿼리 파라미터를 키 기준 정렬 | `?b=2&a=1` → `?a=1&b=2` |
| 프래그먼트 제거 | `#comment` → 제거 |
| 끝 슬래시 제거 | `/article/123/` → `/article/123` |

제거 대상 파라미터 키 (블랙리스트):

```
utm_source, utm_medium, utm_campaign, utm_term, utm_content,
fbclid, gclid, igshid, ref, refer, from, cmpt_cd, sc_from
```

> **쿼리스트링을 통째로 지우면 안 되는 이유 (검증으로 확인)**
> 이데일리는 기사 URL이 `https://www.edaily.co.kr/News/Read?newsId=04529686645544368` 형태로, **기사 식별자가 경로가 아니라 쿼리에 있다.** 실제 피드 50건을 받아 확인한 결과는 다음과 같다.
>
> | 정규화 방식 | 50건 중 남는 고유 URL |
> |---|---|
> | 쿼리 전체 제거 | **1건** |
> | 추적 파라미터만 선별 제거 | **50건** |
>
> 쿼리를 전부 지우면 이데일리 기사 전체가 동일한 `article_id`를 갖게 되어, 하루 첫 기사 1건만 통과하고 나머지 49건이 "이미 발송함"으로 오판된다. 중복 방지 로직이 **정상 기사를 삭제하는 방향으로 고장 나는** 유형이라, 브리핑이 조용히 빈약해질 뿐 에러가 나지 않아 발견도 늦다. 따라서 화이트리스트(모두 제거)가 아닌 블랙리스트(알려진 추적 키만 제거) 방식을 채택한다.
>
> 참고로 검증 시점에 4개 피드 모두 `utm_` 파라미터를 붙이지 않았다. 그러나 매체가 배포 정책을 바꾸면 언제든 추가될 수 있으므로 정규화는 유지한다.

#### 고유값 선정 근거

| 후보 | 채택 여부 | 판단 근거 |
|---|---|---|
| **정규화 URL 해시** | **채택** | 기사 1건에 1:1 대응하며 매체를 가리지 않고 항상 존재한다. 기사 제목이 수정되어도 URL은 유지된다. 해시로 저장하면 시트 셀 길이가 64자로 고정되어 조회가 빠르고, 긴 URL의 셀 잘림 문제가 없다. |
| RSS `guid` | 미채택 | **실측으로 확인됨**: 연합뉴스·조선일보는 `guid`가 원문 URL, 이데일리는 내부 ID(`04529686645544368`), 매일경제와 한국경제는 **`guid` 필드 자체가 없다.** 4개 매체를 하나의 키 체계로 묶을 수 없다. |
| 기사 제목 | 미채택 | 매체별로 같은 사건에 다른 제목을 붙이고, 발행 후 제목이 수정되는 일도 잦다. 제목이 바뀌면 같은 기사가 신규로 인식된다. |
| 원본 URL(정규화 없이) | 미채택 | RSS 피드는 `utm_source` 등 추적 파라미터를 붙여 배포하는 경우가 많다. 같은 기사가 파라미터 차이만으로 다른 문자열이 되어 중복 차단에 실패한다. |

#### 한계와 보완

정규화 URL 해시는 **"같은 기사"** 는 완벽히 막지만, **"같은 사건을 다룬 다른 매체의 기사"** 는 URL이 다르므로 막지 못한다. 이를 위해 보조 키를 함께 저장한다.

```
title_key = SHA256( 제목에서 공백·특수문자·괄호 제거 후 소문자화 )
```

- 1차 차단: `article_id` 일치 → 제거 (이력 대조)
- 2차 차단: 같은 실행 내에서 `title_key` 중복 → 1건만 남김 (매체 간 중복 보도)

2차 차단을 실행 내로 한정하는 이유는, 며칠에 걸쳐 후속 보도가 이어지는 사안(예: 금리 결정 → 시장 반응)을 영구 차단해 버리면 오히려 정보 손실이 크기 때문이다.

#### LLM 호출 이전 차단 — 배치 순서

```
수집 → 정규화 → [이력 대조] → [키워드 필터] → LLM
                     ▲
             반드시 이 위치
```

이력 대조를 LLM 뒤에 두면, 어제 이미 요약한 기사를 오늘 또 요약하면서 **매일 같은 토큰을 재지불**하게 된다. 기사 하나당 요약 비용이 발생하는 구조이므로, 차단 지점이 파이프라인 앞으로 갈수록 비용이 절감된다.

#### 이력 대조 구현

1. `Load History` 노드가 시트에서 최근 N일치 행을 읽는다 (전체 조회는 시트가 커질수록 느려지므로 **최근 7일**로 제한).
2. Code 노드에서 `article_id` 컬럼만 뽑아 `Set` 자료구조로 만든다.
3. 수집된 기사 중 `Set`에 존재하는 것을 제거한다.

> 7일 윈도로 제한하는 이유: RSS 피드가 반환하는 기사는 통상 최근 1~2일치다. 7일보다 오래된 기사가 피드에 다시 나타날 가능성은 사실상 없으므로, 조회 범위를 좁혀 성능을 확보한다.

### 3.4 REQ-04 :: 금융 키워드 필터

#### 결정 — 필터를 LLM **앞**에 둔다

| 배치 | 비용 | 정확도 | 판단 |
|---|---|---|---|
| **LLM 앞 (채택)** | 낮음. 비금융 기사가 토큰을 소비하지 않음 | 키워드에 걸리지 않은 금융 기사를 놓칠 위험(재현율 손실) | **채택** |
| LLM 뒤 | 높음. 연예·스포츠 기사까지 전부 요약 비용 발생 | 높음. LLM이 문맥으로 판단 | 미채택 |

#### 근거

1. **비용**: 종합 일간지 피드에서 금융 관련 기사는 대략 20~30% 수준이다. 필터를 뒤에 두면 **토큰의 70~80%가 버려질 기사에 쓰인다.** 매일 실행되는 워크플로우이므로 이 낭비는 누적된다.
2. **처리 시간**: 8시 30분 발송이라는 시각 약속이 있다. LLM 호출 건수가 곧 소요 시간이므로, 입력 건수를 앞단에서 줄이는 것이 발송 지연 위험을 낮춘다.
3. **정확도 손실은 보완 가능**: 키워드 필터의 약점인 재현율 손실은 아래 2단 구조로 완화한다.

#### 2단 필터 구조 — "앞은 넓게, 뒤는 정밀하게"

```
[1단] 키워드 필터 (LLM 앞)  → 명백한 비금융 기사만 쳐낸다. 넓게 통과시킨다.
[2단] LLM importance 판정   → 통과한 기사 중 가치 없는 것에 importance 1~2를 부여한다.
[3단] importance >= 4 필터  → 최종 선별
```

1단을 의도적으로 **느슨하게(높은 재현율, 낮은 정밀도)** 설계한다. 애매한 기사는 통과시키고, 최종 선별은 LLM의 중요도 점수에 맡긴다. 1단에서 과하게 조이면 놓친 기사는 복구할 방법이 없지만, 느슨하게 통과시킨 기사는 3단에서 걸러지므로 실수의 비용이 비대칭이다.

#### 키워드 사전 설계

**포함 키워드 (하나라도 매칭 시 통과)**

| 분류 | 키워드 |
|---|---|
| 증시 | 코스피, 코스닥, 증시, 주가, 상장, 공모주, 배당, 시가총액, 나스닥, S&P |
| 금리·통화 | 금리, 기준금리, 한국은행, 금통위, 연준, FOMC, 통화정책, 국채, 채권, 수익률 |
| 환율 | 환율, 원달러, 달러, 엔화, 위안화, 외환 |
| 부동산 | 부동산, 아파트값, 분양, 전세, 주택담보, 청약, LTV, DSR |
| 기업 | 실적, 영업이익, 매출, 인수합병, M&A, 유상증자, 어닝, 상장폐지 |
| 정책·거시 | 물가, 소비자물가, CPI, GDP, 경기, 재정, 세제, 수출, 무역수지, 규제 |
| 금융업 | 은행, 증권, 보험, 펀드, ETF, 가상자산, 비트코인, 대출, 연체 |

**제외 키워드 (매칭 시 즉시 탈락, 포함 키워드보다 우선)**

```
연예, 아이돌, 드라마, 영화 흥행, 스포츠, 야구, 축구, 골프, 날씨, 미세먼지,
운세, 부고, 인사이동, 신간, 레시피, 여행 후기
```

**매칭 규칙**

- 대상: `제목 + snippet`
- 방식: 대소문자 무시, 공백 제거 후 부분 문자열 매칭
- 판정: `제외 키워드 매칭 → 탈락` → `포함 키워드 1개 이상 매칭 → 통과` → `그 외 → 탈락`
- 매칭된 키워드 수를 `keyword_score`로 기록해 두고, 기사 수가 LLM 호출 상한(1회 실행당 30건)을 넘으면 점수 순으로 상위 30건만 처리한다. 절단이 발생하면 브리핑 푸터에 표시한다.

> **제외 키워드를 우선 적용하는 이유**: "○○ 배우, 강남 아파트 100억 매입" 같은 기사는 `아파트`·`부동산`이 걸려 통과하지만 시장 정보로서 가치가 없다. 제외 규칙을 먼저 두어 이런 유형을 차단한다.

### 3.5 본문 추출 (REQ-05 보조 단계)

REQ에 명시된 항목은 아니지만, 3.1에서 확인했듯 RSS 본문이 100자 안팎이라 요약 품질을 확보하려면 원문 본문이 필요하다.

#### 배치 위치 — 키워드 필터 **뒤**, LLM **앞**

```
… → 이력 대조 → 키워드 필터 → [본문 추출] → LLM → …
```

| 배치 후보 | 하루 HTTP 요청 수 | 판단 |
|---|---|---|
| 수집 직후 | 약 270건 (3개 피드 전량) | 미채택. 버려질 연예·스포츠 기사까지 원문을 받는다 |
| **키워드 필터 뒤 (채택)** | **약 10~30건** | **채택.** 중복·비금융 기사를 모두 걸러낸 뒤라 요청이 최소가 된다 |

키워드 필터를 본문이 아닌 `title + description`으로 돌리므로 필터 정확도가 다소 낮아지지만, 3.4에서 정한 대로 1단 필터는 느슨하게 통과시키는 것이 설계 의도이므로 문제되지 않는다. 요청 수를 10배 가까이 줄이는 이득이 훨씬 크다.

#### 매체별 추출 규칙 (2026-08-05 실측 검증)

| 매체 | 추출 방식 | 검증 결과 |
|---|---|---|
| 연합뉴스 | `div.story-news.article` 내부 `<p>` 텍스트 결합 | 554자 ✅ |
| 매일경제 | `div.news_cnt_detail_wrap` 내부 `<p>` 텍스트 결합 | 2,246자 ✅ |
| 이데일리 | `div.news_body[itemprop="articleBody"]` 내부 텍스트 | 676자 ✅ |
| 조선일보 | 페이지 스크립트의 `Fusion.globalContent` JSON을 파싱해 `content_elements[type=="text"].content` 결합 | 945자 ✅ |

> **조선일보만 방식이 다른 이유**: 조선일보는 Arc(Fusion) CMS 기반이라 본문이 서버 HTML의 `<p>` 태그로 렌더링되지 않는다. `.article-body` 컨테이너는 존재하지만 그 안의 `<p>` 태그가 **0개**다. 대신 페이지에 포함된 `Fusion.globalContent` JSON에 본문이 들어 있어, 이를 파싱하면 945자를 얻는다.
>
> **이데일리 주의**: `news_body`는 페이지에 4번 등장하는데 첫 매칭이 사이드바 스크립트인 경우가 있다. 클래스명이 아니라 **`itemprop="articleBody"` 속성**으로 지정해야 본문을 정확히 잡는다.

#### 폴백 체인

추출은 언제든 실패할 수 있으므로(사이트 개편, 접속 차단, 타임아웃) 단계적으로 물러선다. 어느 단계에서 확보했는지를 `body_source`에 기록한다.

| 순위 | 소스 | `body_source` | 비고 |
|---|---|---|---|
| 1 | 원문 페이지 추출 (200자 이상) | `fulltext` | 정상 경로 |
| 2 | RSS `content:encoded` | `rss_content` | 조선일보만 해당 |
| 3 | RSS `description` | `rss_desc` | |
| 4 | 기사 제목 | `title_only` | LLM 응답의 `needs_review`를 **강제로 `true`** 로 덮어씀 |

`robots.txt` 차단 경로에 해당하면 1순위를 시도하지 않고 2순위부터 시작하며, `body_source`를 `robots_skip`으로 기록한다(아래 참조).

- 추출 결과가 **200자 미만**이면 성공으로 보지 않고 다음 단계로 내린다. 선택자가 깨지면 광고 문구나 빈 문자열이 잡히는데, 이를 본문으로 넘기면 LLM이 엉뚱한 요약을 만들어낸다.
- 본문은 **3,000자에서 절단**한다. 매일경제처럼 2,000자를 넘는 기사가 있고, 기사 핵심은 앞부분에 있으므로 뒷부분까지 토큰을 쓸 이유가 없다.

#### n8n 노드 구성

| 노드 | 타입 | 설정 |
|---|---|---|
| Fetch Article | HTTP Request | `User-Agent: Mozilla/5.0 …`, Timeout 15초, Retry 2회, **On Error: Continue** |
| Extract Body | Code | `source` 값으로 매체별 추출기 분기, 폴백 체인 적용, `body_source`·`body_len` 기록 |

- **Batch 설정**: 5건씩, 배치 간 1초 대기. 하루 10~30건이므로 매체당 요청은 10건 미만이다.
- **On Error: Continue** 가 핵심이다. 한 기사의 원문 페이지가 죽어도 폴백으로 내려가 요약은 계속되어야 하며, 브리핑 전체가 멈춰서는 안 된다.

#### 선택자 파손 감지

매체가 사이트를 개편하면 선택자는 조용히 깨진다. 에러가 나지 않고 폴백으로 내려갈 뿐이라 알아채기 어렵다. 따라서 `body_source` 분포를 감시한다.

```
당일 처리 기사 중 body_source = 'fulltext' 비율 < 50%
  → 브리핑 푸터에 "⚠️ 본문 추출률 저하 (32%) — 선택자 점검 필요" 표시
```

받는 사람에게는 브리핑이 평소보다 부실한 이유를 알리고, 운영자에게는 점검 신호가 된다.

#### robots.txt 준수 — 차단 경로 사전 필터

4개 매체의 `robots.txt`를 확인한 결과(부록 C), **조선일보의 `/economy/realty/` 경로가 차단**되어 있고 조선일보 경제 피드 100건 중 4건이 이 경로에 해당한다. 부동산은 브리핑 카테고리 중 하나이므로 실제로 매일 걸린다.

따라서 본문 추출 **앞에** 차단 경로 필터를 둔다.

```
if (URL이 아래 차단 규칙에 해당) → 원문 요청을 건너뛰고 폴백 체인 2순위부터 시작
```

| 매체 | 차단 규칙 | 처리 |
|---|---|---|
| 조선일보 | `/economy/realty/` | 원문 요청 생략 → RSS `content:encoded`/`description` 사용 |
| 연합뉴스 | `/view/AEN*`, `/view/AJP*`, `/view/ACK*` 등 외국어판, `/*?*cp=` | 동일 (경제 피드 120건 전량이 한국어판 `AKR`이라 현재는 해당 없음. 방어적으로 유지) |
| 매일경제 | `Allow: /` (제한 없음) | 해당 없음 |
| 이데일리 | 팝업 경로 1건만 차단 | 해당 없음 |

**기사를 버리지는 않는다.** RSS는 매체가 배포 목적으로 직접 제공한 것이므로, 원문 페이지를 긁지 않고 RSS 본문으로 요약해 브리핑에는 정상 포함시킨다. 차단 경로 때문에 폴백된 기사는 `body_source`를 `robots_skip`으로 기록해, 선택자 파손으로 인한 폴백과 구분한다. (3.5의 추출률 경고 계산에서도 `robots_skip`은 정상으로 간주해 제외한다)

#### 그 밖의 운영상 주의

- 4개 매체 모두 `robots.txt`에 `Crawl-delay`를 명시하지 않았다. 본 설계의 요청량(5건씩 1초 간격, 하루 10~30건)은 충분히 보수적이다.
- 브리핑에는 **요약문과 원문 링크만** 싣고 본문 전문을 재배포하지 않는다. 추출한 본문은 요약 생성에만 쓰고 시트에도 저장하지 않는다(`body_len`·`body_source`만 기록).
- `robots.txt`는 매체가 언제든 바꿀 수 있으므로 **분기 1회 재확인**을 운영 항목으로 둔다.

### 3.6 REQ-05 :: LLM 요약과 중요도 분류

#### 출력 스키마

```json
{
  "summary": "금통위가 기준금리를 만장일치로 동결했다. 물가 안정세를 확인했으나 가계부채 부담을 고려한 결정으로 해석된다.",
  "importance": 5,
  "category": "금리",
  "needs_review": false
}
```

| 필드 | 타입 | 허용값 | 검증 규칙 |
|---|---|---|---|
| `summary` | string | 3문장 이하 | 문장 종결부호 개수 ≤ 3, 공백 제외 1자 이상 |
| `importance` | number | 1~5 정수 | 정수이며 1 ≤ n ≤ 5 |
| `category` | string | 증시 / 금리 / 환율 / 부동산 / 기업 / 정책 / 기타 | 7개 값 중 하나와 정확히 일치 |
| `needs_review` | boolean | true / false | 위 3개 중 하나라도 위반 시 강제 `true` |

#### 구조화 출력 구현

n8n **Basic LLM Chain** 노드에 **Structured Output Parser**를 연결하고 위 JSON Schema를 지정한다. 파서가 형식을 강제하므로 자연어 응답에서 JSON을 추출하는 파싱 코드가 불필요하다.

#### 프롬프트 (System)

```
당신은 자산운용사 리서치팀의 뉴스 분석 담당자입니다.
입력된 기사 하나를 읽고 JSON으로만 응답하세요.

[summary]
- 3문장 이하의 한국어 평서문으로 작성합니다.
- 기사에 실제로 적힌 사실만 씁니다. 추정, 전망, 투자 의견을 덧붙이지 마세요.
- 수치(금액, 비율, 지수)가 있으면 반드시 포함합니다.
- "~에 따르면", "기사에 의하면" 같은 군더더기를 쓰지 마세요.

[importance] 아래 기준으로 1~5의 정수를 부여합니다.
5 : 시장 전체를 흔드는 사건. 기준금리 결정, 대형 정책 발표, 지수 급락·급등
4 : 특정 업종이나 대형 기업에 직접 영향. 실적 발표, 대형 인수합병
3 : 참고할 만한 동향. 경제지표 발표, 업계 전망
2 : 일반적인 소식
1 : 브리핑에 넣을 필요 없는 기사 (금융과 무관하거나 정보 가치가 없음)

판단이 애매하면 낮은 쪽을 선택합니다. 브리핑은 4점 이상만 발송되므로,
확신이 없는 기사를 4점으로 올리는 것보다 3점으로 두는 편이 낫습니다.

[category] 다음 7개 중 정확히 하나를 고릅니다.
증시 / 금리 / 환율 / 부동산 / 기업 / 정책 / 기타
어디에도 명확히 속하지 않으면 "기타"를 씁니다.

[needs_review]
기사 내용이 불충분해 요약을 신뢰하기 어렵거나(본문이 제목뿐인 경우 등),
위 지시를 지킬 수 없었다면 true, 정상 처리했다면 false를 반환합니다.
```

#### 프롬프트 (User)

```
제목: {{ $json.title }}
매체: {{ $json.source }}
발행: {{ $json.published_at }}
본문: {{ $json.body }}
```

> `body`는 3.5의 폴백 체인을 거쳐 확보한 값이다. `body_source`가 `title_only`인 경우 요약 근거가 제목뿐이므로, LLM 응답과 무관하게 `needs_review`를 `true`로 덮어쓴다.

#### 검증과 `needs_review`

`Validate` Code 노드에서 스키마를 재검증한다. LLM 응답을 그대로 신뢰하지 않는 이유는, 파서가 형식은 보장해도 **값의 유효성**(예: `category`가 목록 밖의 "산업")까지 보장하지는 않기 때문이다.

| 검증 실패 유형 | 처리 |
|---|---|
| `importance`가 1~5 밖 | 3으로 보정, `needs_review = true` |
| `category`가 허용값 밖 | `"기타"` 로 보정, `needs_review = true` |
| `summary`가 4문장 이상 | 앞 3문장만 사용, `needs_review = true` |
| `summary`가 빈 문자열 | 기사 제목으로 대체, `needs_review = true` |
| LLM 호출 자체 실패 | 해당 기사를 건너뛰고 시트에 `status = llm_error` 기록. 다른 기사 처리는 계속 |

`needs_review = true`인 기사가 브리핑에 포함되면 제목 옆에 `⚠️` 를 표시해 사람이 원문을 확인하도록 유도한다. 자동 요약을 무조건 신뢰하게 만들지 않는 것이 목적이다.

### 3.7 REQ-06 :: 디스코드 브리핑 발송

#### 메시지 1건으로 묶기

기사가 5건이어도 메시지는 1개여야 한다. n8n에서 아이템은 기본적으로 개별 처리되므로, Discord 노드 앞에 **`Build Message` Code 노드**를 두어 모든 아이템을 순회하며 단일 문자열로 조립한 뒤 아이템 1개를 반환한다.

```
importance 내림차순 → 같은 점수면 published_at 내림차순으로 정렬 후 조립
```

#### 정상 브리핑 포맷

```
📈 오늘의 금융 브리핑 (2026-08-10)
읽을 기사 3건

[1] 증시 | 한국은행 기준금리 3.0% 동결
    금통위가 기준금리를 만장일치로 동결했다. 물가 안정세를
    확인했으나 가계부채 부담을 고려한 결정으로 해석된다.
    🔗 https://...

[2] 기업 | 삼성전자 2분기 영업이익 12조 원
    ...
    🔗 https://...

[3] 환율 | 원달러 환율 1,340원대 마감
    ...
    🔗 https://...

──────────────
수집 84건 → 신규 31건 → 금융 12건 → 중요 3건
매체: 연합 42 / 한경 0(실패) / 매경 42
```

- 기사마다 **카테고리 · 제목 · 요약 · 원문 링크**가 모두 들어간다.
- 푸터의 처리 통계는 받는 사람이 브리핑의 신뢰도를 스스로 판단할 근거가 된다.

#### 중요 기사가 없는 날 — 정상 무소식 경로

**시스템이 고장 난 것과 오늘 별일이 없는 것을 받는 사람이 구분할 수 있어야 한다.** 침묵은 두 상태를 구분할 수 없게 만들므로, 아무 기사가 없어도 메시지를 보낸다.

```
📭 오늘의 금융 브리핑 (2026-08-10)
중요 기사 없음

오늘 수집된 기사 중 브리핑 기준(중요도 4 이상)을 넘는 기사가 없었습니다.
시스템은 정상 동작했습니다.

──────────────
수집 71건 → 신규 24건 → 금융 9건 → 중요 0건
매체: 연합 38 / 한경 20 / 매경 13
```

#### 세 가지 경로 정리

| 상황 | 아이콘 | 제목 | 판단 기준 |
|---|---|---|---|
| 중요 기사 있음 | 📈 | 오늘의 금융 브리핑 | `importance >= 4` 가 1건 이상 |
| 중요 기사 없음 (정상) | 📭 | 중요 기사 없음 | 파이프라인은 완주했으나 4점 이상이 0건 |
| 수집 실패 (장애) | ⚠️ | 브리핑 생성 실패 | RSS 전부 실패, 시트 접근 불가, 워크플로우 예외 |

장애 메시지 예시:

```
⚠️ 브리핑 생성 실패 (2026-08-10 08:31)

RSS 피드 3개가 모두 응답하지 않아 브리핑을 만들지 못했습니다.
오늘은 수동으로 뉴스를 확인해 주세요.

실패 지점: RSS Feed A/B/C — 연결 시간 초과
실행 기록: <n8n Execution URL>
```

- 정상 브리핑(📈/📭)과 장애 알림(⚠️)은 **아이콘과 제목 문구를 명확히 다르게** 해서 한눈에 구분되게 한다.
- 장애 알림은 별도 **Error Trigger 워크플로우**로 발송한다. 메인 워크플로우가 예외로 중단되어도 알림은 나가야 하기 때문이다.

#### 디스코드 제약 대응

- 메시지 1건은 **2,000자** 제한이 있다. 기사 수가 많아 초과가 예상되면 **상위 10건까지만** 포함하고, 푸터에 `외 N건은 중요도 순으로 생략됨`을 명시한다.
- 조용한 절단(silent truncation)은 만들지 않는다. 생략이 발생하면 반드시 표시한다.

### 3.8 REQ-07 :: 발송 이력 기록

#### 시트 스키마

시트명: `sent_history`

| 컬럼 | 타입 | 예시 | 용도 |
|---|---|---|---|
| `article_id` | string(64) | `a3f1...` | **중복 방지 조회 키** |
| `title_key` | string(64) | `9c02...` | 매체 간 중복 보도 판별 보조 키 |
| `run_date` | date | `2026-08-10` | 처리 일자 (조회 범위 제한용) |
| `run_at` | datetime | `2026-08-10 08:30:14` | 실행 시각 |
| `source` | string | `연합뉴스` | 매체명 |
| `title` | string | `한국은행 기준금리 3.0% 동결` | 사람이 시트를 볼 때 식별용 |
| `url` | string | `https://...` | 원문 링크 |
| `published_at` | datetime | `2026-08-10 07:12` | 기사 발행 시각 |
| `category` | string | `금리` | LLM 분류 결과 |
| `importance` | number | `5` | LLM 중요도 |
| `summary` | string | `금통위가 기준금리를...` | LLM 요약 |
| `needs_review` | boolean | `false` | 검증 실패 여부 |
| `body_source` | enum | `fulltext` | 본문 확보 경로 (`fulltext`/`rss_content`/`rss_desc`/`title_only`/`robots_skip`) |
| `body_len` | number | `945` | 요약에 투입한 본문 길이. 선택자 파손 추적용 |
| `status` | enum | `sent` | 처리 결과 (아래) |
| `execution_id` | string | `12345` | n8n 실행 ID (장애 추적용) |

`status` 허용값:

| 값 | 의미 |
|---|---|
| `sent` | 디스코드로 발송됨 (importance ≥ 4) |
| `not_sent` | LLM까지 처리했으나 중요도 미달 (importance ≤ 3) |
| `llm_error` | LLM 호출 실패로 요약하지 못함 |

#### 기록 대상 설계 — "발송한 것"이 아니라 "LLM을 태운 것" 전부

| 대안 | 판단 |
|---|---|
| 발송한 기사만 기록 | **미채택.** 중요도 3으로 탈락한 기사가 이력에 없으므로, 내일 같은 기사가 다시 수집되어 **LLM 비용을 또 지불**한다. 매일 반복되면 낭비가 누적된다. |
| **LLM을 호출한 기사 전부 기록** | **채택.** 한 번 요약한 기사는 결과와 무관하게 두 번 요약하지 않는다. `status` 컬럼으로 발송 여부를 구분한다. |
| 수집한 기사 전부 기록 | 미채택. 키워드 필터에서 탈락한 연예·스포츠 기사까지 쌓이면 시트가 급격히 비대해지고 이력 조회가 느려진다. 이들은 다시 수집돼도 키워드 필터에서 무료로 걸러지므로 기록할 이유가 없다. |

#### 쓰기 방식

- Google Sheets **`Append Row`** 를 사용해 누적한다. (`Update`는 기존 행을 덮어쓰므로 이력 용도에 부적합)
- 발송 성공 여부와 무관하게 기록한다. 디스코드 발송이 실패해도 요약 비용은 이미 지불했으므로 이력에는 남겨야 재처리를 막을 수 있다.
- 시트 행이 수만 건으로 늘어나면 조회가 느려지므로, **월 단위 시트 분리** 또는 90일 초과 행의 별도 아카이브 시트 이관을 운영 규칙으로 둔다.

## 4. 예외 처리 정리

| 상황 | 처리 | 브리핑 영향 |
|---|---|---|
| RSS 피드 1개 실패 | 나머지 피드로 계속 진행 | 정상 발송, 푸터에 `실패` 표시 |
| RSS 피드 전부 실패 | 장애 알림(⚠️) 발송 후 종료 | 브리핑 없음, 장애 알림 있음 |
| 신규 기사 0건 | 📭 경로로 발송 | "중요 기사 없음" 메시지 |
| 키워드 필터 통과 0건 | 📭 경로로 발송 | 동일 |
| 원문 페이지 접속 실패·타임아웃 | 폴백 체인으로 RSS 본문 사용 | 정상 발송, 요약 근거만 짧아짐 |
| robots.txt 차단 경로 기사 | 원문 요청 생략, RSS 본문으로 요약 (`body_source = robots_skip`) | 정상 발송 |
| 본문 추출 결과 200자 미만 | 선택자 파손으로 간주하고 폴백 | 정상 발송 |
| `fulltext` 비율 50% 미만 | 브리핑 푸터에 추출률 저하 경고 표시 | 정상 발송 + 경고 |
| LLM 개별 호출 실패 | 해당 기사만 건너뜀, `status = llm_error` | 나머지 기사로 정상 발송 |
| LLM 응답 스키마 위반 | 기본값 보정 + `needs_review = true` | 제목에 `⚠️` 표시하여 발송 |
| 중요도 4 이상 0건 | 📭 경로로 발송 | "중요 기사 없음" 메시지 |
| Google Sheets 조회 실패 | 중복 방지 없이 진행하면 중복 발송 위험 → **중단하고 장애 알림** | 브리핑 없음, 장애 알림 있음 |
| Google Sheets 기록 실패 | 브리핑은 이미 발송됨 → 장애 알림만 추가 발송 | 정상 발송 + 경고 |
| 디스코드 발송 실패 | n8n 노드 재시도 3회 → 실패 시 장애 알림 | 재시도 후 판단 |
| 메시지 2,000자 초과 | 상위 10건만 포함, 생략 건수 명시 | 축약 발송 |

## 5. 테스트 계획

| # | 항목 | 방법 | 기대 결과 |
|---|---|---|---|
| T1 | 전체 경로 | 수동 실행 | 디스코드에 브리핑 1건 도착 |
| T2 | 스케줄 동작 | Cron `*/5 * * * *` 로 임시 변경 | 자동 실행 기록 생성, 시각이 KST |
| T3 | **중복 차단** | 수동 실행 직후 재실행 | 2회차에는 신규 기사만 남고, 없으면 📭 발송 |
| T4 | 피드 장애 | 피드 URL 하나를 잘못된 주소로 변경 | 나머지로 정상 발송, 푸터에 실패 표시 |
| T5 | 전체 장애 | 피드 3개 모두 잘못된 주소로 변경 | ⚠️ 장애 알림 발송 |
| T6 | 키워드 필터 | 종합 피드로 실행 후 통과 목록 육안 검사 | 연예·스포츠·날씨 기사 0건 |
| T7 | 메시지 묶음 | 기사 5건 이상인 날 실행 | 디스코드 메시지 **1개** |
| T8 | 빈 브리핑 | 중요도 임계값을 임시로 6으로 변경 | 📭 "중요 기사 없음" 발송 |
| T9 | 스키마 검증 | 프롬프트를 임시 훼손해 잘못된 category 유도 | `기타`로 보정, `needs_review = true`, `⚠️` 표시 |
| T10 | 시트 기록 | 실행 후 시트 확인 | `sent`/`not_sent` 행이 모두 누적됨 |
| T11 | 본문 추출 | 실행 후 시트의 `body_source` 분포 확인 | `fulltext` 비율 80% 이상, `body_len` 200자 이상 |
| T12 | 추출 폴백 | 매체별 선택자를 임시로 잘못된 값으로 변경 | 에러 없이 `rss_desc`로 폴백, 브리핑은 정상 발송, 푸터에 추출률 경고 |
| T13 | robots 차단 필터 | 조선일보 `/economy/realty/` 기사를 포함해 실행 | 해당 기사에 원문 요청이 나가지 않고 `body_source = robots_skip`, 브리핑에는 정상 포함 |

T3, T8은 요구사항의 핵심 판정 항목이므로 스크린샷을 남겨 제출 자료에 포함한다.

## 6. 설계 결정 요약

제출 문서에 명시가 요구된 두 가지 판단은 다음과 같다.

| 판단 항목 | 결정 | 한 줄 근거 |
|---|---|---|
| **기사 고유값** (REQ-03) | 정규화된 URL의 SHA-256 해시 | 매체와 무관하게 항상 존재하고 기사와 1:1 대응하며, 제목 수정·추적 파라미터에 흔들리지 않는다 |
| **필터 위치** (REQ-04) | LLM 호출 **앞** | 버려질 기사에 토큰을 쓰지 않기 위해서다. 앞단은 느슨하게 통과시키고 최종 선별은 LLM 중요도 점수에 맡겨 재현율 손실을 보완한다 |

추가 설계 결정:

| 항목 | 결정 | 근거 |
|---|---|---|
| 이력 기록 대상 | LLM을 호출한 기사 전부 (`sent` + `not_sent`) | 중요도 미달 기사도 재요약 비용이 발생하므로 |

| 본문 추출 위치 | 키워드 필터 뒤 | HTTP 요청이 하루 270건에서 10~30건으로 줄어듦 |
| robots 차단 경로 | 기사를 버리지 않고 RSS 본문으로 요약 | 조선일보 부동산 기사가 매일 4건가량 해당. 카테고리에 부동산이 있으므로 누락시키면 브리핑에 구멍이 생김 (부록 C) |

## 부록 B. 본문 추출 검증 기록

### B.1 검증 방법

2026-08-05, 각 매체의 실제 기사 1건을 받아 본문 확보 경로를 세 가지 방식으로 순차 확인했다.

1. **JSON-LD `articleBody`** — schema.org 표준 필드. 있으면 선택자 없이 가장 안정적으로 본문을 얻을 수 있다
2. **`og:description`** 메타 태그
3. **매체별 본문 컨테이너** 선택자

### B.2 결과

| 매체 | JSON-LD `articleBody` | `og:description` | 최종 채택 방식 | 확보 본문 |
|---|---|---|---|---|
| 연합뉴스 | 없음 | 83자 | `div.story-news.article` 내 `<p>` | **554자** |

## 7. 구현 노트 (2026-08-06)

기획 단계에서는 예상하지 못했던 문제가 실제 n8n 구현 중 다수 발견됐다. 설계 자체를 바꾼 것은 아니지만, **구현 방식과 검증 방법을 결정한 실제 근거**라 기록해 둔다.

### 7.1 최종 노드 구성

| 구간 | 노드 |
|---|---|
| 트리거 | `Schedule Trigger` (Days, 08:30 KST) |
| 수집 | `연합뉴스 RSS`(RSS Read) · `조선일보 RSS`(RSS Read1) · `매일경제 HTTP → XML → Split` · `Merge Feeds`(append) |
| 정규화 | `Normalize`(Code) |
| 중복 차단 | `Load History`(Sheets 읽기, 별도 갈래) → `Merge History`(append) → `Filter Seen`(Code) |
| 키워드 필터 | `Keyword Filter`(Code) → `Aggregate`(native) → `Has Articles?`(IF) → `Split Articles` |
| robots 필터 | `Check Robots`(Code, `robots_blocked` 판정) → `Robots OK?`(IF) |
| 본문 수집 | `Fetch Article`(HTTP Request) → `Merge Fetch Data`(native Merge・Combine/Position) → `Merge`(append, 스킵분 합류) → `Extract Body`(Code) |
| LLM | `Summarize`(Basic LLM Chain + Gemini, Structured Output Parser 미사용) → `Merge LLM Output`(native Merge・Combine/Position) → `Validate LLM Output`(Code) |
| 발송 | `Build Message` / `Build Empty Message`(Code) → `Send Briefing`(Discord, 2갈래 입력) |
| 기록 | `Prepare History Rows`(Code) → `Log History Write`(Sheets Append) |
| 장애 알림 | 별도 워크플로우: `Error Trigger` → `Build Error Message`(Code) → `Discord` |

**Code 노드 배분**: `Normalize`/`Keyword Filter`/`Extract Body`/`Validate LLM Output`/`Build Message`/`Build Empty Message`/`Prepare History Rows` 7개는 그대로 두고, `Count Articles`·`Reattach Metadata`·LLM 결과 병합 3곳은 각각 **Aggregate**와 **Merge(Combine by Position)** native 노드로 교체했다. 전자는 배열 순회·정규식·문자열 파싱처럼 native 노드로 표현하기 어려운 로직이라 Code가 맞고, 후자는 단순히 "이전 필드를 잃지 않고 다시 합치는" 일이라 native로 충분했다.

### 7.2 실제 발생한 문제와 해결

| # | 문제 | 원인 | 해결 |
|---|---|---|---|
| 1 | RSS 두 번째 피드가 120배(12000건) 호출됨 | 두 RSS 노드를 직렬로 연결 → n8n은 노드를 **입력 아이템 개수만큼 반복 실행**함 | 3개 피드 모두 Schedule Trigger에서 **병렬**로 직접 분기 |
| 2 | URL 정규화 코드에서 `new URL()`이 매번 실패 | n8n Cloud Code 노드 샌드박스가 전역 `URL`/`URLSearchParams`와 `require('url')`을 둘 다 차단 | 정규식·문자열 함수로 URL 파싱을 직접 구현 (3.3에도 반영된 블랙리스트 방식과 별개로, 파싱 자체를 순수 JS로 재작성) |
| 3 | 이력 대조 Code 노드가 `Node 'Load History' hasn't been executed` 에러 | `$('NodeName')`으로 **연결되지 않은 별도 갈래**를 참조하는 방식은 n8n에서 불안정함 (직접 연결된 조상 노드 참조는 문제없음) | `Load History`와 기사 목록을 **Merge(append)로 물리적으로 합친 뒤**, `run_date` 필드 유무로 이력/기사를 구분하는 방식으로 변경 |
| 4 | 키워드 필터 통과 0건일 때 "기사 없음" 분기가 아예 실행 안 됨 | IF 노드는 입력 아이템이 있어야 평가되는데, 0건이면 True/False 양쪽 다 실행되지 않음 | 기사 배열을 `{count, items}` 아이템 **1개로 래핑**(Aggregate)한 뒤 IF로 분기, True 쪽에서 Split Out으로 다시 펼침 |
| 5 | `Fetch Article`(HTTP Request) 이후 `article_id`/`title` 등 기존 필드가 전부 사라짐 | HTTP Request 노드는 응답 필드로 `item.json`을 **통째로 교체**함 (입력 필드를 보존하지 않음) | `Merge`(Combine by Position)로 요청 전 원본 데이터와 응답을 인덱스 기준으로 재결합 |
| 6 | 조선일보만 본문 추출 실패 (`<p>` 태그 0개) | 조선일보는 Arc(Fusion) CMS라 본문이 서버 HTML에 렌더링되지 않고 `<script>` 안 `Fusion.globalContent` JSON에 있음 | 해당 JSON을 중괄호 매칭으로 직접 파싱해 `content_elements[type=text]`를 추출 |
| 7 | `Summarize`(LLM Chain) 이후에도 5번과 동일하게 필드 소실 | LLM Chain 노드도 자기 결과로 `item.json`을 교체 | 5번과 동일하게 `Merge(Combine by Position)`로 재결합 |
| 8 | Gemini가 JSON 스키마 자체를 흉내 내서 응답 (`description`/`enum`/`minimum` 안에 실제 값이 들어감) | n8n Structured Output Parser는 스키마를 프롬프트로 설명해 채우게 하는 방식인데, Gemini가 "스키마 설명"과 "채울 값"을 구분 못 함 | Structured Output Parser를 **떼어내고**, 시스템 프롬프트에 실제 예시 + `type`/`properties`/`enum` 등 금지어를 명시, 응답을 Code에서 직접 `JSON.parse` |
| 9 | 스키마 단순화 후 "모델이 빈 응답을 반환함" 에러 | Gemini의 내부 "생각(thinking)" 토큰이 출력 토큰 한도를 다 써버림 | Maximum Output Tokens를 2048 이상으로 확보 (8번 조치와 함께 근본 해결) |
| 10 | 디스코드 발송이 매번 원인 불명으로 실패 (`sendLegacy: undefined`) | 상위 10건 캡이 **글자수**를 보장하지 못해 2,000자 제한 초과 | 건수가 아니라 **누적 글자수(1,900자)** 기준으로 기사를 하나씩 추가하며 자르는 방식으로 변경 |
| 11 | Table/Schema 뷰에서 서로 다른 기사의 필드가 뒤섞여 보임 | n8n의 **Schema 탭은 여러 아이템의 필드를 하나로 합쳐서** 보여줌 (필드 이름은 합치되 값은 어느 아이템 것인지 보장 안 함) | 실제 아이템 단위 확인은 반드시 **Table/JSON 탭**으로 함 (두 차례 오탐의 원인이었음) |
| 12 | Error Trigger 워크플로우가 계속 무반응 | n8n은 **수동 실행("Execute workflow")에서 난 에러는 Error Trigger로 넘기지 않음** (공식 사양). `Active`/`Error Workflow` 설정은 전부 정상이었음 | 검증 시에는 스케줄을 임시로 짧게 바꿔 **자동 실행이 실제로 에러 나는 상황**을 만들어야 함 |

### 7.4 운영 시 참고

- LLM은 최종적으로 **Google Gemini**를 사용한다. Claude 대비 구조화 출력 안정성이 낮아 프롬프트에 예시·금지어를 명시하고 Code에서 직접 파싱하는 방식으로 우회했다. 이 방식은 모델을 교체해도 그대로 유지 가능하다.
- Gemini의 "생각" 토큰 소비 특성상 Maximum Output Tokens는 여유 있게(2048 이상) 유지해야 한다.
- `Filter Seen`(+`Merge History`)과 `Check Robots`(+`Robots OK?`)는 각각 **Compare Datasets 노드**, **IF 노드의 Expression 조건**으로 대체해 Code 노드를 더 줄일 수 있는 여지가 남아 있다. 검증을 우선하기 위해 이번엔 적용하지 않았고, 현재 구조(Code + Merge/IF)로도 정상 동작을 확인했다.
