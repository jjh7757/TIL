# 새 앱을 올릴 때 해야 할 일

[배포 환경](README.md)이 갖춰진 뒤, **새 프로젝트 하나를 서버에 올릴 때마다** 밟는 절차.
처음 한 번만 15~20분이고, 그 뒤로는 `git push`만 하면 된다.

아래 예시는 `rag`라는 앱을 `rag.ai-agent-develop.cloud`에 올리고,
앱이 컨테이너 안에서 **8000번 포트**를 리슨한다고 가정한다.
실제 앱에 맞춰 **이름·포트 두 가지만** 바꾸면 된다.

## 다시 안 해도 되는 것

한 번 만들어두면 앞으로 건드리지 않는다.

계정·MFA·Budgets / VPC·보안 그룹 / EC2·Elastic IP / Docker·스왑·Caddy /
OIDC 자격 증명 공급자 / `deploy-app` 스크립트 / 도메인 구매

IAM 권한 정책(`deploy`)도 ECR을 `repository/*`로 열어놨으므로 **앱이 늘어도 수정 불필요**하다.

---

## 1. ECR 리포지토리 생성 — AWS 콘솔

ECR → 리포지토리 생성

| 항목 | 값 |
|---|---|
| 표시 여부 | 프라이빗 |
| 이름 | **`rag`** (= `APP_NAME`) |
| 이미지 태그 변경 가능성 | **Mutable** |

> **Immutable로 만들면 안 된다.** 워크플로가 매번 `latest`를 같이 밀어 넣으므로
> 두 번째 푸시부터 "이미 있는 태그"로 실패한다.

생성 후 **수명 주기 정책** → 규칙 추가: 우선순위 `1` / 이미지 상태 **아무거나** /
**이미지 개수가 `10`보다 많음** → 만료. 안 걸면 커밋마다 이미지가 계속 쌓인다.

## 2. IAM 신뢰 정책에 저장소 추가 — AWS 콘솔

**새 GitHub 저장소일 때만.** 기존 저장소에 앱을 추가하는 거라면 건너뛴다.

먼저 저장소 ID를 확인한다. GitHub이 보내는 `sub` 클레임에 숫자 ID가 들어가기 때문이다
(자세한 배경은 [구축기록 ①](구축기록.md) 참고).

```bash
gh api repos/jjh7757/rag --jq '{owner_id:.owner.id, repo_id:.id}'
```

IAM → 역할 → `github-actions-deploy` → 신뢰 관계 → 신뢰 정책 편집 →
`sub` 목록에 한 줄 추가한다.

```json
"token.actions.githubusercontent.com:sub": [
    "repo:jjh7757@307797437/deploy-test@1365988315:*",
    "repo:jjh7757@307797437/rag@<repo_id>:*"
]
```

소유자 ID(`307797437`)는 고정이고 저장소 ID만 바뀐다.

## 3. 앱 저장소 준비 — 로컬

```
Dockerfile
.github/workflows/deploy.yml     ← templates/deploy.yml 복사
```

`deploy.yml`에서 **`APP_NAME`만** 바꾼다. 계정 ID·인스턴스 ID·역할 ARN은 이미 채워져 있다.

```yaml
env:
  AWS_REGION: ap-northeast-2
  APP_NAME: rag
  INSTANCE_ID: i-05ee0665bbba15a52
```

**저장소는 퍼블릭으로 둔다.** 워크플로가 `ubuntu-24.04-arm` 러너를 쓰는데,
ARM 러너는 퍼블릭 저장소에서만 무료다. 프라이빗이면 과금되거나 QEMU 에뮬레이션(느림)을 써야 한다.

## 4. 서버에 디렉토리와 compose — Session Manager

```bash
sudo mkdir -p /srv/rag && sudo chown ubuntu:ubuntu /srv/rag
```

```bash
sudo tee /srv/rag/docker-compose.yml >/dev/null <<'EOF'
services:
  app:
    image: ${ECR_REGISTRY}/${APP_NAME}:${IMAGE_TAG:-latest}
    container_name: ${APP_NAME}
    restart: unless-stopped
    env_file:
      - .env
    networks:
      - web
    expose:
      - "8000"          # ← 앱이 실제로 리슨하는 포트
    deploy:
      resources:
        limits:
          memory: 768M
    healthcheck:
      test: ["CMD", "wget", "-qO-", "http://localhost:8000/"]
      interval: 30s
      timeout: 5s
      retries: 3
      start_period: 30s

networks:
  web:
    external: true
EOF
```

환경변수를 `.env`에 넣는다. **서버에만 두고 절대 커밋하지 않는다.**

```bash
sudo tee /srv/rag/.env >/dev/null <<'EOF'
GOOGLE_API_KEY=...
EOF
sudo chmod 600 /srv/rag/.env
```

환경변수가 없어도 **빈 `.env`는 만들어야 한다.** compose가 `env_file`에 지정된 파일이
없으면 에러를 낸다.

```bash
sudo touch /srv/rag/.env
```

## 5. DNS A 레코드 — 가비아

My가비아 → DNS 관리툴 → `ai-agent-develop.cloud` → DNS 설정

| 타입 | 호스트 | 값 | TTL |
|---|---|---|---|
| A | `rag` | `13.209.128.48` | 600 |

기존 레코드(`whybuy`, `test`)는 건드리지 않는다.

**전파를 확인하고 나서 6번으로 넘어간다.**

```bash
nslookup rag.ai-agent-develop.cloud 8.8.8.8
```

> DNS가 안 퍼진 상태에서 Caddy를 reload하면 인증서 발급이 실패하고,
> Let's Encrypt 실패 한도에 걸려 한동안 재발급이 막힌다.

## 6. Caddy에 블록 추가 — Session Manager

`/srv/caddy/Caddyfile`에 블록을 덧붙인다. **기존 블록은 지우지 않는다.**

```
rag.ai-agent-develop.cloud {
    reverse_proxy rag:8000
}
```

```bash
docker compose -f /srv/caddy/docker-compose.yml exec caddy caddy reload --config /etc/caddy/Caddyfile
```

`reverse_proxy` 대상은 호스트 포트가 아니라 **`web` 네트워크상의 컨테이너 이름과
그 컨테이너가 리슨하는 포트**다.

## 7. 배포

```bash
git push origin master
```

끝. 이후 코드를 고칠 때마다 하는 작업은 이것뿐이다.

## 확인

```bash
curl -s -o /dev/null -w "HTTP %{http_code}\n" https://rag.ai-agent-develop.cloud/
docker compose -f /srv/rag/docker-compose.yml ps
```

배포된 이미지 태그가 방금 push한 커밋과 같은지 본다.
**다르면 예전 컨테이너가 그대로 도는 것이고, 워크플로가 초록불이어도 배포는 실패다.**

## 주의할 세 가지

### ① 포트를 세 군데서 맞춘다

| 위치 | 값 |
|---|---|
| 앱이 실제로 리슨하는 포트 | `8000` |
| compose의 `expose` / `healthcheck` | `8000` |
| Caddyfile의 `reverse_proxy rag:____` | `8000` |

하나라도 틀리면 **502**가 뜬다. 가장 흔한 실수다.

### ② arm64로 빌드되는지

서버가 Graviton(ARM)이다. 파이썬·Node는 대부분 문제없지만 amd64 전용 휠이나 베이스 이미지가
있으면 `exec format error`가 난다. 걸리면 베이스 이미지를 arm64 지원 버전으로 바꾼다.

### ③ RAM 2GB가 실질 제약

| | 사용 |
|---|---|
| OS + Docker | 약 300MB |
| Caddy | 약 50MB |
| 앱 (상한 768MB) | 앱마다 |
| **여유** | **약 1.4GB** |

**앱 2개는 편하고 3개면 빡빡하다.** API 기반 RAG 앱은 300~600MB라 괜찮지만,
n8n(400MB~1GB)까지 올리면 꽉 찬다.

부족하면 인스턴스 타입을 올린다. **EC2는 중지 → 타입 변경 → 시작으로 2분이면 끝난다**
(Elastic IP를 붙여뒀으므로 IP는 안 바뀐다). 다만 `t4g.small`을 벗어나면
2026-12-31까지의 무료 트라이얼 대상에서 빠진다.

## 문제가 생기면

| 증상 | 볼 곳 |
|---|---|
| `502 Bad Gateway` | 포트 세 군데 일치 여부. `docker compose ps`로 컨테이너가 실제로 떠 있는지 |
| `Not authorized to perform sts:AssumeRoleWithWebIdentity` | 2번에서 `sub`를 **ID 포함 형식**으로 넣었는지 |
| `exec format error` | arm64 빌드 여부 |
| 인증서 발급 실패 | DNS 전파 확인 없이 reload했는지. 80번 포트가 열려 있는지 |
| 배포 성공인데 내용이 그대로 | `docker compose ps`의 이미지 태그와 커밋 SHA 대조 |
| SSM 명령 실패 | 서버에서 `sudo /usr/local/bin/deploy-app rag` 직접 실행해 원인 확인 |
