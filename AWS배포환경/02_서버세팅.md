# 2단계 — 서버 초기 세팅

[배포 환경 구축 계획](README.md)의 2단계 상세 절차.

인스턴스는 떴지만 아직 빈 우분투다. 여기서 스왑·Docker·공용 네트워크·배포 스크립트를 올리고,
Caddy를 띄워 80/443을 받게 한다. 대부분은 [`templates/bootstrap.sh`](templates/bootstrap.sh)가
한 번에 처리한다.

## 1. 스크립트를 서버로 옮기기

로컬에 AWS 액세스 키를 만들지 않았으므로 파일을 밀어 넣을 경로가 없다.
**Session Manager 터미널에 heredoc으로 붙여넣는다.**

먼저 이 한 줄만 입력한다.

```bash
cat > /tmp/bootstrap.sh <<'BOOTSTRAP_EOF'
```

프롬프트가 `>`로 바뀌면 `bootstrap.sh` 전체 내용을 붙여넣고, 마지막에 `BOOTSTRAP_EOF`를 입력한다.

> **붙여넣는 중 화면이 깨져 보여도 대부분 표시 문제다.** 브라우저 터미널이 `>` 프롬프트를
> 비동기로 출력해서 `networ> > > ks:` 처럼 단어 중간에 섞여 보인다.
> 실제 파일이 멀쩡한지는 아래 검증으로 판단한다.

```bash
wc -l /tmp/bootstrap.sh && bash -n /tmp/bootstrap.sh && echo "문법 OK"
```

## 2. 실행

```bash
sudo bash /tmp/bootstrap.sh
```

Session Manager는 `ssm-user`로 접속하므로 `sudo`가 필요하다.
2 vCPU라 2~4분이면 끝난다.

### 스크립트가 하는 일

| 항목 | 내용 | 이유 |
|---|---|---|
| 스왑 2GB | `/swapfile` 생성, `vm.swappiness=10` | RAM 1.8Gi에서 스왑이 없으면 컨테이너 몇 개만 띄워도 OOM |
| Docker | arm64 저장소에서 `docker-ce` + compose 플러그인 | |
| **로그 로테이션** | `max-size 10m`, `max-file 3` | 왜샀어 때 겪은 디스크 풀 재발 방지. 기본값은 무제한이라 로그가 디스크를 채운다 |
| AWS CLI | aarch64 빌드 | ECR 로그인에 필요 |
| `web` 네트워크 | `docker network create web` | Caddy와 앱들이 컨테이너 이름으로 통신 |
| `/usr/local/bin/deploy-app` | 배포 스크립트 | Actions가 SSM으로 이걸 호출한다 |

### `deploy-app`을 서버에 두는 이유

워크플로에서 SSM으로 긴 셸 명령을 직접 보내면 JSON 안에 따옴표가 중첩돼 금방 지저분해진다.
**명령을 서버에 파일로 두고 워크플로는 이름만 부르면** 워크플로가 한 줄로 끝나고,
배포 로직을 고칠 때 앱 저장소를 건드리지 않아도 된다.

```bash
aws ssm send-command --document-name "AWS-RunShellScript" \
  --parameters "commands=[\"/usr/local/bin/deploy-app $APP_NAME $SHA\"]"
```

## 3. docker 명령 권한 — 놓치기 쉬운 곳

bootstrap은 `ubuntu` 계정을 docker 그룹에 넣지만, **Session Manager는 `ssm-user`로 접속한다.**
게다가 `ssm-user`는 첫 세션 연결 때 생성되므로 bootstrap 시점에는 없을 수도 있다.

`docker` 명령이 `permission denied while trying to connect to the Docker daemon socket`을 내면
아래를 실행하고 **세션을 새로 연다**(그룹 변경은 새 세션부터 적용된다).

```bash
sudo usermod -aG docker ssm-user
```

docker 그룹은 root와 동등한 권한이지만, `ssm-user`는 이미 암호 없는 sudo를 가지므로
권한이 새로 늘어나는 건 아니다.

## 4. Caddy 기동

`/srv`는 `ubuntu` 소유라 파일 생성에는 `sudo`를 쓴다.

```bash
sudo mkdir -p /srv/caddy
```

```bash
sudo tee /srv/caddy/docker-compose.yml >/dev/null <<'EOF'
services:
  caddy:
    image: caddy:2-alpine
    container_name: caddy
    restart: unless-stopped
    ports:
      - "80:80"
      - "443:443"
    volumes:
      - ./Caddyfile:/etc/caddy/Caddyfile:ro
      - caddy_data:/data
      - caddy_config:/config
    networks:
      - web

networks:
  web:
    external: true

volumes:
  caddy_data:
  caddy_config:
EOF
```

도메인을 붙이기 전에는 살아있는지 확인할 블록만 둔다.

```bash
sudo tee /srv/caddy/Caddyfile >/dev/null <<'EOF'
{
    email junhyeong7757@gmail.com
}

:80 {
    respond "caddy alive" 200
}
EOF
```

```bash
cd /srv/caddy && docker compose up -d && docker compose ps && curl -s localhost && echo
```

`caddy alive`가 찍히면 서버 안에서는 정상이다.
**브라우저에서 퍼블릭 IP로도 접속**해봐야 보안 그룹의 80번 규칙까지 검증된다.

### `caddy_data` 볼륨을 지우지 말 것

발급받은 인증서가 여기 저장된다. 볼륨을 날리면 전부 다시 받아야 하고,
Let's Encrypt 발급 한도에 걸릴 수 있다.

## 5. 확인

```bash
swapon --show
docker --version && docker compose version
docker network ls | grep web
aws --version
aws sts get-caller-identity
```

마지막 명령의 `Arn`에 **`assumed-role/ec2-deploy-target/...`** 이 보여야 한다.
이게 안 나오면 IAM 인스턴스 프로파일이 안 붙은 것이고, ECR에서 이미지를 못 받아온다.
