# AWS 배포 환경 구축 기록 (2026-09-11)

만든 걸 바로 올릴 수 있는 상시 배포 서버를 하루 만에 AWS에 구축한 기록.
계획은 [README](README.md), 단계별 절차는 [00](00_계정설정.md)~[04](04_도메인과HTTPS.md) 문서에 있다.
여기에는 **왜 그렇게 정했는지와 실제로 걸린 지점**을 남긴다.

결과: **https://test.ai-agent-develop.cloud** — `git push` 하나로 빌드부터 HTTPS 서비스까지 끝난다.

## 1. 서버를 어디에 둘 것인가 — 세 번 갈아엎은 의사결정

### 출발점: 네이버클라우드 Micro Server가 너무 느렸다

[왜샀어 Docker 배포](../vercel실습/왜샀어/Docker배포전환.md) 때 쓴 서버는 1 vCPU / 1GB다.
여기서 `docker build`를 반복하다 디스크 풀과 SSH 끊김을 겪었다.
**병목은 RAM 1GB**였고, 새 프로젝트를 계속 올리려면 더 큰 서버가 필요했다.

### AWS 프리티어를 먼저 떠올렸지만, 이미 없어진 제도였다

"12개월 750시간 t2.micro 무료"는 **2025년 7월 15일 이전 계정에만** 적용된다.
지금 신규 가입하면 $100~200 크레딧 + **6개월 뒤 계정 자동 폐쇄** 구조다.
게다가 프리티어 대상인 t3.micro도 RAM 1GB라 **지금과 똑같아서 문제가 해결되지 않았다.**

### Oracle Always Free로 방향을 틀었다가 가입에서 막혔다

2 OCPU / 12GB / 200GB가 영구 무료. 스펙만 보면 압도적이다.
(2026년 6월 15일에 4 OCPU/24GB에서 **공지 없이 반토막** 났다는 것도 이때 알았다.)

하지만 **카드 인증에서 10번 넘게 실패**했다. Oracle은 가입 심사가 유독 빡빡한 걸로 알려져 있고,
뚫더라도 A1 인스턴스는 "Out of Capacity"로 생성 자체가 안 되는 경우가 많다.
기대값이 낮다고 판단해 접었다.

### 유료 전환을 검토하며 깨달은 것

가성비만 보면 Contabo(4 vCPU/8GB, 월 약 1만원)가 압도적이다. Hetzner는 2026년 6월 가격 인상으로
싱가포르 CX가 €15.49부터라 후보에서 빠졌다.

그런데 **애초에 AWS를 원했던 이유가 "취업 스펙"이었다.** 여기서 판단이 갈렸다.

- 이력서에 적히는 문장은 어느 클라우드든 "리눅스 서버에 Docker로 배포"로 똑같다.
  **클라우드 이름 자체는 변별력이 없다.**
- 변별력은 EC2가 아니라 **VPC·보안 그룹·IAM·ECR 같은 매니지드 서비스를 실제로 다뤄본 경험**에서 나온다.
- Lightsail은 그걸 전부 감춰버려서, 싸고 쉬운 대신 목적을 절반만 충족한다.

그래서 **EC2**로 정했다. 리눅스·Docker·리버스 프록시는 이미 해봤으니 추가로 배울 게
정확히 VPC/보안그룹/IAM뿐이고, 그게 배워야 할 부분이었다.

### 결정타: t4g.small이 2026-12-31까지 무료였다

`t4g.small`(2 vCPU / 2GB, Graviton2 ARM)은 **월 750시간 무료 트라이얼**이 2026년 12월 31일까지
연장돼 있었다. 서울 리전 포함, 신규·기존 계정 모두. 750시간이면 한 달 내내 켜둘 수 있다.

일반 프리티어와 **별개 프로그램**이라 콘솔에 "프리 티어 사용 가능" 배지로 안 뜰 수 있다.
배지가 없다고 없는 게 아니다.

| | 2026-12-31까지 | 2027-01-01부터 |
|---|---|---|
| EC2 t4g.small | $0 | 약 $15 |
| EBS gp3 30GB | 약 $2.7 | 약 $2.7 |
| ECR·Elastic IP·전송 | 약 $0.1 | 약 $0.1 |
| **월 합계** | **약 $3** | **약 $18** |

### 네이버 서버는 남겨뒀다

2027년 8월까지 무료이고, 왜샀어는 KIS API 왕복 지연 때문에 한국 리전이 실제로 의미 있는
유일한 앱이다. 공짜로 굴러가는 걸 지금 버릴 이유가 없다. 무료가 끝날 때 이관 여부를 정한다.

## 2. 만든 구조

```
git push (master)
   │
   ▼
GitHub Actions  ── OIDC ──▶ IAM Role (장기 키 없음)
   │ docker build --platform linux/arm64
   │ push ──▶ ECR
   │
   └─ SSM Run Command ──▶ EC2에서 deploy-app 실행

EC2 t4g.small (ap-northeast-2)
   ├─ Caddy :80 :443   서브도메인 라우팅 + Let's Encrypt 자동 발급
   └─ deploy-test      docker network "web", 호스트 포트 미개방
```

설계에서 의도적으로 지킨 네 가지.

| 원칙 | 이유 |
|---|---|
| **서버에서 빌드하지 않는다** | 왜샀어 때 1 vCPU에서 빌드하다 겪은 디스크 풀·SSH 끊김의 구조적 제거. 서버는 pull만 한다 |
| **포트 22를 열지 않는다** | SSM Session Manager로 접속. SSH 키는 SSM이 고장 났을 때를 위한 안전망으로만 등록 |
| **장기 액세스 키를 만들지 않는다** | GitHub OIDC로 매번 임시 자격증명. GitHub Secrets에 AWS 키가 없으니 유출 사고가 구조적으로 불가능 |
| **권한을 리소스 단위로 좁힌다** | SSM 명령 대상을 인스턴스 ARN으로 고정. 역할이 탈취돼도 다른 인스턴스는 못 건드린다 |

## 3. 트러블슈팅

### ① `sub` 클레임 형식 — 설정이 다 맞는데 계속 거절당했다

증상: `Could not assume role with OIDC: Not authorized to perform sts:AssumeRoleWithWebIdentity`

확인한 것은 전부 정상이었다.

- OIDC 공급자 URL·Audience(`sts.amazonaws.com`) ✓
- 역할 ARN이 워크플로가 부르는 값과 글자까지 일치 ✓
- 신뢰 정책의 `Principal.Federated`, `Action`, `aud` 조건 ✓
- 역할 생성 시각이 실행보다 앞섬(전파 지연 아님) ✓

**AWS가 "역할 없음"과 "신뢰 정책 불일치"를 같은 메시지로 응답한다**는 점이 진단을 어렵게 했다.
역할 이름 추측을 막으려는 의도적 설계인데, 덕분에 엉뚱한 데를 계속 의심했다.

추측을 멈추고 **GitHub이 실제로 보내는 클레임을 워크플로에서 찍어봤다.**

```python
# ACTIONS_ID_TOKEN_REQUEST_URL로 토큰을 받아 payload만 디코드 (토큰 자체는 출력하지 않음)
sub = 'repo:jjh7757@307797437/deploy-test@1365988315:ref:refs/heads/master'
```

`sub`에 **owner ID와 repo ID가 붙어 있었다.** AWS 콘솔 마법사는 구형식
`repo:jjh7757/deploy-test:*`를 생성하는데, 이건 위 값과 매칭되지 않는다.

```
repo:jjh7757@307797437/deploy-test@1365988315:ref:refs/heads/master
     ^^^^^^^ ^^^^^^^^^ ^^^^^^^^^^^ ^^^^^^^^^^
     소유자  소유자 ID   저장소       저장소 ID
```

이름이 바뀌거나 남이 그 이름을 차지해도 ID는 안 변하므로 **보안상 더 강한 형식**이다.
GitHub이 먼저 바꿨고 AWS 콘솔이 아직 못 따라온 상태였다. ID는 다음으로 확인한다.

```bash
gh api repos/<owner>/<repo> --jq '{owner_id:.owner.id, repo_id:.id}'
```

신뢰 정책에 두 형식을 모두 넣어 해결했다. 둘 다 저장소를 특정하므로 보안은 그대로다.

**교훈: 콘솔 마법사가 만들어준 값이라고 맞다는 보장이 없다.
에러 메시지가 모호할 때는 추측을 반복하는 것보다 실제 값을 출력해보는 게 훨씬 빠르다.**

### ② compose 환경변수 범위 — 배포는 성공했는데 빨간불

증상: 이미지 pull과 컨테이너 기동은 로그에 찍히는데 워크플로가 실패했다.

```
Container deploy-test Started
...
The "APP_NAME" variable is not set. Defaulting to a blank string.
validating /srv/deploy-test/docker-compose.yml: services.app.container_name '' does not match pattern
```

원인은 내가 쓴 `deploy-app` 스크립트였다. compose 변수를 **명령 앞에만** 붙여놨더니,
마지막 상태 확인용 `docker compose ps`에서 변수가 빠져 `container_name`이 빈 문자열이 됐다.

```bash
# 잘못
ECR_REGISTRY="$REGISTRY" APP_NAME="$APP" docker compose up -d
docker compose ps          # ← 변수 없음

# 고침
export ECR_REGISTRY="$REGISTRY"
export APP_NAME="$APP"
docker compose up -d
docker compose ps
```

**이걸 잡아낸 건 워크플로에 넣어둔 SSM 결과 상태 체크였다.**
`ssm send-command`는 명령을 보내기만 하고 성공 여부를 알려주지 않으므로,
`get-command-invocation`으로 Status를 확인해 실패 시 종료하도록 해뒀다.

```bash
if [ "$STATUS" != "Success" ]; then
  echo "배포 실패: $STATUS"; exit 1
fi
```

이 체크가 없었으면 **워크플로는 초록불인데 서버는 반쯤 실패한 상태**를 그냥 지나쳤을 것이다.
배포 자동화에서 "명령을 보냈다"와 "명령이 성공했다"는 다른 얘기다.

### ③ 그 밖에 걸린 작은 것들

- **Session Manager는 `ssm-user`로 접속한다.** bootstrap이 `ubuntu`만 docker 그룹에 넣어서
  `docker` 명령이 permission denied였다. `ssm-user`는 첫 세션 연결 때 생성되므로
  bootstrap 시점에 없을 수 있어, 조건부로 추가하도록 스크립트를 고쳤다.
- **ECR 이미지 태그는 Mutable이어야 한다.** Immutable로 만들면 매번 밀어 넣는 `latest`가
  두 번째 푸시부터 실패한다.
- **DNS 전파 확인 전에 Caddy를 reload하면 안 된다.** Let's Encrypt가 HTTP-01로 도메인을
  확인하는데, 실패가 쌓이면 발급 한도에 걸려 한동안 묶인다.

## 4. 검증

`sha` 값이 push한 커밋과 일치하는지가 핵심이다. 이게 맞아야 **새 이미지가 실제로 반영된 것**이고,
아니면 예전 컨테이너가 그대로 도는 것이라 워크플로가 초록불이어도 배포는 실패다.

| 검사 | 결과 |
|---|---|
| HTTPS | `200`, TLS 검증 통과 |
| HTTP → HTTPS | `308` 리다이렉트 |
| 인증서 | `CN=test.ai-agent-develop.cloud`, Let's Encrypt, ~2026-12-10 |
| 배포 커밋 | 응답의 `sha`가 push한 커밋과 일치 |

## 5. 새 프로젝트를 올릴 때

1. ECR 리포지토리 생성
2. 저장소에 `Dockerfile` + [`deploy.yml`](templates/deploy.yml) 복사 (`APP_NAME`만 수정)
3. IAM 신뢰 정책에 그 저장소 `sub` 추가 — **ID 포함 형식으로**
4. 서버에 `/srv/<앱>/docker-compose.yml` + `.env`
5. Caddyfile에 블록 3줄 + A 레코드 추가
6. `git push`
