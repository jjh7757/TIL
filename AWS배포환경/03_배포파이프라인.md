# 3단계 — 배포 파이프라인

[배포 환경 구축 계획](README.md)의 3단계 상세 절차.

`git push` 한 번으로 빌드부터 서버 반영까지 끝나게 만든다.

```
git push (master)
   │
   ▼
GitHub Actions  ── OIDC ──▶ IAM Role (장기 키 없음)
   │ docker build --platform linux/arm64
   │ push ──▶ ECR
   │
   └─ SSM Run Command ──▶ EC2에서 deploy-app 실행
                            (docker compose pull && up -d)
```

**먼저 [테스트 앱](templates/test-app/)으로 경로만 뚫고, 그다음 실제 앱으로 교체한다.**
복잡한 앱으로 처음 시도하면 실패 원인이 빌드인지 권한인지 가려내기 어렵다.

## 3-1. GitHub OIDC 자격증명 공급자 (계정당 한 번)

IAM → **자격 증명 공급자(Identity providers)** → **공급자 추가**

- 공급자 유형: **OpenID Connect**
- 공급자 URL: `https://token.actions.githubusercontent.com`
- 대상(Audience): `sts.amazonaws.com`

→ **공급자 추가**

이걸 등록하면 GitHub Actions가 발급한 토큰을 AWS가 신뢰하게 된다.
덕분에 **장기 액세스 키를 만들어 GitHub Secrets에 넣을 필요가 없다.**

## 3-2. ECR 리포지토리

ECR → **리포지토리 생성**

- 표시 여부: **프라이빗**
- 이름: 앱 이름과 동일하게 (예: `deploy-test`)

이 이름이 세 곳에서 같아야 한다.

| 위치 | 값 |
|---|---|
| ECR 리포지토리 이름 | `<APP_NAME>` |
| 서버 디렉토리 | `/srv/<APP_NAME>` |
| `deploy.yml`의 `APP_NAME` | `<APP_NAME>` |

### 이미지 수명 주기 규칙 (권장)

리포지토리 → **수명 주기 정책** → 규칙 추가

- 규칙 우선순위: `1`
- 이미지 상태: **아무거나(Any)**
- 일치 기준: **이미지 개수가 다음보다 많음** → `10`
- 작업: 만료

커밋마다 이미지가 쌓이므로 이걸 안 걸면 ECR 저장 비용이 계속 는다.
월 $0.1 수준이라 당장 문제는 아니지만, 한 번 걸어두면 신경 쓸 일이 없어진다.

## 3-3. IAM 역할 `github-actions-deploy`

IAM → **역할** → 역할 생성 → **웹 자격 증명**

- 자격 증명 공급자: `token.actions.githubusercontent.com`
- Audience: `sts.amazonaws.com`
- GitHub 조직: `jjh7757` / 리포지토리: 배포할 저장소 이름

권한은 일단 비워두고 생성한 뒤, 역할 이름을 **`github-actions-deploy`** 로 한다.

생성 후 두 가지를 손본다.

1. **신뢰 정책** — [`templates/iam/github-actions-trust-policy.json`](templates/iam/github-actions-trust-policy.json)
   내용으로 교체하고 `REPO_NAME`을 실제 저장소 이름으로 바꾼다
2. **권한 정책** — 인라인 정책으로
   [`templates/iam/github-actions-permissions.json`](templates/iam/github-actions-permissions.json) 추가 (이름 `deploy`)

### 신뢰 정책의 `sub` 조건이 보안의 핵심

```json
"token.actions.githubusercontent.com:sub": "repo:jjh7757/REPO_NAME:*"
```

여기를 `repo:*` 같은 와일드카드로 열면 **아무나 자기 GitHub 저장소에서 이 역할을 가져다 쓸 수 있다.**
저장소를 반드시 특정한다. 저장소가 여러 개면 역할을 따로 만들거나 `sub` 조건에 나열한다.

권한 정책 쪽에서도 SSM 명령 대상을 인스턴스 ARN으로 고정해뒀다.
역할이 탈취돼도 다른 인스턴스에는 명령을 보낼 수 없다.

## 3-4. 저장소 준비

배포할 저장소 루트에 다음을 둔다.

```
Dockerfile
.github/workflows/deploy.yml     ← templates/deploy.yml 복사
```

`deploy.yml`에서 `APP_NAME`을 실제 이름으로 바꾼다.
`INSTANCE_ID`와 역할 ARN은 이미 채워져 있다.

### 러너 아키텍처

워크플로는 `ubuntu-24.04-arm` 러너를 쓴다. 서버가 ARM(Graviton)이라 네이티브로 빌드해야 빠르다.

- **퍼블릭 저장소**: 무료
- **프라이빗 저장소**: 과금됨 → 저장소를 퍼블릭으로 두거나, `ubuntu-latest` + QEMU로 바꾼다
  (`deploy.yml`의 주석 참고. 에뮬레이션이라 빌드가 몇 배 느려진다)

## 3-5. 서버 준비

```bash
sudo mkdir -p /srv/<APP_NAME>
sudo chown ubuntu:ubuntu /srv/<APP_NAME>
```

[`templates/app-compose.yml`](templates/app-compose.yml)을 `/srv/<APP_NAME>/docker-compose.yml`로 둔다.
앱에 환경변수가 필요하면 같은 디렉토리에 `.env`를 만든다. **`.env`는 서버에만 두고 절대 커밋하지 않는다.**

## 3-6. 검증

`git push` 후 Actions 로그를 본다.

```bash
# 서버에서
docker compose -f /srv/<APP_NAME>/docker-compose.yml ps
curl -s localhost:3000
```

**`sha=` 값이 방금 push한 커밋과 일치하는지 반드시 확인한다.**
일치하지 않으면 예전 이미지가 그대로 돌고 있는 것이고, 워크플로가 초록불이어도 배포는 실패한 것이다.

## 자주 걸리는 곳

| 증상 | 원인 |
|---|---|
| `Not authorized to perform sts:AssumeRoleWithWebIdentity` | **1순위: `sub` 클레임의 ID 형식.** GitHub은 `repo:owner@<소유자ID>/repo@<저장소ID>:...`를 보내는데 콘솔 마법사는 구형식을 생성한다. 2순위: 역할 이름 오타 (AWS는 역할 없음도 같은 메시지로 응답) |
| `no basic auth credentials` / ECR 푸시 실패 | 권한 정책에 `ecr:GetAuthorizationToken`이 `Resource: "*"`로 있는지 확인 |
| SSM 명령이 `Failed` | 서버에서 `sudo /usr/local/bin/deploy-app <APP_NAME>`을 직접 실행해 원인을 본다 |
| 배포는 됐는데 워크플로가 빨간불 / `container_name '' does not match pattern` | `deploy-app`에서 compose 변수를 개별 명령 앞에만 붙이면 뒤따르는 `docker compose ps`에서 빠져 검증 에러가 난다. `export`로 둘 것 |
| `exec format error` | arm64가 아닌 이미지를 올렸다. 러너 아키텍처와 `--platform` 확인 |
| 배포는 성공인데 내용이 그대로 | compose가 `latest` 태그를 캐시했다. `deploy-app`은 SHA 태그로 pull하므로, 태그가 제대로 넘어갔는지 확인 |

## 실제 구축에서 걸린 곳 (2026-09-11)

파이프라인이 초록불이 되기까지 두 번 막혔다. 둘 다 "설정은 맞아 보이는데 안 되는" 유형이었다.

1. **`sub` 클레임 형식** — AWS 콘솔 마법사가 만든 `repo:owner/repo:*`가 GitHub이 실제로 보내는
   ID 포함 형식과 안 맞았다. 에러 메시지가 "역할 없음"과 동일해서 역할 이름만 계속 의심했다.
   **워크플로에서 실제 클레임을 찍어보고 나서야 원인이 드러났다.**
   추측으로 돌리는 것보다 실제 값을 출력해보는 게 빨랐다.
2. **`deploy-app`의 환경변수 범위** — 배포는 성공했는데 마지막 상태 확인 명령에서 변수가 빠져
   스크립트가 1로 종료됐다. 워크플로의 상태 체크가 이걸 잡아냈다.
   **체크가 없었으면 초록불인데 실제로는 반쯤 실패한 상태를 못 봤을 것이다.**
