# 모니터링 / 알림 — SNS + 헬스체크 cron

지금까지는 앱이나 DB가 죽어도 직접 URL을 열어보거나 `docker compose ps`를 치기 전엔 몰랐다.
이 문서대로 설정하면 이상이 생겼을 때 이메일로 알림이 온다.

관련: [DB환경구성.md](DB환경구성.md), [환경정보.md](환경정보.md)

## 왜 이렇게 구성하는가

- **왜 Uptime Kuma 같은 걸 서버에 안 띄우는가** — RAM 2GB에서 [DB를 얹은 뒤 여유는 이미
  1.3GB](DB환경구성.md#ram-예산-재계산)뿐이다. 모니터링 도구까지 상주 컨테이너로 얹으면
  앱에 쓸 메모리가 또 줄어든다. 대신 **cron으로 짧게 스쳐 지나가는 스크립트**를 쓰면
  상시 메모리 점유가 없다 — 백업 스크립트와 같은 이유.
- **왜 UptimeRobot 같은 외부 서비스를 안 쓰는가** — 앱(HTTP 200)은 외부에서도 확인할 수
  있지만, **DB는 애초에 외부에 노출을 안 하므로**([설계 원칙](DB환경구성.md)) 외부 서비스가
  DB 컨테이너 상태나 디스크 사용률은 볼 방법이 없다. 서버 내부에서 도는 스크립트라야
  둘 다 한 번에 확인된다.
- **왜 SNS인가 (Discord 웹훅 대신)** — 이미 AWS 단일 구성을 원칙으로 삼고
  있고([README](README.md) "왜 AWS 단일 구성인가"), SNS는 완전 관리형이라 서버에 아무것도
  추가로 띄울 필요가 없다. 이메일 구독은 무료고, 나중에 Slack/Discord/SMS로 바꿀 때도
  구독만 추가하면 된다 — 알리는 대상과 감지 로직이 분리돼 있다.
- **왜 매번 안 알리고 상태가 바뀔 때만 알리는가** — 5분마다 도는 cron이 매번 알리면 장애가
  1시간 지속될 때 12통이 온다. `/srv/monitor.state`에 마지막 상태를 저장해두고
  정상→이상, 이상→정상 **전이가 일어난 순간에만** 발행한다.

## 구조

```
cron (5분마다)
   │
   ▼
/srv/monitor.sh
   ├─ curl로 앱 URL 확인 (deploy-test, rag) — HTTP 200이 아니면 이상
   ├─ docker inspect로 postgres/redis healthcheck 확인
   ├─ df로 루트 디스크 사용률 확인 (85% 이상이면 이상)
   │
   └─ 상태 전이 시에만 ─▶ SNS 토픽 server-alerts ─▶ 이메일 구독
```

## 결정 사항

| 항목 | 선택 | 이유 |
|---|---|---|
| 실행 방식 | cron 5분 간격 스크립트 (상주 프로세스 아님) | RAM 상시 점유 없음. [왜](#왜-이렇게-구성하는가) 참고 |
| 확인 대상 | 앱 HTTP 200, postgres/redis healthcheck, 루트 디스크 사용률 | 외부 노출 안 되는 DB까지 보려면 서버 내부에서 확인해야 함 |
| 알림 채널 | SNS 토픽 → 이메일 구독 | AWS 단일 구성 유지, 완전 관리형, 채널 교체가 구독 변경만으로 끝남 |
| 알림 빈도 | 상태 전이 시에만 (`/srv/monitor.state`로 이전 상태 추적) | 매번 알리면 장애 지속 중 스팸이 됨 |
| SNS 권한 | EC2 역할에 이 토픽 한정 `sns:Publish`만 인라인 정책으로 추가 | S3 백업과 동일한 최소 권한 패턴 |
| 비용 | 사실상 $0 | SNS는 월 100만 요청·이메일 1,000건까지 무료(영구 무료 티어)이고, 상태 전이 시에만 발행하므로 한 달에 많아야 몇 건 |
| RAM | 상시 점유 0 | cron이 몇 초짜리 프로세스를 5분마다 돌릴 뿐, postgres/redis처럼 떠 있는 컨테이너가 아니라 "앱용 여유" 예산을 깎지 않음 |

## 최초 1회 설정

**SNS 토픽 + 이메일 구독 — 로컬 admin 자격증명으로** (서버가 아니라 내 컴퓨터에서 실행)

```bash
aws sns create-topic --name server-alerts --region ap-northeast-2

aws sns subscribe \
  --topic-arn arn:aws:sns:ap-northeast-2:403187831140:server-alerts \
  --protocol email \
  --notification-endpoint <내 이메일> \
  --region ap-northeast-2
```

> AWS가 구독 확인 이메일을 보낸다. **그 안의 "Confirm subscription" 링크를 눌러야** 실제로
> 알림이 온다. 안 누르면 `aws sns list-subscriptions-by-topic`에 `PendingConfirmation`으로
> 계속 남아 있다 — SNS 발행 자체는 성공해도(로그엔 `MessageId`가 찍힘) 받는 사람이 없는 상태.

EC2 역할에 이 토픽 한정 발행 권한만 추가한다.

```bash
aws iam put-role-policy --role-name ec2-deploy-target --policy-name server-alerts-sns-publish \
  --policy-document '{
    "Version": "2012-10-17",
    "Statement": [{
      "Sid": "ServerAlertsPublish",
      "Effect": "Allow",
      "Action": ["sns:Publish"],
      "Resource": "arn:aws:sns:ap-northeast-2:403187831140:server-alerts"
    }]
  }'
```

**모니터링 스크립트를 서버에 올린다** — Session Manager에서.

```bash
sudo tee /srv/monitor.sh >/dev/null <<'EOF'
(templates/monitor.sh 내용 그대로)
EOF
sudo chown ubuntu:ubuntu /srv/monitor.sh
sudo chmod +x /srv/monitor.sh

( sudo crontab -l 2>/dev/null | grep -vF "/srv/monitor.sh" || true; \
  echo "*/5 * * * * /srv/monitor.sh >> /var/log/monitor.log 2>&1" ) | sudo crontab -

sudo /srv/monitor.sh   # 1회 즉시 실행 -- 현재 정상이면 알림 없이 "ok"만 남아야 함
cat /srv/monitor.state
```

> 원본은 [templates/monitor.sh](templates/monitor.sh) — 배포된 앱이 늘어나면 `check_url` 줄만
> 추가하면 된다.

## 장애 시뮬레이션 검증 기록

> **2026-09-20**: 알림이 실제로 오는지 직접 장애를 내서 검증했다 (아직 어떤 앱도 연결 안 된
> `redis`라 안전하게 테스트 가능했다).
>
> 1. `docker stop redis` → `monitor.sh` 실행 → `컨테이너 redis: unhealthy` 감지, SNS 발행
>    성공(`MessageId` 확인), 상태 파일 `fail`로 전이
> 2. `docker start redis` → healthy 될 때까지 대기(4회, 8초) → `monitor.sh` 재실행 →
>    "정상 복구" 알림 발행, 상태 파일 `ok`로 전이
>
> 두 알림 모두 SNS 발행까지는 성공을 확인했다. 다만 이때는 이메일 구독이 아직
> `PendingConfirmation`이라 실제 수신은 안 된 상태였다 — 확인 메일이 **스팸함**으로
> 들어가 있었다. 스팸함에서 찾아 구독을 확인한 뒤 `aws sns publish`로 테스트 메시지를
> 보내 **실제 수신까지 확인**했다(같은 날). 구독 확인 전에 발행된 알림은 재전송되지
> 않고 유실되므로, 설정 직후에는 꼭 테스트 발행으로 수신을 확인할 것.

## 주의할 점

- **이메일 구독을 확인 안 하면 알림이 안 온다.** 위 검증 기록처럼 SNS 발행은 성공해도
  구독이 `PendingConfirmation`이면 아무도 못 받는다. **구독 확인 메일이 스팸함으로
  가기 쉬우니**(실제로 그랬다) 설정 직후 꼭 스팸함까지 확인할 것.
- **`monitor.sh`는 `set -e`를 쓰지 않는다.** 개별 확인 하나가 실패해도 나머지 확인과
  알림 발행까지는 계속 진행돼야 하기 때문이다(백업 스크립트와 의도적으로 다른 부분).
- **디스크 85% 임계값은 임의값이다.** gp3 30GB 기준으로 여유를 넉넉히 남긴 숫자이므로,
  이미지가 큰 앱(`rag`처럼 1.5GB)을 여러 개 올리면 낮춰서 더 일찍 알림받는 걸 고려할 것.
- **새 앱을 배포하면 `check_url` 줄을 추가해야 모니터링된다.** 자동으로 감지되지 않는다.

## 문제가 생기면

| 증상 | 확인할 것 |
|---|---|
| 알림이 하나도 안 옴 | `aws sns list-subscriptions-by-topic`으로 구독 상태가 `PendingConfirmation`인지 |
| SNS 발행이 `AccessDenied` | 인라인 정책의 `Resource` ARN이 토픽 ARN과 정확히 일치하는지, EC2 역할에 붙었는지 |
| 장애가 지속되는데 알림이 한 번만 옴 | 의도된 동작이다. 상태 전이 시에만 알리므로 — `/var/log/monitor.log`로 계속 감지 중인지 확인 |
| cron이 안 도는 것 같음 | `sudo crontab -l`로 등록 확인, `/var/log/monitor.log` 최근 갱신 시각 확인 |
