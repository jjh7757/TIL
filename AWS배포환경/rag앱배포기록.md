# RAG 앱 배포 기록 (2026-09-12)

[전날 만든 배포 환경](구축기록.md)에 실제 앱을 처음 올린 기록.
[새 앱 배포 절차](새앱배포절차.md)가 실전에서 맞는지 검증하는 목적도 있었다.

결과: **https://rag.ai-agent-develop.cloud** — 저장소 [jjh7757/rag-web](https://github.com/jjh7757/rag-web)

정부 보도자료·계획 문서 11건에 질문하면 근거 문단을 찾아 답한다.
검색 전략(hybrid / similarity / mmr / bm25)을 UI에서 바꿔가며 같은 질문의 결과를 비교할 수 있다.

## 올릴 코드가 없다는 것부터 확인했다

TIL 저장소에는 [RAG 문서](../CS지식/RAG_파이프라인.md)만 있고 **실행 가능한 앱이 없었다.**
실습을 노트북에서 하고 정리만 커밋해온 결과다.

실제 코드는 저장소 밖 `python/aim-ai-agent/langchain_/10-rag-evalution-script/`에 있었다.
청킹·검색·생성·평가가 모듈로 분리된 978줄짜리 평가 CLI였는데, **웹 서버가 없었다.**
그래서 "배포"가 아니라 "서빙 레이어를 새로 씌우는 작업"이 됐다.

## 평가 스크립트를 서비스로 옮기며 정한 것

### 서빙에 필요한 것만 옮겼다

평가(RAGAS)·비교 모듈은 통째로 뺐다. 서비스에 필요 없는데 의존성이 무겁다.
청킹·검색·생성만 가져오니 235줄로 줄었다.

### 인덱스는 백그라운드에서 만든다

임베딩에 수 분이 걸릴 수 있는데, 기동을 막으면 **헬스체크가 실패하고 Caddy가 502를 낸다.**
서버는 바로 뜨고 인덱스는 별도 스레드에서 만든다. 준비 전 질문에는 503으로 진행 상황을 알려주고,
UI가 `/status`를 폴링해 표시한다.

`/health`는 인덱스 상태와 무관하게 200을 준다. 컨테이너가 살아 있는지와
인덱스가 준비됐는지는 다른 질문이기 때문이다.

### 인덱스는 볼륨에 두고 fingerprint로 재사용을 판단한다

문서 구성(파일명·크기)과 청킹 설정, 임베딩 모델로 해시를 만들어 저장해둔다.
다음 기동 때 같으면 기존 인덱스를 그대로 쓴다.

이게 없으면 **코드 한 줄 고쳐 재배포할 때마다 임베딩을 처음부터 다시 한다.**
시간도 시간이지만 API 호출이 그만큼 낭비된다.

### 질의를 직렬화한다

Kiwi와 Chroma 모두 스레드 안전을 보장하지 않는다. `uvicorn --workers 1` 에
앱 내부 락으로 질의를 하나씩 처리한다. 개인 학습용 서비스라 동시성보다 안정성을 택했다.

### 공개 URL이라 요청 제한을 뒀다

질문 한 번이 곧 Gemini API 호출이다. 링크를 받은 사람이 바로 써볼 수 있어야 포트폴리오로
의미가 있으므로 접속 키 대신 **IP별 분당 3회·시간당 20회 + 전체 일 300회**로 남용만 막았다.
인메모리라 재시작하면 초기화되지만 단일 컨테이너에는 충분하다.

## 절차대로 갔을 때 실제로 막힌 곳

[새 앱 배포 절차](새앱배포절차.md)의 7단계를 그대로 따라갔고, 막힌 건 하나였다.

### ECR 리포지토리를 다른 곳에 만들었다

```
name unknown: The repository with name 'rag' does not exist in the registry with id '403187831140'
```

**빌드와 푸시는 별개 단계라, 빌드가 다 끝난 뒤에야 드러난다.** 콘솔에서 리포지토리를
만들었는데도 이 에러가 나면 리전이 다르거나 퍼블릭 레지스트리에 만든 것이다.
ECR은 프라이빗과 퍼블릭이 별도 레지스트리이고 주소 체계도 다르다.

리전을 맞춰 다시 만드니 통과했다. **리소스를 만들 때 우측 상단 리전을 확인하는 습관**이
여전히 제일 중요하다는 걸 다시 확인했다.

### 그 외는 문서대로 통과했다

OIDC 신뢰 정책에 저장소를 추가할 때도 ID 형식(`repo:owner@<소유자ID>/repo@<저장소ID>:*`)을
문서에 적어둔 덕에 전날처럼 헤매지 않았다.

## 이미지가 커지면서 드러난 버그

`deploy-app`의 이미지 정리가 잘못돼 있었다.

```bash
docker image prune -f        # dangling(태그 없는) 이미지만 지운다
```

배포마다 커밋 SHA로 태그가 붙으므로 **이전 버전은 태그를 단 채 남아 계속 쌓인다.**
30MB짜리 테스트 앱에서는 드러나지 않았지만, 이 앱은 이미지가 약 1.5GB라
며칠이면 디스크 30GB를 채웠을 것이다.

```bash
docker image prune -af --filter "until=72h"   # 최근 것은 롤백용으로 남기고 정리
```

**작은 앱으로만 검증한 파이프라인은 큰 앱에서 처음 깨진다.**
테스트 앱이 파이프라인의 연결은 검증했지만 자원 관리까지 검증하지는 못했다.

ECR 쪽도 보관 개수를 `deploy-test`의 10개가 아니라 **5개**로 줄였다. 1.5GB × 10이면 15GB다.

## 메모리 실측

배포 전 가장 걱정한 부분이었다. 예상 700~850MB, 실제 **667MB**로 예상 범위 안이었다.

```
CONTAINER      MEM USAGE / LIMIT
rag            667.5MiB / 1.172GiB   55.62%
deploy-test     12.03MiB / 768MiB
caddy           23.85MiB
```

```
              total   used   free   buff/cache   available
Mem:          1.8Gi  1.1Gi   72Mi        784Mi       671Mi
Swap:         2.0Gi  5.3Mi  2.0Gi
```

### `free`는 available을 봐야 한다

`free`가 72Mi라고 위험한 게 아니다. 리눅스는 남는 메모리를 파일 캐시(`buff/cache`)로 쓰고,
앱이 요구하면 즉시 반납한다. **실제로 쓸 수 있는 양은 `available` 671Mi다.**

**스왑이 2GB 중 5.3Mi만 쓰인 것**도 중요한 신호다. 메모리 압박이 있으면 스왑이 차오른다.

### 남은 여유

| | |
|---|---|
| 가용 | 약 670MiB |
| 작은 앱 하나 더 | 가능 |
| RAG급 앱 하나 더 | 불가 |

한 개 정도는 더 올릴 수 있고, 그 이상은 `t4g.medium`(4GB)으로 올려야 한다.
타입 변경은 2분이고 Elastic IP라 주소도 안 바뀌지만,
**2026-12-31까지의 t4g.small 무료 트라이얼 대상에서 빠진다.**

### 상한은 실사용에 가깝게

실사용 667MB인데 상한이 1.2GB면, 앱이 메모리를 흘릴 때 서버 전체를 스왑으로 끌고 간다.
900MB로 낮추면 그 상황에서 이 앱만 OOM으로 죽고 나머지는 멀쩡하다.
인덱스가 볼륨에 있어 재시작해도 임베딩 없이 10초 안에 복구되므로 안전한 실패 방식이다.

## 검증

```
{"ready":true,"progress":"완료 (64초)","documents":11,"chunks":520}
```

| 항목 | 결과 |
|---|---|
| 인덱스 구축 | 64초 (문서 11건 / 청크 520개) |
| HTTPS | 200, TLS 검증 통과 |
| HTTP → HTTPS | 308 |
| 검색 | 814ms (hybrid) |
| 생성 | 2,513ms |
| 인용 | 질문과 맞는 PDF의 1·4·6·18쪽 |

## 관찰 — 청크 520개는 적다

문서 11건에 청크 520개면 문서당 47개다. 정부 PDF치고 적은 편이라,
표·이미지 위주 페이지에서 텍스트 추출이 덜 됐을 가능성이 있다.

[RAG 검색 고도화](../CS지식/RAG_검색고도화.md)에 정리한
*"검색 문제는 알고리즘 이전에 문서 추출·청킹 품질부터 점검"* 이 정확히 이 지점이다.
지금은 답변이 잘 나오지만, 검색이 안 되는 질문을 만나면 여기부터 봐야 한다.

로그에 뜨는 `fontTools is required to fully parse...` 경고도 같은 맥락이다.
텍스트 추출 자체에는 영향이 없지만, 추출 품질을 의심할 근거는 된다.

## 정리

- **절차 문서는 실전에서 통했다.** 7단계 중 막힌 건 ECR 리전 하나뿐이고, 전날 겪은
  OIDC `sub` 형식 문제는 문서에 적어둔 덕에 재발하지 않았다.
- **작은 앱으로 검증한 파이프라인에는 사각지대가 있었다.** 이미지 정리 버그가
  1.5GB 앱을 올리고 나서야 드러났다.
- 이제 `git push` 하나로 RAG 앱이 갱신된다.
