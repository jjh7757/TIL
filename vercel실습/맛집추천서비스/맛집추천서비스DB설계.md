# 맛집 추천 서비스 DB 설계

지도 API 캐싱 없이, 사용자가 직접 다녀온(또는 갈) 식당을 등록·기록하는 방식으로 단순화한 설계.
`budget` 필드로 예산 조건 필터링을, `visited`/`rating`/`memo`로 개인 기록을 겸한다.
카카오/네이버 지도 API 연동, 추천 요청 이력, 가격 태그, 즐겨찾기 별도 테이블은 이번 MVP에서 빼고
테이블 하나로 시작한다.

## 테이블 설계

```
restaurants
  id            (자동)
  name          식당 이름
  category      한식/중식/일식/양식/카페
  address       주소
  budget        예산
  visited       다녀왔는지 (true/false)
  rating        별점 (1~5, 안 갔으면 비움)
  memo          한 줄 메모
  user_id       누가 등록했는지
  created_at    (자동)
```

## SQL (Supabase/Postgres)

```sql
create table if not exists public.restaurants (
  id          bigint generated by default as identity primary key,
  name        text not null,
  category    text not null check (category in ('한식', '중식', '일식', '양식', '카페')),
  address     text,
  budget      integer not null check (budget > 0),
  visited     boolean not null default false,
  rating      int check (rating between 1 and 5),
  memo        text,
  user_id     uuid not null references auth.users(id) on delete cascade,
  created_at  timestamptz not null default now(),
  -- 안 갔으면 별점은 비워둔다
  check (rating is null or visited = true)
);

create index if not exists restaurants_user_id_idx on public.restaurants (user_id);
create index if not exists restaurants_budget_idx on public.restaurants (budget);
create index if not exists restaurants_category_idx on public.restaurants (category);

alter table public.restaurants enable row level security;

create policy "users can read own restaurants"
  on public.restaurants for select to authenticated using (auth.uid() = user_id);

create policy "users can add own restaurant"
  on public.restaurants for insert to authenticated with check (auth.uid() = user_id);

create policy "users can update own restaurant"
  on public.restaurants for update to authenticated using (auth.uid() = user_id);

create policy "users can delete own restaurant"
  on public.restaurants for delete to authenticated using (auth.uid() = user_id);
```

## 이 설계에서 "예산 기반 추천"이 동작하는 방식

별도의 추천 테이블 없이, 조회 시점에 필터링한다.

```sql
-- 내가 등록한 식당 중 예산 이하, 카테고리 일치하는 곳
select * from public.restaurants
where user_id = auth.uid()
  and budget <= :my_budget
  and category = :my_category
order by rating desc nulls last;
```

## 업데이트 — 전체 공개 조회로 변경

사용자 요청에 따라 "본인 목록만 조회" 정책을 "읽기는 공개, 쓰기는 본인만"으로 바꿨습니다.

```sql
drop policy if exists "users can read own restaurants" on public.restaurants;

create policy "authenticated users can read all restaurants"
  on public.restaurants for select to authenticated using (true);
```

목록·상세·추천 화면에 등록자를 표시하기 위해 프로필 테이블을 추가하고, 신규 가입 시 트리거로 채웁니다.

```sql
create table if not exists public.profiles (
  id    uuid primary key references auth.users(id) on delete cascade,
  email text not null
);

create function public.handle_new_user()
returns trigger as $$
begin
  insert into public.profiles (id, email) values (new.id, new.email);
  return new;
end;
$$ language plpgsql security definer;

create trigger on_auth_user_created
  after insert on auth.users
  for each row execute function public.handle_new_user();
```

INSERT/UPDATE/DELETE 정책은 그대로 본인 소유 행만 가능하도록 유지합니다 (`auth.uid() = user_id`).

## 이전 설계에서 빠진 것 (필요해지면 다시 검토)
- 카카오/네이버 지도 API로 식당을 검색·캐싱하는 기능 — 지금은 사용자가 이름·주소를 직접 입력
- 위도/경도 기반 "내 근처" 검색 — `address`가 텍스트라 거리순 정렬 불가
- 추천 요청 이력(`recommendations`/`recommendation_items`), 가격 태그(`restaurant_price_tags`),
  별도 즐겨찾기 테이블 — 등록된 행 자체가 "내 리스트"이자 사실상 즐겨찾기라 따로 안 둠

## 아직 정하지 않은 것
- `category`를 5종 고정 enum이 아니라 자유 입력으로 바꿀지

> 다른 사람이 등록한 식당을 공유해서 볼 수 있게 할지는 "업데이트" 항목에서 공개 조회로 확정했습니다.
