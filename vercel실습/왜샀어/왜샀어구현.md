- 서비스명: 왜샀어 (영문: **WhyBuy**)
- 한 줄 정의: 투자 초보자가 모의투자로 실제 매매를 하되, 주문 전에 반드시 "왜 사는지/파는지" 근거를 남기게 해서 "그냥 감"으로 사고파는 습관을 줄여주는 서비스
- 기획 원안: [KIS-Agent-Notes](../../KIS-Agent-Notes/01_Baseline/01_project_statement.md) — 텔레그램 봇으로 처음 기획했던 버전
- 웹 서비스 기획 문서: [jjh7757/whybuy의 KIS-Web-Agent-Notes](https://github.com/jjh7757/whybuy/tree/master/KIS-Web-Agent-Notes) — 채팅 대신 웹 폼으로 피벗한 뒤 다시 쓴 기획서. 계획이 뒤집힌 곳은 지우지 않고 "원래 계획 + 왜 뒤집었는지"를 함께 남겨둠
- 구현 저장소: [jjh7757/whybuy](https://github.com/jjh7757/whybuy)

- 발표자료: [왜샀어_발표.pptx](왜샀어_발표.pptx)

## 배경 — 왜 텔레그램 봇에서 웹 서비스로 바꿨나

[금융투자봇](../../n8n실습/금융투자봇/README.md)(n8n + 텔레그램, KIS 모의투자 API 연동)을 5일 개인 프로젝트로 구체화하며 [KIS-Agent-Notes](../../KIS-Agent-Notes/01_Baseline/01_project_statement.md) 기획서까지 썼지만, 실제 개발 단계에서 자연어 채팅 인터페이스를 웹 폼으로 바꿨다. 채팅은 매수/매도 같은 되돌리기 어려운 액션에 "몇 주를 얼마에 살지"를 자연어로 정확히 확인받기엔 느리고 부정확했고, 폼은 수량·가격·근거를 구조화된 입력으로 강제할 수 있어 이 서비스의 핵심("근거를 반드시 남긴다")과 더 잘 맞았다.

## 화면 3개

| 경로 | 화면 | 내용 |
|---|---|---|
| `/` | 내 계좌 | 가상 투자금·주문에 쓴 금액·남은 예산, 보유 종목과 평가손익, 대기중인 지정가 주문(체결 확인·취소) |
| `/trade` | 종목 찾아보기 | 검색·인기 종목 → 탭 3개(차트·호가 / 종목정보 / 공시뉴스) → 근거를 고르고 매수·매도 주문 |
| `/journal` | 지난 근거 | 과거 주문의 근거와 당시 가격 vs 현재 가격, AI의 근거 편중 지적 |

첫 방문자에게는 실제 화면 요소를 짚어주는 6단계 스포트라이트 튜토리얼이 자동 실행된다.

## 데이터베이스 설계

Supabase 테이블 6개: `stocks`(종목 마스터, 코스피 전 종목 915개) · `orders`(주문) · `rationales`(판단 근거) · `user_wallets`(사용자별 가상 예산) · `kis_tokens`(KIS 토큰 캐시) · `event_logs`(이벤트 기록)

- `orders.expected_price`(주문 당시 가격)가 회고 화면의 핵심 — "그때 얼마였는지"를 나중에 비교하려면 주문 시점 가격을 반드시 그대로 저장해야 함
- **종목명을 `orders`에 중복 저장**: 정규화보다 기록의 불변성을 우선함. 종목명이 바뀌거나 상장폐지돼 `stocks`에서 사라져도 "그때 무엇을 샀는지" 기록은 그대로 남아야 하기 때문
- **남은 예산은 컬럼으로 캐시하지 않고 매번 `orders` 합계로 계산**: 캐시 값과 실제 주문 합계가 어긋나는 사고를 원천 차단
- `stocks.dart_corp_code`(DART 고유번호) — 공시 조회가 종목이 아니라 회사 단위 API라 별도 매핑 필요. 915종목 중 805개만 매핑됨(누락 110개는 전부 우선주 — 원래 회사 단위 공시가 따로 없어 문제 아님)
- `kis_tokens`는 RLS를 켜되 정책은 아예 두지 않아, anon key로는 읽을 수 없고 서버 전용 클라이언트만 접근 가능

## KIS API 연동과 레이트리밋 트러블슈팅

가장 오래 막혔던 문제. KIS는 앱키 하나당 **초당 1건**까지만 API 호출을 허용하는데(`EGW00201: 초당 거래건수를 초과하였습니다`), 처음엔 이걸 모르고 기능마다 따로 부딪혔다 — 매수 직후 매수가능조회가 이어지는 주문 API, 인기 종목 목록, 분봉 차트, 배당 조회 등에서 각각 새로고침 두 번 만에 걸릴 정도였다.

**해결**: 기능별로 재시도·캐시를 따로 넣던 방식을 버리고, 모든 KIS 호출이 공통으로 거치는 지점([`lib/kis.ts`](https://github.com/jjh7757/whybuy/blob/master/lib/kis.ts)의 `callKis`)에 "마지막 호출로부터 최소 1.1초는 기다렸다가 나간다"는 전역 프라미스 체인 큐(`reserveKisSlot`)를 하나 추가했다. 처음엔 450ms 간격으로도 간헐적으로 걸렸고, 1.1초에서는 실주문(주문번호 `0000005301`, 삼성전자 2주)까지 확인하며 충분함을 검증했다.

- raw `fetch`로 KIS를 직접 부르는 경로(예: hashkey 발급)도 앞에 `reserveKisSlot()`을 넣어야 한다 — 하나라도 큐를 건너뛰면 그 호출이 다른 호출과 충돌해 다시 `EGW00201`이 뜬다.
- **분봉 차트**([`app/api/chart/route.ts`](https://github.com/jjh7757/whybuy/blob/master/app/api/chart/route.ts))처럼 한 요청 안에서 최대 13페이지를 연속 호출해야 하는 기능은 이 큐 때문에 응답이 오래 걸리는 새 문제가 생겼다. 이중으로 걸려있던 페이지 간 sleep(`INTRADAY_GAP_MS`, 큐가 이미 1.1초를 보장하므로 순수 낭비였음) 제거, 응답 데드라인을 7초 → 40초로 확대(+ Vercel `maxDuration: 45`), 토큰 조회를 페이지마다 다시 안 읽고 메모리 캐시로 바꾸는 세 가지를 같이 고쳐서 하루 전체 391개 분봉 기준 24초 → 15.8초로 줄였다. 리전을 한국(`icn1`)으로 옮긴 것도 지연 단축에 기여했다.
- **토큰 만료가 항상 401로 오지 않는다**: 한 번은 HTTP 500 + `{"rt_cd":"1","msg_cd":"EGW00123","msg1":"기간이 만료된 token 입니다."}`로 왔다. 자동 재발급 로직이 `status === 401`일 때만 도는데 이번엔 500이라 안 걸려서, 이후 모든 KIS 호출이 계속 실패했다. 이 케이스는 아직 근본 수정 전 — 다음에 이 경로를 손보면 `msg_cd === "EGW00123"`도 재발급 트리거에 포함해야 한다.

## 지정가 주문 — 주문 상태 모델을 바꿔야 했던 이유

"초보자라도 시장가로만 매수하는 건 실용성이 떨어진다"고 판단해 지정가 주문을 중간에 추가했는데, 이 앱 전체가 "주문 접수 = 즉시 체결"이라는 전제로 설계돼 있었다. 지정가는 접수 후 체결이 안 될 수 있으므로 이 전제부터 깨야 했다.

- `orders.status`: `requested → submitted(=완료 취급)/rejected` 3가지 → `requested → filled/submitted(지정가 대기중, 부분체결 가능)/cancelled/rejected` 5가지로 확장
- 시장가는 여전히 접수 즉시 `filled` 취급(체결가 재확인은 안 함, 이름만 바뀜). `submitted`(대기중)는 지정가에서만 나옴
- 신규 컬럼: `order_type`(market/limit), `limit_price`, `filled_qty`, `filled_price`, `krx_fwdg_ord_orgno`(취소에 필수)
- 가상 예산 계산([`lib/portfolio.ts`](https://github.com/jjh7757/whybuy/blob/master/lib/portfolio.ts)의 `lockedAmount`): 체결분은 `filled_price`, 지정가 미체결 잔량은 `limit_price`로 계산해 둘 다 예산에서 묶어둔다 — 대기중인 지정가 주문도 실제 증권사처럼 매수 여력을 미리 예약하고, 취소하면 풀린다
- 보유 종목(홀딩)은 `filled_qty > 0`인 주문만 집계(과거엔 `status='submitted'` 전체를 보유로 계산했음). 부분체결도 있을 수 있으므로 수량 합계는 `qty`가 아니라 `filled_qty` 기준
- **체결 확인은 자동 폴링이 아니라 사용자가 "내 계좌"에서 버튼을 눌렀을 때만** KIS에 물어본다([`check-fill`](https://github.com/jjh7757/whybuy/blob/master/app/api/order/%5Bid%5D/check-fill/route.ts), [`cancel`](https://github.com/jjh7757/whybuy/blob/master/app/api/order/%5Bid%5D/cancel/route.ts)). Vercel에 상주 프로세스가 없어 스케줄러 기반 자동 감시가 구조적으로 불가능하기 때문
- **함정**: 주문을 취소해도 원주문 행의 `cncl_yn`은 그대로 `"N"`이다. 취소는 `orgn_odno`로 원주문을 가리키는 별도의 취소 거래 행으로 따로 생기므로, "이 주문이 취소됐는가"는 원주문 행의 `cncl_cfrm_qty`(또는 `rmn_qty`)로 판단해야 한다
- 주문 정정취소 API(`tr_id: VTTC0803U`)는 원주문번호(`ORGN_ODNO`)뿐 아니라 **매수주문 응답에 들어있던 `KRX_FWDG_ORD_ORGNO`도 필수**다. 주문 시점에 저장해두지 않으면 나중에 취소할 방법이 없어서, 이 컬럼을 뒤늦게 추가했다
- **호가단위(tick size)**: KRX는 가격대별로 지정가 단위가 다르다(2천원 미만 1원 … 20만~50만원 500원 … 50만원 이상 1000원). 벗어나면 "호가단위 오류"로 거부된다([`lib/market.ts`](https://github.com/jjh7757/whybuy/blob/master/lib/market.ts)의 `priceTickSize`에 구현)

## 매도 주문 — `orders.side`가 처음 실사용되며 드러난 계산 버그

매도는 매수와 **완전히 같은 엔드포인트**(`order-cash`)를 쓰고 `tr_id`만 다르다(`VTTC0801U`). 그래서 [`lib/kis.ts`](https://github.com/jjh7757/whybuy/blob/master/lib/kis.ts)에서 `placeCashOrder(trId, ...)` 공통 함수로 묶고 매수/매도는 tr_id만 다르게 감싼 얇은 래퍼로 만들었다.

매도를 넣으면서 `getMyPortfolio`를 side-aware로 다시 짜야 했다:

- **평단가는 매수 체결분만으로 계산**하고 매도해도 바뀌지 않음(평균 매입단가 방식)
- **보유수량 = 매수 체결 수량 합 − 매도 체결 수량 합**
- **가상 예산에 매도가 반대로 작용** — 매도 체결분은 `lockedAmount()`에서 음수로 잡혀 예산을 돌려줌
- 종목코드별 지금 매도 가능한 수량(`availableToSell` = 보유수량 − 대기중 매도 잔량)을 새로 계산해 `/api/budget`에 포함. **매도는 KIS 실계좌 잔고로 검증하지 않는다** — 공유 모의계좌라 실계좌 잔고엔 다른 사용자 보유분이 섞여 있어서, 이 서비스의 `orders` 집계로만 사전 검증함
- **잠재 버그 발견**: 중복주문 방어(60초 내 동일 종목·동일 수량 재주문 차단)가 `side`를 안 보고 있어서 "5주 매수" 직후 "5주 매도"를 중복으로 오인해 막을 뻔했다. `side`를 조건에 추가해 수정

## AI 해석 설계 — 판단은 대신하지 않는다

AI가 하는 일은 세 가지: ① 시세 화면의 숫자(PER·PBR 등) 해석 + 최근 공시·뉴스를 "있었던 일"로만 언급 ② 계좌 화면의 예산·보유 종목 해석 ③ 최근 근거 20건을 보고 편중 지적 + 다음에 물어볼 질문 1개 제안(회고 화면). 매수·매도 여부 자체는 AI가 결정하지 않는다.

- **입력은 서버가 모은 실제 숫자**: 시세·지표는 KIS, 예산·보유 종목은 Supabase 주문 기록 집계(KIS 계좌 잔고 아님 — 공유 모의계좌라 잔고엔 남의 주문이 섞여 있음), 공시·뉴스는 DART·Google. Gemini는 이 숫자를 설명하는 한국어 텍스트만 돌려받는다
- **공통 금지 규칙을 모든 프롬프트 앞에 붙임**: 특정 종목 매수·매도 권유 금지, 목표가·수익률 예측 금지, 사용자 판단이 맞다/틀렸다 평가 금지. PER·PBR은 "높다/낮다"까지만 말하고 "싸다/비싸다·고평가/저평가"로 단정하지 못하게 별도로 한 번 더 못박음(같은 값도 업종·시점에 따라 뜻이 달라지므로)
- **AI가 실패해도 화면이 안 깨짐**: Gemini 호출 함수는 절대 throw하지 않고 `{ok:false}`만 반환. 화면은 숫자는 그대로 두고 AI 영역만 "해석을 준비하지 못했습니다 + 다시 시도"로 대체. 모델이 출력 형식(`제목|내용`)을 안 지켜도 글이 사라지지 않도록 형식 파싱 실패 → 빈 줄 문단 분리 → 통짜 한 덩어리 순의 폴백 체인을 둠([`lib/gemini.ts`](https://github.com/jjh7757/whybuy/blob/master/lib/gemini.ts))
- **공시뉴스 탭을 사용자에게도 그대로 공개**: 처음엔 AI 해석의 재료로만 쓰려 했지만, "AI만 원문을 보면 사용자가 AI 말을 검증할 수 없다"는 문제를 발견해 원문을 별도 탭으로 열었다. "AI가 대신 판단해주지 않는다"는 원칙과 정면으로 어긋나는 설계였기 때문

## 실서비스로 확장한다면 — 법적 리스크 검토

이 서비스의 진짜 강점은 **계좌 개설 없이 구글 로그인 하나로 실제 증권사(KIS) API 기반 모의투자를 즉시 시작할 수 있다는 것**이다. 시중 "모의주식" 앱 대부분은 자체 서버가 가짜 잔고·가짜 체결을 흉내 내는 순수 시뮬레이터인데, 이 서비스는 실제로 KIS API를 통해 진짜 계좌·진짜 주문 처리 파이프라인을 타고 진짜 주문번호가 발급된다.

그런데 이게 가능한 이유(모의계좌 1개를 여러 사용자가 가상 예산으로 나눠 씀)가 그대로 확장의 법적 벽이 된다.

- 자본시장법 제6조③: 투자중개업 = "**타인의 계산으로**" 금융투자상품 매매를 "**영업으로 하는 것**"
- 제11조: 무인가 영업 금지, 제11조의2: 무인가 영업 목적의 계좌 대여 알선·중개 금지, 제444조: 위반 시 5년 이하 징역 또는 2억원 이하 벌금
- 법에 인원수 기준은 없고, "타인의 계산으로"(손익이 실질적으로 남에게 귀속)와 "영업으로"(반복·계속·불특정 다수 — 무료라도 성립 가능) 두 성격 요건만 있다. 사용자 수를 늘리거나 계좌를 여러 개로 쪼개도 이 성격 판단 자체가 바뀌지 않는다
- "가상의 돈이니까 괜찮지 않나" 가설은 절반만 맞다. KRX가 직접 운영하는 모의증권투자게임처럼, **자체 서버가 가짜 잔고를 관리하는 순수 시뮬레이터**는 분명 안전하다. 하지만 이 서비스는 가짜인 건 돈뿐이고 **실제 증권사의 실제 계좌 인프라(모의투자 계좌도 실계좌와 동일한 형식의 고유 계좌번호가 발급됨)를 불특정 다수가 공유**하는 구조라 성격이 다르다
- 확장 경로 3가지 — 사용자별 실제 KIS 계좌를 OAuth로 연동(편의성은 잃음) / 실주문 없이 시세만 받는 자체 체결 엔진으로 전환("진짜 계좌" 차별점을 잃음) / 증권사와 정식 제휴해 화이트라벨로 편입(개인 프로젝트 단계에서 바로 못 감)
- 이번 과제에서는 셋 중 하나를 미리 구현하기보다, 한계를 명확히 인지한 채 **학습·포트폴리오 목적의 기간제 데모**로 운영하는 쪽을 택했다

## 알려진 제한사항

- 모의계좌 1개를 가상 예산으로 나눠 쓰는 구조 — 실서비스 확장 시 사용자별 실계좌 연동 필요
- `SUPABASE_SERVICE_ROLE_KEY` 사용 — 원래는 `security definer` 함수로 대체할 계획이었으나 4일 안에 못 함. 서버 코드에 버그가 생겨도 RLS가 막아주지 못함
- 지정가 주문 가격을 서버가 시세와 대조하지 않음(호가단위 배수인지만 검증)
- 코스피 915종목 전부가 KIS 모의투자에서 시세·주문까지 되는지 전수 검증 못 함
- 매도 주문을 실제 로그인 상태로 끝까지 눌러본 적 없음 — 공유 모의계좌라 대신 눌러볼 계정이 없어 기존 실주문 데이터로 집계 로직만 손으로 대조함
- 표본이 작음(본인 + 테스트 사용자 2명, 4일 데이터) — 측정값은 비율이 아니라 실수(`6건 중 4건`)로 표시

## 새롭게 배운 점

- 레이트리밋은 기능별로 막을 게 아니라, 외부 API를 호출하는 **모든 경로가 반드시 거치는 단일 지점**(이 프로젝트에선 `callKis`)에 큐를 둬야 근본적으로 해결된다. 기능마다 따로 재시도를 넣으면 어딘가 하나는 반드시 큐를 건너뛴다
- "주문 접수 = 즉시 체결"처럼 처음에 세운 전제 하나가 무너지면(지정가 도입), DB 컬럼 하나 추가로 끝나지 않고 상태 모델·집계 로직 전체를 다시 훑어야 한다는 걸 체감했다 — `orders.status` 값 하나를 늘렸을 뿐인데 보유수량·예산 계산이 참조하는 모든 곳을 다시 확인해야 했다
- "가상의 돈이라 법적으로 안전하다"는 직관은 틀릴 수 있다 — 위험의 기준은 돈의 진위가 아니라 **실제 계좌 인프라를 공유하는가**였다. 서비스의 가장 뾰족한 강점(계좌 개설 없는 즉시성)과 법적 리스크가 같은 설계 결정에서 함께 나온다는 것도 새로운 발견이었다
