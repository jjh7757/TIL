### 왜 Day 2에 이미 주문을 한 번 통과시킵니까?

주문 서브워크플로우는 이미 동작합니다(8/3자 주문 기록 2건 존재). 하지만 **`create` → `update`로 바꾸는 순간 그 검증이 무효가 됩니다.**

```
변경한 것을 검증할 수 있는 날: 목 · 금 (2일)
검증하지 않고 주말에 들어가면: 발표일 아침까지 모릅니다
```

**가장 되돌릴 수 없는 변경을 가장 이른 장중에 검증합니다.** 확인 단계와 근거 입력을 붙이기 전이라도, "메인에서 `order_id`를 넘기면 기존 행이 UPDATE된다"를 목요일에 확인해 둡니다.

**Day 2 종료 확인**

- [ ] `삼성전자` 조회 시 `삼성전자우`가 후보로 함께 제시되고 **주문이 진행되지 않습니다.**

### 가장 위험한 3개

**1위 — 주말 배치 (위험 1).** 시간을 더 써서 해결할 수 없는 유일한 제약입니다. 수·목·금 3일 안에 주문 검증과 녹화를 끝내야 합니다.

**2위 — 의도 분류 (위험 2).** 임계 경로 최대 작업이고 이후 모든 흐름이 의존합니다. 자연어 입력을 선택한 대가입니다.

**3위 — 토큰 만료 경로 (위험 3).** 24시간 내 테스트로는 절대 드러나지 않고, **발표일 월요일 아침에 처음 터집니다.** 만료시각을 강제로 바꿔보지 않으면 발견할 방법이 없습니다.

### 버퍼 사용 우선순위

```
1순위  Day 3 주문 시연 녹화 (실패하면 발표에서 주문을 못 보여줌)
2순위  Day 4 통합 테스트에서 발견한 오류 수정
3순위  발표자료와 시연 영상 보완
4순위  문서의 ⚠️ 확인 필요 항목 해소
5순위  Should 1순위 (대화 맥락) 추가
```

**5순위는 1~4순위가 모두 끝난 뒤에만 시작합니다.** 그리고 Day 5 오전까지 완성되지 않으면 되돌립니다.

---

## 8. 각 날짜에 "끝났다"고 판단하는 기준

| 날짜 | 넘어가도 되는 조건 |
|---|---|
| Day 1 수 | 테스트 표현 18/20 이상 + **토큰 두 경로 모두 확인** |
| Day 2 목 | 🔴 **주문 1건이 실제 접수되고 기존 행이 UPDATE됨** |
| Day 3 금 | 🔴 **주문 시연 영상 존재** + 확인·근거 전 KIS 미호출을 Executions에서 확인 |
| Day 4 토 | 조회 3종 동작 + **토큰 비운 상태에서 용어 설명 동작** + 장마감 차단 확인 |
| Day 5 일 | 발표자료 2분 안에 읽힘 + 리허설 1회 완료 |

> Day 2와 Day 3의 조건이 절대적입니다. **이 두 날을 놓치면 주말에 복구할 방법이 없습니다.**
