# KIS 모의투자 연동 텔레그램 AI 에이전트

초보 투자자가 **자신의 매매 판단 근거를 스스로 설명할 수 있게** 만드는 텔레그램 대화형 에이전트입니다.

## 프로젝트 소개

모의투자 계좌를 처음 열면 화면에 숫자는 많은데 무엇을 봐야 할지 알 수 없습니다. `PER`, `이동평균선`, `평가손익` 같은 용어가 설명 없이 놓여 있고, 결국 근거 없이 감으로 매매하거나 아예 매매를 미루게 됩니다.

이 프로젝트는 **투자 조언을 하지 않습니다.** 대신 세 가지를 합니다.

1. 투자용어와 지표를 초보자 언어로 설명합니다.
2. 내 모의투자 계좌 상황을 해석 문장으로 보여줍니다.
3. **모의 주문을 실행할 때 판단 근거를 함께 기록합니다.**

세 번째가 이 프로젝트의 핵심입니다.

## 해결하려는 문제

```
모의투자를 처음 시작하는 초보 투자자는
투자용어와 계좌 화면을 해석하지 못해 매매 판단을 내리지 못합니다.

판단을 내리지 못하면 매매를 미루거나, 근거 없이 감으로 매매합니다.
```

## 대상 사용자

모의투자를 처음 도전해보는 초보 투자자.

## 프로젝트 목표

```
모의 매매 1건마다 자신의 판단 근거를 스스로 적고 설명할 수 있게 만듭니다.
```

### 수익을 목표로 하지 않는 이유

| 이유 | 설명 |
|---|---|
| 통제 불가 | 시장이 하락하면 시스템이 완벽해도 수익은 나지 않습니다. |
| 기간 내 검증 불가 | "안정적인 수익"은 수개월 데이터가 필요합니다. |
| 문제와 층위 불일치 | 정의한 문제는 "이해"의 문제이고 수익은 "성과"의 문제입니다. |
| 설계 왜곡 | 수익을 목표로 걸면 시스템이 종목 추천기가 되고, 특정 종목 매수 권유는 유사투자자문 영역에 해당합니다. |

**수익은 장기 기대 효과로 두고 이 프로젝트에서 측정하지 않습니다.**

## 주요 기능

| 기능 | 사용자 발화 예시 | 하는 일 |
|---|---|---|
| 투자용어 설명 | `PER이 뭐야?` | 용어와 지표를 초보자 언어로 해설 |
| 내 계좌 진단 | `내 계좌 어때?` | 예수금·보유종목·수익률을 해석 문장으로 변환 |
| 종목 시세 해석 | `삼성전자 어때?` | 현재가·등락률과 함께 지표의 의미 설명 |
| **모의 매수 + 근거 기록** | `삼성전자 10주 사줘` | 확인 → **판단 근거 입력** → 주문 접수 |

모든 입력은 **자유로운 자연어**입니다. 슬래시 명령어를 쓰지 않습니다.

### 판단 근거 입력

주문 확인 후 근거 선택지가 인라인 키보드로 제시됩니다.

```
저평가라고 판단 / 실적이 좋아짐 / 업황이 좋아 보임
뉴스나 이슈를 봄 / 배당을 기대 / 그냥 감
```

`그냥 감`을 선택지에 넣은 이유: 없으면 사용자가 아무거나 고르고 **데이터가 오염되어 측정값을 믿을 수 없게 됩니다.** 정직한 선택지를 주면 `그냥 감` 비율 자체가 의미 있는 지표가 됩니다.

## AI가 하지 않는 것

| 금지 | 대신 누가 하는가 |
|---|---|
| 특정 종목 매수·매도 권유 | 아무도 하지 않습니다 (유사투자자문 위험) |
| 수익률 예측 | 아무도 하지 않습니다 |
| 종목코드 생성 | `stocks` 테이블 조회로만 확정 |
| 가격·수익률 계산 | 코드가 계산 |
| 주문 수량 최종 확정 | LLM이 추출하고 **코드가 검증** |

**LLM이 만든 값을 주문 파라미터로 바로 쓰지 않습니다.**

## MVP 범위

### 포함

- 자연어 의도 분류
- 종목명 → 종목코드 변환 (모호할 경우 되묻기)
- 투자용어·지표 설명
- 내 계좌 상황 진단
- 종목 시세 조회와 해석
- 모의 **매수** 주문
- 주문 확인 단계
- **판단 근거 입력과 저장**
- 예외 처리 11종
- `chat_id` 화이트리스트

### 제외

- 실전 투자 계좌
- 특정 종목 추천, 수익률 예측
- **체결 확인** (주문 접수까지만 다룹니다)
- 매도 주문
- 자동 매매, 백테스팅, 차트 분석, 뉴스 수집
- 다수 사용자·권한 체계

> **체결 확인을 제외한 이유**: 성공 기준은 체결과 무관합니다. 근거는 주문 전에 기록되므로 체결 여부가 측정값을 바꾸지 않습니다.

## 아키텍처 요약

```
사용자 → 텔레그램 → n8n 메인 워크플로우
                      ├─ 발신자 검증
                      ├─ 의도 분류 (LLM)
                      ├─ 종목코드 변환 (Supabase)
                      ├─ 사전 검증 (장 시간·예수금·중복)
                      ├─ 주문 상태 관리
                      └─ 근거 입력
                          │
                      서브워크플로우 4개
                      ├─ KIS 토큰 발급/갱신
                      ├─ 모의계좌 잔고조회
                      ├─ 시세조회
                      └─ 모의 매수/매도 주문
                          │
                      KIS 모의투자 Open API
```

| 구성 | 기술 |
|---|---|
| 오케스트레이션 | n8n (메인 1개 + 서브 4개) |
| 대화 채널 | 텔레그램 Bot API |
| 데이터 저장소 | Supabase (PostgreSQL) |
| 증권 API | KIS 모의투자 Open API (`openapivts`) |
| 자연어 처리 | LLM |

### 검증 순서 — 비용이 낮은 것부터

```
발신자(환경변수) → 의도(LLM 1회) → 종목(DB 1회)
→ 중복 주문(DB 1회) → 장 시간(계산) → 예수금(KIS 2회)
```

가장 비싼 예수금 검증이 마지막입니다. 미등록 사용자의 메시지 때문에 KIS를 호출하지 않습니다.

## 핵심 데이터

Supabase 테이블 5개입니다.

| 테이블 | 역할 |
|---|---|
| 토큰 | KIS 접근토큰 캐시 |
| 주문 | 주문의 전 생애주기 (**대기 상태 포함**) |
| `stocks` | 종목 마스터 (종목명 → 종목코드) |
| `rationales` | **판단 근거** |
| `event_logs` | 이벤트 기록 |

### 잔고·시세를 저장하지 않습니다

실시간으로 변하는 값을 복제하면 곧 틀린 값이 됩니다. 조회 시점에 KIS에서 가져오고 **조회했다는 사실만** 이벤트로 남깁니다.

### 주문 대기 상태를 별도 테이블로 만들지 않았습니다

`status` 컬럼 하나로 전 생애주기를 담습니다. 두 테이블로 나누면 같은 주문이 옮겨 다니며 상태 불일치가 생깁니다.

```
requested → awaiting_confirmation → awaiting_rationale → submitted
실패·종료: rejected / expired / cancelled
```

## 핵심 이벤트

도메인 이벤트 7개가 주문의 상태를 바꿉니다.

```
order_requested
order_confirm_asked
order_confirmed
rationale_recorded      ← 이것 없이는 주문이 진행되지 않습니다
order_submitted
order_rejected
order_expired
```

이벤트 이름은 **과거형 `snake_case`**입니다. 이미 발생한 사실의 기록이기 때문입니다.

## 측정 지표

```sql
-- 근거 기록률
rationale_recorded ÷ (order_submitted + order_rejected)

-- '그냥 감' 비율
reason_type = 'gut' 비율

-- 근거 입력 이탈률
rationale_skipped ÷ order_confirmed

-- 의도 분류 성공률
분류 성공 ÷ 전체 메시지
```

> ⚠️ **표본이 작습니다.** 5일간 3명이 만든 데이터는 통계가 아닙니다. 정량 지표는 참고치로 쓰고, **정성 확인(사용자에게 직접 근거를 물어보기)을 주된 검증 방법**으로 삼습니다.

## 개발 계획

5일 개인 프로젝트입니다 (2026-08-05 ~ 08-09, 발표 08-10).

| 시점 | 마일스톤 | 장중 필요 |
|---|---|---|
| Day 1 (수) | 기반 정비 + 의도 분류 | 불필요 |
| Day 2 (목) | 종목 해석 + 시세 + 주문 1건 실제 통과 | 🔴 필수 |
| Day 3 (금) | 주문 흐름 완성 + 검증 + 시연 녹화 | 🔴 필수 |
| Day 4 (토) | 조회 흐름 + 이벤트 + 장마감 예외 검증 | 불필요 |
| Day 5 (일) | 문서 검토 + 발표 준비 + 버퍼 | 불필요 |

**Day 4·5가 휴장일이므로 장중 검증이 필요한 작업을 Day 1~3에 전부 배치했습니다.**

## 알려진 한계

| 한계 | 설명 |
|---|---|
| 의도 분류가 단일 실패점 | 오분류되면 아래 모든 흐름이 어긋납니다. **주문 확인 단계가 최종 방어선**입니다. |
| 대화 맥락 미구현 | `그거 10주 사줘`의 "그거"를 해석하지 못합니다. 매번 종목명을 말해야 합니다. |

| 체결 확인 없음 | 주문 접수까지만 다룹니다. |

## 보안

- KIS 앱키·시크릿, 텔레그램 봇 토큰, LLM 키, Supabase 키는 **n8n Credential에만** 저장합니다.
- 계좌번호는 환경변수로 관리하며 저장소·문서·발표자료에 남기지 않습니다.
- 등록된 `chat_id`에서 온 메시지만 처리합니다. 봇은 사용자명을 알면 누구나 메시지를 보낼 수 있고 **주문은 되돌릴 수 없습니다.**

## 면책

이 프로젝트는 **학습 목적의 모의투자 도구**입니다. 투자 자문이나 종목 추천을 제공하지 않으며, 실제 투자 판단의 근거로 사용해서는 안 됩니다.
