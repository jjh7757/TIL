# 프로젝트 기준선

## 문서 정보

- 프로젝트명: KIS 모의투자 연동 텔레그램 AI 에이전트
- 문서 버전: **`v1.0`**
- 작성일: 2026-08-04
- 작성자: (본인)
- 현재 상태: **구현 기준 확정**
- 실행 환경: n8n (메인 1개 + 서브워크플로우 4개)
- 저장소: Supabase (PostgreSQL) — 기존 2개 + 신규 3개
- 일정: 5일 (기획 + 개발), 개발 종료 다음 날 발표

> `v1.0`은 구현 기준으로 합의한 첫 공식 버전입니다. 이후 변경은 반드시 **변경 기록**에 남깁니다.
- 진행 방식: 5일 개인 프로젝트 (기획 + 개발), 개발 종료 다음 날 발표

> 교안 3.4의 **필수 12개 항목**이 모두 작성되었습니다. 이제 이 문서는 구현의 기준입니다.
> 구현 중에 기준과 다른 판단이 필요해지면, 코드를 먼저 바꾸지 말고 **이 문서를 고치고 변경 기록에 남긴 뒤** 진행합니다. 문서와 구현이 다른 상태가 가장 위험합니다.

## 1. 프로젝트 목적

```
모의투자를 처음 시작하는 초보 투자자가 매매 판단을 스스로 내릴 수 있도록
투자용어 설명, 계좌 상황 해석, 종목 정보 조회를 텔레그램 대화로 제공하고,
모의 매매를 실행할 때 판단 근거를 함께 기록하도록 만듭니다.
```

이 프로젝트는 **수익을 목표로 하지 않습니다.** 사용자가 자신의 판단을 이해하고 설명할 수 있게 만드는 것이 목적입니다.

**성공 기준**: 사용자가 자신의 매매 판단 근거를 설명할 수 있는가.
근거와 제외 이유는 [프로젝트 한 문장](01_project_statement.md) 문서를 참고합니다.

---

## 2. 문제 정의

| 항목 | 내용 |
|---|---|
| 사용자 | 모의투자를 처음 도전해보는 초보 투자자 |
| 사용 상황 | 모의투자 계좌를 열었으나 무엇을 보고 어떻게 판단해야 할지 모르는 상황 |
| 문제 | 투자용어가 어려워 어떤 정보를 봐야 하는지, 어떤 전략을 써야 하는지 모릅니다. |
| 결과 | 판단을 내리지 못해 매매를 미루거나, 근거 없이 감으로 매매합니다. |
| 기대 변화 | 모의 매매 1건마다 자신의 판단 근거를 적고 설명할 수 있습니다. |

## 3. 도메인 정의

```
모의투자 계좌를 사용하는 초보 투자자가
투자용어와 계좌·종목 정보를 이해하고,
판단 근거를 남기면서 모의 매매를 실행하는 업무
```

이 프로젝트에는 웹 화면이 없습니다. **대화가 화면입니다.** 따라서 화면 설계 대신 대화 흐름 설계가 그 자리를 대신합니다.

### 주요 도메인 요소

| 도메인 요소 | 코드 이름 | 도메인 요소 | 코드 이름 |
|---|---|---|---|
| 사용자 | `User` | 의도 | `Intent` |
| 모의투자 계좌 | `Account` | 주문 | `Order` |
| 보유 종목 | `Holding` | 체결 | `Execution` |
| 종목 | `Stock` | **판단 근거** | `Rationale` |
| 시세 | `Quote` | 접근토큰 | `AccessToken` |
| 투자용어 | `Term` | 대화 세션 | `Conversation` |

`판단 근거`는 이 프로젝트의 **성공 기준을 측정하는 유일한 대상**이므로 1급 도메인 요소로 취급합니다.

자세한 내용은 [도메인 요소](../02_Domain/01_domain_elements.md) 문서를 참고합니다.

## 4. 사용자 역할

| 역할 | 주요 책임 |
|---|---|
| 투자자 | 매매를 판단하고 근거를 기록합니다. |
| AI 설명 에이전트 | 용어와 데이터를 초보자 언어로 해석합니다. |
| 대화 오케스트레이터 | 의도를 판별하고 흐름을 제어합니다. |
| KIS 모의투자 시스템 (외부) | 계좌·시세를 제공하고 주문을 접수·체결합니다. |
| 텔레그램 (외부) | 메시지를 전달합니다. |
| 운영자 | 워크플로우를 운영하고 오류를 확인합니다. |

이번 프로젝트는 **본인 단일 사용자**입니다. `투자자`와 `운영자`는 같은 사람이지만 역할을 구분해, 텔레그램에서는 운영 기능을 제공하지 않습니다.

### 필수 권한 규칙

```
등록된 chat_id에서 온 메시지만 처리합니다.
등록되지 않은 chat_id는 응답 없이 무시합니다.
```

봇은 누구나 찾을 수 있고 주문은 되돌릴 수 없으므로, 이 규칙은 `Must`입니다. 자세한 근거는 [사용자 역할](../02_Domain/02_user_roles.md) 문서를 참고합니다.

## 5. 업무 흐름

모든 흐름은 **의도 분류**라는 하나의 관문을 통과합니다. 사용자가 자유로운 자연어를 쓰기로 결정했기 때문에 의도 분류는 선택 기능이 아니라 필수 관문입니다.

### 정상 흐름 4개

| 흐름 | 내용 | 턴 수 |
|---|---|---:|
| A. 투자용어 질문 | 용어 추출 → AI 설명 → 기록 | 1 |
| B. 내 계좌 상황 진단 | 잔고 조회 → AI 해석 → 기록 | 1 |
| C. 종목 시세 조회와 해석 | 종목명 → 코드 변환 → 시세 조회 → AI 해석 → **맥락 저장** | 1 |
| D. **모의 주문** | 요청 → 확인 → **근거 입력** → 실행·결과 | 4 |

흐름 C의 맥락 저장이 없으면 흐름 D의 `그거 10주 사줘`가 동작하지 않습니다.

### 근거를 주문 전에 받는 이유

주문 후에 요청하면 사용자가 이탈해 기록률이 떨어집니다. 주문 전에 요청하면 기록률이 높아지고, **주문 직전에 스스로 이유를 말하게 만들어 판단을 한 번 더 점검**하게 됩니다. 두 번째 효과는 데이터 수집을 넘어 이 프로젝트의 목적 그 자체입니다.

### 예외 흐름 11개

| # | 예외 상황 | 주문 진행 | 재시도 |
|---|---|---|---|
| 1 | 의도 분류 실패 | — | ✅ |
| 2 | 종목명 모호 (삼성전자 / 삼성전자우) | ❌ 중단 (임의 선택 금지) | ✅ |
| 3 | 종목명 없음 | ❌ 중단 | ✅ |
| 4 | KIS 토큰 만료 | 자동 복구 (무음 재시도) | 자동 |
| 5 | 장 운영시간 아님 | ❌ 차단 (조회는 계속 가능) | 장 개시 후 |
| 6 | 예수금 부족 | ❌ 차단 | ✅ |
| 7 | KIS 주문 거부 | ❌ 실패 (근거는 삭제하지 않음) | ✅ |
| 8 | 근거 입력 중 이탈 | ❌ 미실행 + 대기상태 만료 | ✅ |
| 9 | 중복 주문 요청 | ❌ 차단 | 완료·취소 후 |
| 10 | LLM 응답 실패 | ❌ 중단 (조회는 원본 수치 전송) | ✅ |
| 11 | 미등록 사용자 | ❌ 차단 (무응답) | — |

> **11개 중 8개가 주문 흐름의 예외입니다.** 주문이 되돌릴 수 없기 때문입니다. 정상 흐름보다 예외 흐름에 개발 시간이 더 들 것으로 예상합니다.

자세한 내용은 [정상·예외 업무 흐름](../02_Domain/03_workflow.md) 문서를 참고합니다.

## 6. 데이터 소스

데이터가 처음 발생하거나 시스템으로 들어오는 곳입니다.

| 소스 | 제공하는 데이터 |
|---|---|
| 텔레그램 (외부) | 메시지 원문, `chat_id`, 인라인 키보드 선택 |
| LLM (외부) | 의도·종목명·수량 추출 결과, 용어·계좌·시세 해석문 |
| 종목 마스터 (사전 적재) | 종목코드, 종목명, 시장구분 |
| KIS 모의투자 (외부) | 접근토큰, 예수금·보유종목·수익률, 현재가·등락률·거래량, 주문번호·주문결과, 체결 결과 |
| 우리 시스템 (Supabase) | 주문 상태, **판단 근거**, 이벤트 기록 |

### 우리가 새로 만들어내는 데이터는 3가지뿐입니다

| 데이터 | 왜 우리만 만들 수 있는가 |
|---|---|
| 주문 상태 | KIS는 접수 결과만 줍니다. 확인 대기·근거 대기 같은 **대화 단계는 우리만 압니다.** |
| **판단 근거** | 어디에도 존재하지 않던 데이터입니다. **이 프로젝트가 새로 만드는 유일한 가치.** |
| 이벤트 기록 | 성공 기준 측정을 위해 우리가 남깁니다. |

### LLM이 만든 값은 주문 파라미터로 바로 쓰지 않습니다

| 값 | 확정 주체 |
|---|---|
| 종목코드 | 종목 마스터 조회 (LLM 생성 금지 — 없는 코드를 만들 수 있음) |
| 금액·수익률 | 코드 계산 (LLM 계산 금지 — 숫자를 틀릴 수 있음) |
| 수량 | LLM이 추출, **코드가 검증** (음수·0·과도한 수량 차단) |
| 매수·매도 권유 | 생성 금지 (유사투자자문 위험) |

### KIS 장애 시 영향

| 장애 | 영향 |
|---|---|
| 토큰 발급 실패 | **모든 KIS 기능 정지.** 용어 설명(흐름 A)만 동작 |
| 잔고·시세 조회 실패 | 해당 흐름 불가 + 주문도 차단 (예상 금액·예수금 검증 불가) |
| 주문 실패 | 주문만 불가. 조회는 계속 동작 |

> **흐름 A(용어 설명)는 KIS에 의존하지 않습니다.** 발표 당일 KIS 장애가 나도 시연 가능합니다. 시연 순서는 의존성이 낮은 흐름부터 배치합니다.

자세한 내용은 [데이터 소스](../03_Data_Event/02_data_sources.md) 문서를 참고합니다.

## 7. 데이터 유형

| 유형 | 해당 데이터 |
|---|---|
| 기준 정보 | 종목 마스터, 근거 유형 선택지 |
| 거래 정보 | 주문, 체결 |
| 상태 정보 | 주문 상태, 대화 맥락, 토큰 상태 |
| 사건 기록 | 이벤트 로그 (도메인 이벤트 + 운영 로그) |
| 개인정보 | `chat_id`, 계좌번호 |
| **참조 정보** (저장 안 함) | 예수금, 보유종목, 시세 |

### Supabase 테이블 5개

| 테이블 | 역할 |
|---|---|
| `stocks` | 종목 마스터 (종목명 → 종목코드 변환) |
| `orders` | 주문 전 생애주기 (**대기 상태 포함**) |
| `rationales` | 판단 근거 |
| `conversation_context` | 대화 맥락 (`그거` 해석) |
| `event_logs` | 이벤트 기록 |

**잔고·시세는 저장하지 않습니다.** 실시간으로 변하므로 저장하면 곧 틀린 값이 됩니다. 조회 시점에 KIS에서 가져오고, 조회했다는 사실만 이벤트로 남깁니다.

**주문 대기 상태를 별도 테이블로 만들지 않았습니다.** `orders.status`가 전 생애주기를 담습니다. 두 테이블로 나누면 같은 주문이 옮겨 다니며 상태 불일치가 생깁니다.

### 개인정보 취급

| 데이터 | 취급 |
|---|---|
| `chat_id` | DB 저장은 하되 **발표자료·시연 영상·README에는 가립니다.** |
| 계좌번호 | 저장하지 않습니다. n8n Credential 또는 환경변수. 노출 금지. |
| KIS 앱키·시크릿, 봇 토큰, LLM 키 | n8n Credential. 워크플로우 JSON 내보내기 시 포함 여부 확인. |

자세한 내용은 [데이터 구조 초안](../03_Data_Event/01_data_structure.md) 문서를 참고합니다.

## 8. 도메인 이벤트

3교시에서 찾은 이벤트 후보 21개를 성격에 따라 나눴습니다.

| 구분 | 정의 | 개수 |
|---|---|---:|
| **도메인 이벤트** | 주문의 상태를 바꿉니다. 하나라도 빠지면 흐름이 끊깁니다. | 8 |
| **운영 로그** | 상태를 바꾸지 않습니다. 오류 분석과 프롬프트 개선용. | 13 |
| 보안 사건 | 미등록 접근 기록 | 1 |

### 도메인 이벤트 8개

| 이벤트 | 상태 변화 |
|---|---|
| `order_requested` | 없음 → `requested` |
| `order_confirm_asked` | `requested` → `awaiting_confirmation` |
| `order_confirmed` | `awaiting_confirmation` → `awaiting_rationale` |
| `rationale_recorded` | `awaiting_rationale` 유지 → KIS 주문 호출 |
| `order_submitted` | `awaiting_rationale` → `submitted` |
| `order_executed` | `submitted` → `executed` |
| `order_rejected` | 임의 → `rejected` |
| `order_expired` | `awaiting_*` → `expired` |

`rationale_recorded`가 도메인 이벤트인 이유: 이것 없이는 `awaiting_rationale`에서 `submitted`로 넘어갈 수 없고(흐름 차단), 성공 기준을 측정할 데이터도 없습니다(목적 미달).

### 성공 기준 측정에 쓰이는 이벤트

| 측정 항목 | 계산식 |
|---|---|
| 근거 기록률 | `rationale_recorded` ÷ (`order_submitted` + `order_rejected`) |
| `그냥 감` 비율 | `rationales.reason_type = 'gut'` 비율 |
| 용어 재질문 감소 | `term_explained`의 `payload.term` 반복 횟수 |
| 근거 입력 이탈률 | `rationale_skipped` ÷ `order_confirmed` |

> **이 4개를 측정할 수 있어야 발표에서 결과를 보여줄 수 있습니다.** 이벤트를 남기지 않으면 발표에서 "동작합니다"만 말하고 끝납니다.

자세한 내용은 [이벤트 카탈로그](../03_Data_Event/03_event_catalog.md) 문서를 참고합니다.

## 9. 데이터 흐름

### 조회 흐름 (A·B·C)

```
사용자 → 텔레그램 → 발신자 검증 → 의도 분류 → 분기
  ├ ask_term       → LLM 용어 설명
  ├ check_account  → KIS 잔고조회 → LLM 해석
  └ check_quote    → stocks 조회(종목코드) → KIS 시세조회 → LLM 해석 → 대화 맥락 저장
→ 텔레그램 전송 → 이벤트 기록
```

### 주문 흐름 (D) — 4턴

```
1턴  맥락 조회 → 시세·잔고 조회 → 사전 검증 → 주문 행 생성(requested)
2턴  확인 요청(awaiting_confirmation) → 사용자 동의(awaiting_rationale)
3턴  근거 선택지 → 선택 → 메모 → rationales 저장
4턴  주문 서브 호출(order_id 전달) → KIS 주문 → 주문 행 UPDATE(order_no, status) → 결과 안내
```

**주문 행이 KIS 호출보다 먼저 생성됩니다.** 대기 상태를 담아야 하기 때문입니다. 기존 워크플로우는 주문 성공 후 `create`였으므로 `update`로 변경합니다.

**판단 근거가 KIS 호출 앞에 있습니다.** 근거가 저장되기 전에는 주문이 나가지 않습니다.

### 검증 순서 — 싼 것부터

| 순서 | 검증 | 비용 |
|---|---|---|
| 1 | 발신자 | 환경변수 비교 |
| 2 | 의도 | LLM 1회 |
| 3 | 종목 | DB 조회 1회 |
| 4 | 중복 주문 | DB 조회 1회 |
| 5 | 장 시간 | 계산만 |
| 6 | 예수금 | **KIS 호출 2회** |

가장 비싼 예수금 검증이 마지막입니다. 미등록 사용자의 메시지 때문에 KIS를 호출하지 않습니다.

### AI가 하지 않는 것

| 금지 | 대신 누가 하는가 |
|---|---|
| 종목코드 생성 | `stocks` 테이블 조회 |
| 가격·수익률 계산 | 코드 계산 |
| 수량 최종 확정 | LLM이 추출, **코드가 검증** |
| 매수·매도 권유 | 아무도 하지 않음 |
| 수익 예측 | 아무도 하지 않음 |

### 🔴 장애 시 살아남는 흐름 — 발표 시연 순서의 근거

| 장애 | 살아 있는 흐름 |
|---|---|
| KIS 토큰 실패 | A (용어 설명) |
| KIS 잔고 실패 | A, C |
| KIS 시세 실패 | A, B |
| KIS 주문 실패 | A, B, C |
| 장 마감 | A, B, C |
| LLM 또는 Supabase 장애 | 없음 |

**시연 순서**: `용어 설명 → 계좌 진단 → 시세 조회 → 주문`. 의존성이 낮은 순서로 배치하면 뒤에서 터져도 앞은 이미 보여준 상태가 됩니다. 주문부터 보여주다 실패하면 아무것도 못 보여줍니다.

**장 시간 밖에 발표하면 1~3만 라이브, 4는 녹화 영상으로 대체합니다.**

자세한 내용은 [데이터 흐름](../04_Architecture/01_data_flow.md)과 [아키텍처](../04_Architecture/02_architecture.md) 문서를 참고합니다.

## 10. 용어와 네이밍 컨벤션

프로젝트에서 같은 대상을 같은 이름으로 표현하기 위한 공통 규칙입니다.

### 핵심 규칙

- 고유 번호는 뒤에 `_id` (`order_id`, `rationale_id`)
- 여러 단어는 `snake_case` (Supabase가 소문자 기본이므로 `stockCode`는 큰따옴표를 강제함)
- 시각 컬럼은 `_at`으로 끝냄, 참·거짓은 `is_`로 시작
- **이벤트는 과거형** (`order_submitted` ✅ / `submit_order` ❌)
- **상태는 현재형** (`awaiting_confirmation`)
- 합의하지 않은 줄임말 금지 (`qty` ❌ → `quantity` ✅)
- n8n 기본 노드 이름(`HTTP Request1`) 금지 → `<동작> - <대상>` 형식

### 반드시 구분할 이름

| 구분 대상 | 이름 | 섞으면 |
|---|---|---|
| 내부 주문 식별자 / KIS 주문번호 | `order_id` / `kis_order_no` | **조회가 실패합니다** |
| 예상 금액 / 실제 체결 금액 | `expected_amount` / 체결 조회 결과 | 금액 불일치로 혼란 |
| 예수금 / 보유종목 평가금액 | `deposit` / `holding` | 둘 다 "잔고"로 불려 헷갈림 |

자세한 내용은 [용어와 네이밍 컨벤션](../03_Data_Event/04_naming_convention.md) 문서를 참고합니다.

## 11. 산출물 기준

### 프로젝트 진행 방식

**혼합형(Waterfall + Agile)입니다.**

| 미리 고정 | 반복 실험 |
|---|---|
| 5일 기간과 발표일, 프로젝트 목적과 성공 기준, 데이터 구조와 이벤트, 주문 4턴 구조, 개인정보 원칙, 완료 기준 | 의도 분류 프롬프트, 용어 설명 표현, 계좌 진단 문장의 상세도, 근거 선택지 문구 |

버퍼가 물리적으로 0이므로 **구조 변경 비용이 큰 것을 먼저 고정**합니다. 프롬프트 품질만 반복해서 개선합니다.

### MVP 범위 (Must · 약 30h)

- `chat_id` 버그 수정, 토큰 출력 통일, 발신자 검증
- 주문 테이블 확장 + 중복 방지 인덱스, 신규 테이블 생성
- `stocks` 상위 200종목 적재
- **의도 분류** (자연어 → 의도·종목명·수량)
- 종목코드 변환 + 모호성 처리
- 용어·지표 설명 / 계좌 상황 진단 / 시세 조회와 해석
- 사전 검증 (장 시간·예수금·중복 주문)
- 주문 확인 단계
- **판단 근거 입력과 저장**
- 주문 서브 `create` → `update`
- 주문 실패 분기 + 대기 상태 만료
- 이벤트 기록 (도메인 7 + 핵심 운영 3)
- 통합 테스트, **시연 영상 녹화**

### Should (버퍼가 남으면)

| 순위 | 기능 | 예상 |
|---:|---|---:|
| 1 | **대화 맥락 (`그거 10주 사줘`)** | 3h |
| 2 | 매도 주문 | 2h |
| 3 | 전략 유형 후보 제시 | 3h |

### 범위 밖 (Won't now)

- **체결 조회 / `order_executed`** — 성공 기준과 무관하고 기존 워크플로우에 없음
- 실전 계좌, 특정 종목 매수·매도 권유, 수익률 예측
- 자동 매매, 백테스팅, 차트 분석, 뉴스 수집
- 다수 사용자·권한 체계, 텔레그램에서의 운영 기능

### 시간 배분

```
가용 40h (5일 × 8h) = 개발 Must 30h + 문서 검토 3h + 발표 리허설 2h + 버퍼 5h
```

자세한 내용은 [MVP 범위와 기능 우선순위](../05_Scope/01_mvp_scope.md) 문서를 참고합니다.

## 12. 완료 체크리스트

완료 기준은 **다른 사람이 직접 확인할 수 있는 형태**로만 작성했습니다.

### 프로젝트 성공 기준

**주 기준 (정성)**

```
테스트 사용자 2명에게 각 3회 이상 모의 매수를 진행하게 한 뒤,
"왜 이 종목을 골랐습니까?"라고 물었을 때
자신의 판단 근거를 말할 수 있는가.
```

**보조 지표 (정량 참고치)**

| 지표 | 계산 |
|---|---|
| 근거 기록률 | `rationale_recorded` ÷ (`order_submitted` + `order_rejected`) |
| `gut` 비율 | `reason_type = 'gut'` 비율 |
| 근거 입력 이탈률 | `rationale_skipped` ÷ `order_confirmed` |
| 의도 분류 성공률 | 분류 성공 ÷ 전체 메시지 |

> ⚠️ **표본이 작습니다.** 5일간 3명이 만든 데이터는 통계가 아닙니다. 정량 지표는 참고치로만 쓰고, 정성 확인을 주 기준으로 삼습니다. 발표에서 "근거 기록률 100% 달성"이 아니라 **"6건 모두 근거를 기록했습니다"**라고 말합니다.

### 성공 기준으로 사용하지 않는 것

| 항목 | 이유 |
|---|---|
| 모의투자 수익률·수익금 | 시장이 결정합니다. 팀이 통제할 수 없습니다. |
| 승률 | 5일 표본으로는 우연과 구분되지 않습니다. |
| 사용자 수 | 단일 사용자 프로젝트입니다. |

### 핵심 완료 조건 (전체 체크리스트는 별도 문서)

- [ ] **확인에 동의하기 전에 KIS 주문이 호출되지 않습니다.**
- [ ] **근거가 저장되기 전에 KIS 주문이 호출되지 않습니다.**
- [ ] 의도 분류가 테스트 표현 20개 중 18개 이상을 올바르게 분류합니다.
- [ ] 종목명이 모호하면 되묻고 임의로 고르지 않습니다.
- [ ] 장 마감·예수금 부족·중복 주문이 각각 차단되고 안내됩니다.
- [ ] 주문 거부 시에도 `rationales` 행이 보존됩니다.
- [ ] 대기 상태가 10분 후 만료되고, 만료 후 `네`는 주문을 실행하지 않습니다.
- [ ] 조회 응답 30건에 매수·매도 권유 표현이 0건입니다.
- [ ] 토큰 테이블을 비운 상태에서도 용어 설명이 동작합니다.
- [ ] 측정 지표 4개를 각각 SQL 한 번으로 산출할 수 있습니다.
- [ ] 계좌번호·`chat_id`·토큰값이 문서·발표자료·시연 영상에 없습니다.

전체 체크리스트는 [완료 기준과 체크리스트](../05_Scope/02_definition_of_done.md) 문서를 참고합니다.

### 팀 완료의 정의

- [ ] 작업의 완료 기준을 만족합니다.
- [ ] **정상 상황과 실패 상황을 모두 확인했습니다.**
- [ ] 변경한 데이터·이벤트·상태를 관련 문서에 반영했습니다.
- [ ] 문서와 구현이 일치합니다. (다르면 문서를 고칩니다)
- [ ] 개인정보와 자격증명이 노출되지 않습니다.
- [ ] 다른 사람이 같은 방법으로 완료 여부를 확인할 수 있습니다.

> 두 번째 항목이 특히 중요합니다. **예외 흐름 11개 중 8개가 주문 흐름**이므로, 정상 흐름만 확인하고 완료로 판단하면 발표 시연에서 터집니다.

## 프로젝트 위험

> 상세 대응은 7교시 단계에서 작성합니다.

| 위험 | 예상 영향 | 대응 방향 |
|---|---|---|
| **일정 버퍼 0** — 개발 종료 다음 날이 발표일 | 지연 시 복구 불가 | Day 4에 시연 가능 상태 완성, Day 5는 버퍼+발표 준비 |
| **발표 당일 라이브 시연 실패** | 결과를 보여줄 수 없음 | Day 4에 정상·실패 흐름 시연 영상 녹화 |
| **n8n 멀티턴 대화 상태 관리** | `그거 10주 사줘`를 해석 못 해 흐름이 끊김 | 외부 저장소에 대화 맥락 저장 |
| **종목명 → 종목코드 변환 신규 개발** | 흐름 C·D 전체가 막힘 | 종목 마스터를 상위 종목으로 제한해 범위 축소 |
| **주문 확인 없는 오주문** | 되돌릴 수 없는 주문 실행 | 확인 단계·중복 방지를 Must 배치 |
| **AI가 종목 추천으로 읽히는 답변 생성** | 유사투자자문 위험 | 프롬프트에서 종목 권유 금지 |
| **미등록 사용자의 주문 난입** | 발표 시연 방해, 근거 데이터 오염 | `chat_id` 화이트리스트 |
