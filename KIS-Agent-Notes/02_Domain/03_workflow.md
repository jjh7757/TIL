# 정상·예외 업무 흐름

- 작성일: 2026-08-04
- 근거 교안: 3교시

---

## 0. 이 프로젝트의 흐름이 특별한 이유

일반적인 웹 서비스는 화면이 상태를 들고 있습니다. 이 프로젝트는 화면이 없고 **대화가 화면**입니다. 따라서 다음이 다릅니다.

| 웹 서비스 | 이 프로젝트 |
|---|---|
| 화면이 입력값을 붙잡고 있음 | 앞 대화를 저장소에서 꺼내야 함 |
| 사용자가 화면을 보고 다음 버튼을 찾음 | 사용자가 아무 말이나 할 수 있음 (의도 분류 필요) |
| 폼 검증 후 제출 | 확인 단계를 대화로 만들어야 함 |
| 뒤로 가기 가능 | 대화는 되돌릴 수 없음 |

**모든 흐름은 `의도 분류`라는 하나의 관문을 통과합니다.**

```
사용자 메시지
→ 의도 분류 (자연어 → 요청 종류 + 종목명 + 수량 추출)
→ 해당 흐름으로 분기
```

사용자가 슬래시 명령어가 아닌 **자유로운 자연어**를 쓰기로 결정했기 때문에, 의도 분류는 선택 기능이 아니라 **모든 흐름의 필수 관문**입니다.

## 1. 정상 업무 흐름

### 흐름 A. 투자용어 질문

```
1. 사용자가 "PER이 뭐야?"라고 보냅니다.
2. 의도 분류가 `용어 질문`으로 판별하고 용어를 추출합니다.
3. AI가 초보자 언어로 용어를 설명합니다.
4. 설명을 텔레그램으로 전송합니다.
5. 질문한 용어를 기록합니다.
```

> 5번을 빠뜨리면 성공 기준 중 `용어 재질문 감소`를 측정할 수 없습니다.

**사용하는 기존 자산**: LLM 연동 ✅ / 데이터 저장소 ✅

---

### 흐름 B. 내 계좌 상황 진단

```
1. 사용자가 "내 계좌 어때?"라고 보냅니다.
2. 의도 분류가 `계좌 진단`으로 판별합니다.
3. KIS 토큰을 확인합니다. (만료 시 갱신)
4. 모의계좌 잔고조회 서브워크플로우를 호출합니다.
5. 예수금, 보유 종목, 평균단가, 평가금액, 수익률을 받습니다.
6. AI가 숫자를 초보자가 읽을 문장으로 해석합니다.
7. 해석 결과를 전송합니다.
8. 조회 사실을 기록합니다.
```

**6번이 이 프로젝트의 핵심 가치입니다.** 숫자를 그대로 보여주는 것은 KIS 앱도 합니다. `평가손익 -32,000원 / -4.2%`를 "무엇을 의미하고 지금 무엇을 봐야 하는지"로 바꾸는 것이 차별점입니다.

**사용하는 기존 자산**: KIS 토큰 발급/갱신 ✅ / 모의계좌 잔고조회 ✅ / LLM ✅

---

### 흐름 C. 종목 시세 조회와 해석

```
1. 사용자가 "삼성전자 어때?"라고 보냅니다.
2. 의도 분류가 `시세 조회`로 판별하고 종목명 "삼성전자"를 추출합니다.
3. 종목명을 종목코드로 변환합니다. ← ⚠️ 신규 작업
4. KIS 토큰을 확인합니다.
5. 시세조회 서브워크플로우를 호출합니다.
6. 현재가, 등락률, 거래량 등을 받습니다.
7. AI가 지표를 해석하고, 등장한 용어를 함께 설명합니다.
8. 결과를 전송합니다.
9. 조회한 종목을 대화 맥락에 저장합니다. ← 흐름 D에서 "그거"로 참조됨
```

**9번이 멀티턴의 연결 고리입니다.** 이 저장이 없으면 다음 턴의 `그거 10주 사줘`가 동작하지 않습니다.

**사용하는 기존 자산**: KIS 토큰 ✅ / 시세조회 ✅ / LLM ✅ / 저장소 ✅
**신규 작업**: 종목명 → 종목코드 변환

> ⚠️ AI 해석에는 **매수·매도 권유가 포함되지 않아야 합니다.** "지금 사세요"가 아니라 "이 숫자는 이런 의미입니다"까지입니다. 프롬프트에 명시적으로 금지합니다.

---

### 흐름 D. 모의 주문 (핵심 흐름 · 4턴)

이 프로젝트에서 가장 복잡하고, 성공 기준을 측정하는 유일한 흐름입니다.

```
[1턴] 주문 요청
1. 사용자가 "그거 10주 사줘"라고 보냅니다.
2. 의도 분류가 `매수 주문`으로 판별하고 수량 10을 추출합니다.
3. "그거"를 대화 맥락에서 해석합니다. → 삼성전자(005930)
4. 시세를 조회해 예상 주문금액을 계산합니다.
5. 예수금이 충분한지 확인합니다.

[2턴] 확인
6. "삼성전자 10주, 예상 약 OOO원입니다. 진행하시겠습니까?"를 전송합니다.
7. 주문 대기 상태를 저장소에 기록합니다. (종목코드·수량·요청시각)
8. 사용자가 "네"라고 답합니다.

[3턴] 근거 입력
9. 근거 선택지를 인라인 키보드로 제시합니다.
   (저평가 / 실적 개선 / 업황 / 뉴스 / 배당 / 그냥 감)
10. 사용자가 하나를 선택합니다.
11. "추가로 적을 내용이 있으면 보내주세요. 없으면 건너뛰기를 누르세요."
12. 사용자가 메모를 보내거나 건너뜁니다.
13. 판단 근거를 저장합니다.

[4턴] 주문 실행과 결과
14. 모의 매수/매도 주문 서브워크플로우를 호출합니다.
15. 주문 결과를 받습니다.
16. 주문번호와 근거를 연결해 저장합니다.
17. 주문 대기 상태를 해제합니다.
18. "주문이 접수되었습니다. 주문번호 OOO. 기록한 근거: 실적 개선"을 전송합니다.
19. 체결 여부를 확인해 안내합니다.
```

#### 왜 근거를 주문 **전에** 받습니까?

| 시점 | 결과 |
|---|---|
| 주문 **후**에 요청 | 주문이 끝났으므로 사용자가 답하지 않고 이탈합니다. 근거 기록률이 떨어집니다. |
| 주문 **전**에 요청 (채택) | 주문을 완료하려면 근거를 지나가야 합니다. 기록률이 높아지고, **주문 직전에 스스로 이유를 말하게 만들어 판단을 한 번 더 점검**하게 됩니다. |

두 번째 효과가 특히 중요합니다. 근거 입력 단계는 데이터 수집 장치이면서 동시에 **이 프로젝트의 목적 그 자체**입니다.

**사용하는 기존 자산**: 모의 매수/매도 주문 ✅ / 시세조회 ✅ / 잔고조회 ✅ / 저장소 ✅
**신규 작업**: 멀티턴 상태 관리, 확인 단계, 근거 입력 UI, 중복 주문 방지, 주문-근거 연결

## 2. 예외 업무 흐름

교안 3교시의 작성 순서를 따릅니다.

```
무엇이 실패했는가?
→ 현재 상태를 어떻게 유지하거나 변경하는가?
→ 사용자에게 무엇을 안내하는가?
→ 다시 시도할 수 있는가?
→ 어떤 기록을 남기는가?
```

### 2.1 의도 분류 실패

```
사용자가 "음..." 처럼 의도를 알 수 없는 메시지를 보냅니다.
→ 어떤 흐름도 시작하지 않습니다. 상태를 변경하지 않습니다.
→ "이런 것을 도와드릴 수 있습니다: 용어 설명 / 내 계좌 / 종목 시세 / 매수·매도" 를 안내합니다.
→ 다시 입력할 수 있습니다.
→ intent_classification_failed 이벤트를 원문과 함께 기록합니다.
```

> 원문을 남기는 이유: 어떤 표현이 분류에 실패하는지 모아야 프롬프트를 개선할 수 있습니다.

### 2.2 종목명이 모호함

```
사용자가 "삼성전자 사줘"라고 보냅니다.
→ 종목명 조회 결과가 2건 이상입니다. (삼성전자 / 삼성전자우)
→ 주문을 진행하지 않습니다. 임의로 하나를 고르지 않습니다.
→ "어느 종목입니까? 1) 삼성전자(005930) 2) 삼성전자우(005935)" 를 제시합니다.
→ 사용자가 선택하면 흐름을 이어갑니다.
→ stock_ambiguous 이벤트를 기록합니다.
```

> **임의 선택은 금지입니다.** 주문은 되돌릴 수 없으므로 시스템이 종목을 추측하면 안 됩니다.

### 2.3 종목명을 찾을 수 없음

```
사용자가 존재하지 않거나 지원 목록에 없는 종목명을 말합니다.
→ 주문을 진행하지 않습니다.
→ "해당 종목을 찾을 수 없습니다. 정확한 종목명이나 종목코드로 다시 알려주세요." 를 안내합니다.
→ 다시 입력할 수 있습니다.
→ stock_resolution_failed 이벤트를 입력값과 함께 기록합니다.
```

### 2.4 KIS 토큰 만료

```
KIS API 호출이 인증 오류를 반환합니다.
→ 토큰 발급/갱신 서브워크플로우를 호출해 재발급합니다.
→ 재발급에 성공하면 원래 요청을 1회 재시도합니다. 사용자에게는 알리지 않습니다.
→ 재발급에 실패하면 "잠시 후 다시 시도해주세요." 를 안내합니다.
→ token_refreshed 또는 token_refresh_failed 이벤트를 기록합니다.
```

### 2.5 장 운영시간이 아님

```
사용자가 장 마감 후 또는 휴장일에 주문을 요청합니다.
→ 주문을 접수하지 않습니다. 주문 대기 상태를 만들지 않습니다.
→ "지금은 장 운영시간이 아닙니다. 평일 09:00~15:30에 주문할 수 있습니다.
   대신 종목 정보와 계좌 상황은 지금도 확인할 수 있습니다." 를 안내합니다.
→ 장이 열리면 다시 시도할 수 있습니다.
→ order_rejected_market_closed 이벤트를 기록합니다.
```

> 조회 흐름(A·B·C)은 장 시간 밖에도 동작해야 합니다. **주문만 막습니다.** 발표가 장 시간 밖에 잡힐 경우 조회 흐름은 라이브 시연이 가능합니다.

### 2.6 예수금 부족

```
예상 주문금액이 예수금을 초과합니다.
→ 주문을 접수하지 않습니다. 확인 단계로 넘어가지 않습니다.
→ "예수금이 부족합니다. 현재 예수금 OOO원, 필요 금액 OOO원.
   수량을 줄이거나 다른 종목을 선택해주세요." 를 안내합니다.
→ 수량을 바꿔 다시 시도할 수 있습니다.
→ order_rejected_insufficient_funds 이벤트를 기록합니다.
```

### 2.7 KIS가 주문을 거부함

```
주문 API가 실패 응답을 반환합니다.
→ 주문 상태를 접수 완료로 변경하지 않습니다.
→ 이미 저장한 판단 근거는 삭제하지 않고 `주문 실패`로 표시해 남깁니다.
→ "주문이 거부되었습니다. 사유: OOO. 다시 시도하시겠습니까?" 를 안내합니다.
→ 다시 시도할 수 있습니다.
→ order_rejected 이벤트를 거부 사유와 함께 기록합니다.
```

> 근거를 삭제하지 않는 이유: 실패한 주문의 근거도 **사용자가 근거를 만들었다는 사실**은 유효합니다. 성공 기준 측정에 포함시킬 수 있습니다.

### 2.8 근거 입력 중 사용자가 이탈함

```
확인까지 진행한 뒤 근거를 입력하지 않고 대화를 멈춥니다.
→ 주문을 실행하지 않습니다.
→ 일정 시간이 지나면 주문 대기 상태를 만료시킵니다.
→ 다음 메시지가 오면 "이전 주문 요청은 만료되었습니다. 새로 요청해주세요." 를 안내합니다.
→ order_expired 와 rationale_skipped 이벤트를 기록합니다.
```

> **만료 처리가 없으면 위험합니다.** 대기 상태가 남아 있으면 며칠 뒤 사용자가 보낸 "네"가 옛 주문을 실행할 수 있습니다.

### 2.9 중복 주문 요청

```
주문 대기 상태가 이미 있는데 새 주문을 요청합니다.
→ 새 주문을 만들지 않습니다.
→ "진행 중인 주문 요청이 있습니다: 삼성전자 10주.
   먼저 완료하거나 취소해주세요." 를 안내합니다.
→ 취소하거나 완료한 뒤 다시 시도할 수 있습니다.
→ duplicate_order_blocked 이벤트를 기록합니다.
```

### 2.10 LLM 응답 실패

```
LLM 호출이 실패하거나 시간을 초과합니다.
→ 흐름을 중단합니다. 조회한 원본 데이터는 유지합니다.
→ 조회 흐름이면 AI 해석 없이 원본 수치라도 전송합니다.
→ 주문 흐름이면 "설명을 준비하지 못했습니다. 다시 시도해주세요." 를 안내하고 주문은 진행하지 않습니다.
→ 다시 시도할 수 있습니다.
→ llm_call_failed 이벤트를 기록합니다.
```

> 조회 흐름에서 원본 수치라도 보내는 이유: 사용자가 아무것도 못 받는 것보다 낫고, **발표 시연 중 LLM이 실패해도 화면에 무언가는 나옵니다.**

### 2.11 등록되지 않은 사용자

```
화이트리스트에 없는 chat_id에서 메시지가 옵니다.
→ 어떤 흐름도 시작하지 않습니다.
→ 응답하지 않습니다. (봇의 존재를 확인시켜 주지 않습니다)
→ unauthorized_access_blocked 이벤트를 chat_id와 함께 기록합니다.
```

## 3. 예외 흐름 요약

| # | 예외 상황 | 주문 진행 | 사용자 안내 | 재시도 |
|---|---|---|---|---|
| 2.1 | 의도 분류 실패 | — | 가능한 기능 목록 | ✅ |
| 2.2 | 종목명 모호 | ❌ 중단 | 후보 목록 제시 | ✅ |
| 2.3 | 종목명 없음 | ❌ 중단 | 다시 입력 요청 | ✅ |
| 2.4 | 토큰 만료 | 자동 복구 | 안내 없음 (무음 재시도) | 자동 |
| 2.5 | 장 마감 | ❌ 차단 | 운영시간 안내 + 조회는 가능 | 장 개시 후 |
| 2.6 | 예수금 부족 | ❌ 차단 | 잔액과 필요 금액 | ✅ |
| 2.7 | 주문 거부 | ❌ 실패 | 거부 사유 | ✅ |
| 2.8 | 근거 입력 이탈 | ❌ 미실행 | 만료 안내 | ✅ |

## 4. 상태와 이벤트 (초안)

교안 3교시에서는 흐름 안에 어떤 상태와 사건이 필요한지만 찾습니다. 정식 정의는 4교시 단계에서 작성합니다.

### 주문 상태 흐름

```
requested
→ awaiting_confirmation
→ awaiting_rationale
→ submitted
→ executed
```

실패·종료 상태:

```
rejected
expired
cancelled
```

```
intent_classified / intent_classification_failed

term_explained
account_diagnosed
quote_retrieved
order_requested / order_confirmed / order_submitted / order_executed / order_rejected / order_expired
rationale_recorded / rationale_skipped
token_refreshed / token_refresh_failed
llm_call_failed

```
