# MVP 범위와 기능 우선순위

- 작성일: 2026-08-04
- 근거 교안: 6교시

---

## 1. 프로젝트 진행 방식

**혼합형(Waterfall + Agile)입니다.**

| 미리 고정할 것 | 반복해서 실험할 것 |
|---|---|
| 5일 기간과 발표일 | 의도 분류 프롬프트 |
| 프로젝트 목적과 성공 기준 | 용어 설명의 표현 방식 |
| 데이터 구조와 이벤트 정의 | 계좌 진단 문장의 상세도 |
| 주문 흐름의 4턴 구조 | 근거 선택지 문구 |
| 개인정보·자격증명 원칙 | |
| 필수 산출물과 완료 기준 | |

### 왜 혼합형입니까?

기간이 5일이고 **버퍼가 물리적으로 0**입니다(개발 종료 다음 날이 발표일). 따라서 구조를 반복해서 바꿀 여유가 없습니다. 데이터 구조와 흐름은 **Waterfall처럼 먼저 확정**합니다.

반면 프롬프트의 품질은 한 번에 맞출 수 없습니다. `PER이 뭐야?`에 어떤 깊이로 답할지는 실제로 돌려보고 고쳐야 합니다. 이 부분만 **Agile처럼 반복**합니다.

> 교안 7장의 변경 비용 개념을 적용한 판단입니다. **구조 변경 비용은 크고 프롬프트 변경 비용은 작습니다.** 비용이 큰 것을 먼저 고정합니다.

---

## 2. 핵심 가정

```
투자용어와 계좌 상황을 초보자 언어로 설명해주고,
주문 직전에 판단 근거를 적게 하면
사용자가 자신의 매매 판단을 설명할 수 있게 될 것입니다.
```

이것은 **가정이며 아직 검증되지 않았습니다.** MVP의 목적은 이 가정을 확인하는 것입니다.

---

## 3. MVP 사용자 흐름

```
용어 질문 → 설명 확인
→ 내 계좌 상황 확인
→ 종목 시세 확인과 해석
→ 매수 요청
→ 주문 확인
→ 판단 근거 입력
→ 주문 접수 결과 확인
```

**이 흐름이 끝까지 이어지는 것이 MVP의 정의입니다.** 중간에 끊기면 성공 기준을 측정할 수 없습니다.

## 4. MoSCoW 우선순위

### 4.1 Must Have — 약 30h

| # | 기능·작업 | 예상 | 선택 이유 |
|---:|---|---:|---|
| 1 | `chat_id` 표현식 버그 수정 | 0.1h | 이걸 안 고치면 중복 방지·맥락·측정이 전부 무효 |
| 2 | 토큰 워크플로우 출력 통일 + 유효기간 여유 10분 | 0.5h | 토큰 만료 순간에 터짐. **발표 당일 아침에 처음 드러날 수 있음** |
| 3 | 발신자 검증 (`chat_id` 화이트리스트) | 0.5h | 봇은 누구나 찾음 + 주문은 비가역. 시연 난입·데이터 오염 방지 |
| 4 | 주문 테이블 컬럼 6개 추가 + 부분 유니크 인덱스 | 0.5h | `status` 없이는 대기 상태를 담을 수 없음 |
| 5 | 신규 테이블 3개 생성 | 0.5h | `rationales`, `event_logs`, (`conversation_context`는 Should) |
| 6 | `stocks` 테이블 + 상위 200종목 적재 | 2h | **없으면 흐름 C·D가 전부 막힘.** 사용자는 종목명으로 말함 |
| 7 | **의도 분류** (LLM 구조화 추출 + 라우팅) | 4h | 자연어를 쓰기로 했으므로 모든 흐름의 필수 관문 |
| 8 | 종목코드 변환 + 모호성 처리 | 2h | `삼성전자` vs `삼성전자우`. **임의 선택 금지** |
| 9 | 용어·지표 설명 | 2h | 문제 정의 직결. **KIS에 의존하지 않는 유일한 흐름 = 시연 안전판** |
| 10 | 내 계좌 상황 진단 | 2h | 문제 정의 직결. 계좌 화면을 해석 못하는 문제 해결 |
| 11 | 종목 시세 조회와 해석 | 1.5h | 주문 전 판단에 필요. `expected_price` 확보 |
| 12 | 사전 검증 (장 시간·예수금·중복 주문) | 2h | 주문은 되돌릴 수 없음 |
| 13 | 주문 확인 단계 | 2h | **의도 오분류의 최종 방어선.** 생략하면 방어선이 사라짐 |
| 14 | **판단 근거 입력** (인라인 키보드 + 저장) | 3h | **성공 기준을 측정하는 유일한 수단** |
| 15 | 주문 서브 `create` → `update` + `order_id` 파라미터 | 1h | 거부된 주문도 기록되어야 측정 분모가 채워짐 |
| 16 | 주문 실패 분기 + 대기 상태 만료 정리 | 1.5h | 만료가 없으면 며칠 뒤 `네`가 옛 주문을 실행함 |
| 17 | 이벤트 기록 (도메인 7 + 핵심 운영 3) | 2h | 없으면 발표에서 "동작합니다"만 말하고 끝 |
| 18 | 통합 테스트 (정상 + 실패 흐름) | 3h | |
| 19 | **시연 영상 녹화** (정상 + 실패) | 0.5h | 발표 당일 장 시간 밖이거나 API 장애 시 대체 |
| | **합계** | **약 30h** | |

### 4.2 Should Have

| 기능 | 예상 | 왜 Must가 아닌가 |
|---|---:|---|
| **대화 맥락 (`그거 10주 사줘`)** | 3h | 사용자가 매번 종목명을 말하면 동작합니다. `그거`는 편의 기능입니다. 확인 단계의 `네`는 `orders.status`가 담당하므로 이 테이블 없이도 주문 흐름이 완성됩니다. |
| 매도 주문 | 2h | 근거 선택지를 매수용/매도용으로 나눠야 하고(손절·차익실현은 매수 근거와 다름) 보유 수량 검증도 별도입니다. **매수만으로 성공 기준을 측정할 수 있습니다.** |
| 전략 유형 후보 제시 | 3h | 문제 정의의 "어떤 전략을 써야 하는지 모른다"에 대응하지만, 용어·계좌 설명만으로도 판단 근거는 형성됩니다. |

> 🔴 **`대화 맥락`은 Should 중 1순위입니다.** Day 4에 버퍼가 남으면 가장 먼저 추가합니다. 발표 시연에서 `그거 10주 사줘`가 가장 인상적인 순간이기 때문입니다. 다만 **발표 효과를 위해 Must로 올리지는 않습니다** — MVP는 인상이 아니라 가정 검증으로 정의합니다.

### 4.3 Could Have

| 기능 | 예상 |
|---|---:|
| 종목 마스터를 전체 상장 종목으로 확대 | 2h |
| 운영 로그 이벤트 나머지 10개 | 1h |
| 근거 입력 시 과거 유사 근거 보여주기 | 3h |

### 4.4 Won't Have (이번에는 하지 않음)

| 기능 | 제외 이유 |
|---|---|
| **체결 조회 / `order_executed`** | 성공 기준은 체결과 무관합니다. 기존 워크플로우에 없으므로 +3h이고 버퍼가 얇습니다. 발표에서 "주문 접수까지"라고 명시합니다. |
| 실전 투자 계좌 | 실제 자금 위험. 목적과 무관 |
| 특정 종목 매수·매도 권유 | 유사투자자문 영역 |
| 수익률 예측·목표 수익률 | 검증 불가하고 목적과 무관 |
| 자동 매매·알고리즘 트레이딩 | 범위가 큼 |
| 다수 사용자·권한 체계 | KIS 계좌가 1개. 여러 사용자를 받으면 모두 같은 계좌로 주문 |
| 백테스팅 | 별도 프로젝트 규모 |
| 차트 이미지·기술적 분석 자동화 | 5일에 들어가지 않음 |
| 뉴스·공시 실시간 수집 | 외부 데이터 수집 범위가 큼 |
| 텔레그램에서의 운영 기능 | 투자자 역할과 운영자 역할을 분리 |

## 5. 시간 배분

```
사용자 가용 시간      40h  (5일 × 8h)
─────────────────────────
개발 Must            -30h
기획 문서 검토         -3h   (문서는 Claude가 작성, 사용자는 검토만)
발표 리허설            -2h
─────────────────────────
남는 버퍼             약 5h
```

### 🔴 버퍼가 5시간뿐인 이유

개발 종료 다음 날이 발표일이므로 **예비 날짜가 없습니다.** 교안 10장(7교시)은 일정 버퍼를 필수로 봅니다.

**대응: 버퍼를 날짜가 아니라 기능에서 확보합니다.**

```
Day 4 종료 시점에 이미 시연 가능한 상태를 완성한다
→ Day 5는 통째로 버퍼 + 발표 준비
```

Must 기능을 Day 1~4에 몰아넣는 배치입니다. 상세 일정은 [마일스톤](../06_WBS/02_milestones.md) 문서에서 작성합니다.

## 6. Scope Creep 방어

새로운 기능이 떠올랐을 때 아래 3가지를 모두 만족하지 않으면 **Could 또는 Won't now로 보냅니다.**

```
1. 이 기능이 없으면 핵심 가정을 검증할 수 없는가?
2. 이 기능이 없으면 MVP 사용자 흐름이 끊기는가?
3. Must 합계가 30h를 넘지 않는가?
```

**5일 프로젝트에서 가장 흔한 실패는 기능 부족이 아니라 미완성입니다.** 기능 8개가 90% 완성된 것보다 기능 5개가 100% 완성된 것이 발표에서 낫습니다.

### 이번 프로젝트에서 특히 유혹적일 기능

| 유혹 | 왜 참아야 하는가 |
|---|---|
| 차트 이미지 생성 | 시각적으로 화려하지만 판단 근거와 무관합니다 |
| 종목 추천 | 가장 그럴듯해 보이지만 **유사투자자문 위험**이고 프로젝트 목적과 반대 방향입니다 |
| 실시간 알림 | 스케줄러·상태 관리가 늘어납니다 |
| 여러 종목 비교 | 대화 UI에서 표현이 어렵고 흐름이 복잡해집니다 |

## 7. 아직 검증할 내용

| 검증할 질문 | 방법 | 5일 내 |
|---|---|---|
| 초보 투자자가 매매를 못 하는 주된 이유가 용어인가? | 초보 투자자 3명 질문 | ✅ |
| 용어·계좌 설명이 근거를 말할 수 있게 만드는가? | 테스트 사용자 2명에게 각 3회 매매 후 "왜 샀는지 설명해보세요" | ✅ |
| 주문 전 근거 입력이 이탈을 유발하는가? | `rationale_skipped` ÷ `order_confirmed` 확인 | ✅ |
| 근거 선택지 6개가 적절한가? | `gut` 선택 비율 확인 | ✅ |
| 의도 분류가 실제 표현을 얼마나 잡는가? | `intent_classification_failed` 원문 검토 | ✅ |

> ⚠️ **표본이 작다는 것을 인정합니다.** 5일 동안 본인과 테스트 사용자 2명이 쓴 데이터는 통계가 되지 않습니다. 정량 지표는 참고치로 쓰고, **정성 확인(설명할 수 있는지 직접 물어보기)을 주된 검증 방법으로 삼습니다.** 발표에서도 이렇게 말합니다.
