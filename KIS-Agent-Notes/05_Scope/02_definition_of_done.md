## 0. 좋은 완료 기준의 조건

교안 6교시 14장의 요구: **다른 사람이 완료 여부를 직접 확인할 수 있어야 합니다.**

| 나쁜 완료 기준 | 왜 나쁜가 | 좋은 완료 기준 |
|---|---|---|
| 의도 분류가 잘 동작한다 | "잘"의 기준이 없습니다 | 준비한 표현 20개 중 18개 이상을 올바른 의도로 분류합니다 |
| 용어 설명이 이해하기 쉽다 | 확인 방법이 없습니다 | 초보자 3명이 설명을 읽고 용어를 자기 말로 다시 설명할 수 있습니다 |
| 주문이 안정적으로 처리된다 | "안정적"이 측정 불가 | 예수금 부족·장 마감·중복 요청 각각에서 주문이 접수되지 않고 안내가 표시됩니다 |
| 수익이 난다 | **팀이 통제할 수 없습니다** | (성공 기준으로 사용하지 않습니다) |

## 1. 기능별 완료 기준

### 1.1 기반

| 기능 | 완료 기준 |
|---|---|
| `chat_id` 저장 | 새로 생성된 주문 행의 `chat_id`에 숫자 형태의 실제 값이 들어 있습니다. `$(`로 시작하는 문자열이 없습니다. |
| 발신자 검증 | 등록되지 않은 계정에서 메시지를 보내면 응답이 없고, `event_logs`에 `unauthorized_access_blocked` 행이 생깁니다. |
| 토큰 출력 통일 | 토큰 테이블의 만료시각을 과거로 바꾼 뒤 호출해도, 그리고 유효한 상태로 호출해도 **같은 필드명으로 토큰을 받습니다.** |
| 종목 마스터 | `stocks` 테이블에 200행 이상이 있고 `stock_name`으로 조회하면 `stock_code`가 반환됩니다. |
| 주문 테이블 확장 | `status`, `expected_price`, `expected_amount`, `reject_reason`, `expires_at`, `updated_at` 컬럼이 존재합니다. |
| 중복 방지 인덱스 | 진행 중 주문이 있는 상태에서 새 주문 행을 INSERT하면 DB가 거부합니다. |

### 1.2 의도 분류와 종목 해석

| 기능 | 완료 기준 |
|---|---|
| 의도 분류 | 미리 준비한 테스트 표현 20개 중 **18개 이상**을 올바른 의도로 분류합니다. |
| 판별 불가 처리 | `음...` 같은 메시지에 가능한 기능 목록이 안내되고, `intent_classification_failed`가 원문과 함께 기록됩니다. |
| 종목코드 변환 | `삼성전자`를 입력하면 `005930`으로 변환됩니다. |
| 종목명 모호 | `삼성전자`가 `삼성전자`·`삼성전자우` 두 건으로 조회되면 **후보 목록이 제시되고 주문이 진행되지 않습니다.** |
| 종목명 없음 | 목록에 없는 종목명을 입력하면 안내가 표시되고 주문이 진행되지 않습니다. |

### 1.3 조회 흐름

| 기능 | 완료 기준 |
|---|---|
| 용어 설명 | `PER이 뭐야?`에 초보자 대상 설명이 표시되고 `term_explained`가 기록됩니다. |
| 용어 설명 품질 | 초보자 3명이 설명을 읽고 해당 용어를 **자기 말로 다시 설명할 수 있습니다.** |
| 계좌 진단 | `내 계좌 어때?`에 예수금·보유 종목·수익률이 **숫자 나열이 아닌 해석 문장**으로 표시됩니다. |
| 시세 조회 | 종목명을 말하면 현재가·등락률이 표시되고, 등장한 지표의 의미가 함께 설명됩니다. |
| 권유 금지 | 조회 응답 30건을 검토했을 때 `지금 사세요`, `매수 추천` 류의 표현이 **0건**입니다. |
| KIS 독립성 | 토큰 테이블을 비운 상태에서도 **용어 설명은 정상 동작합니다.** |

### 1.4 주문 흐름

| 기능 | 완료 기준 |
|---|---|
| 주문 요청 | 종목명과 수량을 말하면 예상 금액이 계산되고 주문 행이 `requested`로 생성됩니다. |
| 장 마감 차단 | 장 시간 밖에 주문을 요청하면 주문이 접수되지 않고 운영시간이 안내됩니다. **조회 기능은 계속 동작합니다.** |
| 예수금 부족 차단 | 예수금을 초과하는 주문을 요청하면 현재 예수금과 필요 금액이 안내되고 주문이 접수되지 않습니다. |
| 중복 주문 차단 | 진행 중 주문이 있는 상태에서 새 주문을 요청하면 기존 주문이 안내되고 새 주문이 만들어지지 않습니다. |
| 확인 단계 | 확인에 동의하기 전에는 KIS 주문 API가 호출되지 않습니다. (n8n Executions에서 확인) |
| 취소 | 확인 단계에서 거부하면 주문 상태가 `cancelled`가 되고 KIS가 호출되지 않습니다. |
| 근거 입력 | 확인 후 근거 선택지 6개가 인라인 키보드로 표시됩니다. |
| 근거 저장 | 선택한 근거가 `rationales`에 저장되고 `order_id`로 주문과 연결됩니다. |
| 근거 필수성 | **근거가 저장되기 전에는 KIS 주문 API가 호출되지 않습니다.** |
| 메모 건너뛰기 | 메모를 건너뛰어도 주문이 정상 진행되고 `reason_memo`가 비어 있습니다. |
| 주문 접수 | KIS가 주문을 접수하면 주문번호가 안내되고 `status`가 `submitted`, `order_no`가 채워집니다. |
| 주문 거부 | KIS가 거부하면 사유가 안내되고 `status`가 `rejected`, `reject_reason`이 채워집니다. **`rationales` 행은 삭제되지 않습니다.** |
| 대기 만료 | 근거 입력 없이 10분 이상 지난 뒤 메시지를 보내면 만료가 안내되고 `status`가 `expired`입니다. |
| 만료 후 오작동 방지 | 만료된 주문이 있는 상태에서 `네`를 보내도 **주문이 실행되지 않습니다.** |

### 1.5 이벤트와 측정

| 기능 | 완료 기준 |
|---|---|
| 도메인 이벤트 | 정상 주문 1건을 완료하면 `event_logs`에 `order_requested`, `order_confirm_asked`, `order_confirmed`, `rationale_recorded`, `order_submitted`가 모두 기록됩니다. |
| 측정 가능성 | 아래 4개 지표를 **SQL 한 번으로 각각 산출할 수 있습니다.** |

```sql
-- 근거 기록률
-- gut 비율
-- 용어 재질문 횟수
-- 근거 입력 이탈률
```

### 1.6 문서와 발표

| 산출물 | 완료 기준 |
|---|---|
| 프로젝트 기준선 | 12개 항목이 모두 작성되어 있고 `추후 작성`이 남아 있지 않습니다. |
| 문서 연결 | Obsidian에서 기준선의 링크를 눌러 모든 하위 문서로 이동할 수 있습니다. |
| README | 프로젝트 소개·문제·범위·아키텍처·개발 계획이 작성되어 있습니다. |
| 발표자료 | 슬라이드 6장과 발표자 노트가 작성되어 있고 **2분 안에 읽을 수 있습니다.** |
| 시연 영상 | 정상 흐름과 실패 흐름이 녹화되어 있고 **계좌번호·`chat_id`·토큰값이 보이지 않습니다.** |

## 2. 완료 체크리스트

### 프로젝트 목적과 범위

- [ ] 핵심 사용자와 해결하려는 문제가 작성되어 있습니다.
- [ ] 성공 기준이 기간 내 확인 가능한 형태로 작성되어 있습니다.
- [ ] 이번에 만들 기능과 만들지 않을 기능이 구분되어 있습니다.
- [ ] Must·Should·Could·Won't now가 구분되어 있습니다.
- [ ] 사실과 가정이 구분되어 있고 미검증 가정이 명시되어 있습니다.

### 기반

- [ ] `chat_id`에 실제 값이 저장됩니다.
- [ ] 등록되지 않은 사용자의 메시지가 무시됩니다.
- [ ] 토큰이 유효한 경우와 만료된 경우 모두 같은 형태로 반환됩니다.
- [ ] `stocks` 테이블에 200종목 이상이 적재되어 있습니다.
- [ ] 주문 테이블에 상태 관리용 컬럼이 추가되어 있습니다.
- [ ] 중복 주문이 DB 수준에서 차단됩니다.

### 조회 흐름

- [ ] 자연어로 용어를 물으면 초보자 수준의 설명이 표시됩니다.
- [ ] 자연어로 계좌를 물으면 해석 문장이 표시됩니다.
- [ ] 종목명으로 시세를 물으면 현재가와 해석이 표시됩니다.
- [ ] 응답에 매수·매도 권유 표현이 없습니다.
- [ ] 종목명이 모호하면 되묻고 임의로 고르지 않습니다.
- [ ] 의도를 판별하지 못하면 가능한 기능이 안내됩니다.

### 주문 흐름

- [ ] 확인에 동의하기 전에 KIS 주문이 호출되지 않습니다.
- [ ] 근거가 저장되기 전에 KIS 주문이 호출되지 않습니다.
- [ ] 근거 선택지가 인라인 키보드로 표시됩니다.
- [ ] 메모를 건너뛰어도 주문이 진행됩니다.
- [ ] 장 시간 밖에는 주문이 차단되고 조회는 동작합니다.
- [ ] 예수금 부족 시 주문이 차단되고 금액이 안내됩니다.
- [ ] 진행 중 주문이 있으면 새 주문이 차단됩니다.
- [ ] 주문 거부 시 사유가 안내되고 근거는 보존됩니다.
- [ ] 대기 상태가 10분 후 만료되고, 만료 후 `네`는 주문을 실행하지 않습니다.

### 측정

- [ ] 정상 주문 1건에서 도메인 이벤트 5개가 모두 기록됩니다.
- [ ] 근거 기록률을 SQL로 산출할 수 있습니다.
- [ ] `gut` 비율을 SQL로 산출할 수 있습니다.
- [ ] 용어 재질문 횟수를 SQL로 산출할 수 있습니다.
- [ ] 근거 입력 이탈률을 SQL로 산출할 수 있습니다.

## 3. 팀 완료의 정의

혼자 하는 프로젝트이지만 **모든 작업에 공통으로 적용할 기준**입니다.

- [ ] 작업의 완료 기준을 만족합니다.
- [ ] **정상 상황과 실패 상황을 모두 확인했습니다.**
- [ ] 변경한 데이터·이벤트·상태를 관련 문서에 반영했습니다.
- [ ] 문서와 구현이 일치합니다. (다르면 문서를 고칩니다)
- [ ] 개인정보와 자격증명이 화면·문서·로그에 노출되지 않습니다.
- [ ] 다른 사람이 같은 방법으로 완료 여부를 확인할 수 있습니다.

> 두 번째 항목이 이 프로젝트에서 특히 중요합니다. **예외 흐름 11개 중 8개가 주문 흐름**이므로, 정상 흐름만 확인하고 완료로 판단하면 발표 시연에서 터집니다.

## 4. 프로젝트 성공 기준

### 4.1 주 기준 — 정성 확인

```
테스트 사용자 2명에게 각각 3회 이상 모의 매수를 진행하게 한 뒤,
"왜 이 종목을 골랐습니까?"라고 물었을 때
자신의 판단 근거를 말할 수 있는가.
```

**이것이 주된 성공 기준입니다.** 확인 방법이 명확하고 5일 안에 실행 가능합니다.

### 4.2 보조 지표 — 정량 참고치

| 지표 | 계산 | 참고 목표 |
|---|---|---|
| 근거 기록률 | `rationale_recorded` ÷ (`order_submitted` + `order_rejected`) | 구조상 100%에 가까워야 정상 |
| `gut` 비율 | `reason_type = 'gut'` 비율 | 낮을수록 좋음 |
| 근거 입력 이탈률 | `rationale_skipped` ÷ `order_confirmed` | 낮을수록 좋음 |
| 용어 재질문 | 같은 `term`의 반복 횟수 | 줄어들수록 좋음 |
| 의도 분류 성공률 | 분류 성공 ÷ 전체 메시지 | 90% 이상 |

### 4.3 ⚠️ 표본이 작다는 것을 인정합니다

5일 동안 본인과 테스트 사용자 2명이 만든 데이터는 **통계적으로 유의미하지 않습니다.**

| 정직하게 말할 것 | 말하지 말 것 |
|---|---|
| "테스트 사용자 2명이 각 3회 매매했고, 6건 모두 근거를 기록했습니다." | "근거 기록률 100%를 달성했습니다." (표본 6건) |
| "`그냥 감` 선택이 6건 중 1건이었습니다." | "감에 의존한 매매를 83% 줄였습니다." |
| "이 방향이 가능해 보이지만 더 많은 사용자로 확인이 필요합니다." | "가정이 검증되었습니다." |

**발표에서 이렇게 말하는 것이 감점 요인이 아닙니다.** 표본 6건으로 "검증 완료"를 주장하는 것이 감점 요인입니다. 교안 4.4가 요구하는 것은 가정을 감추지 않는 태도입니다.

### 4.4 성공 기준으로 사용하지 않는 것

| 항목 | 이유 |
|---|---|
| 모의투자 수익률 | 시장이 결정합니다. 팀이 통제할 수 없습니다. |
| 누적 수익금 | 동일 |
| 승률 | 5일 표본으로는 우연과 구분되지 않습니다. |
| 사용자 수 | 단일 사용자 프로젝트입니다. |
