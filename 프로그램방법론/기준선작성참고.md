# 기준선 작성 참고

[기준선 작성](기준선작성.md)에서 사용한 핵심 개념을 정리한 참고 자료입니다. 예시는 모두 특강 공통 실습 프로젝트인 "오늘 뭐 먹지? AI 배달 메뉴 추천 및 주문 서비스" 기준입니다.

## 1. 도메인, 사용자 역할, 업무 흐름

### 도메인이란
- 프로젝트가 다루는 실제 업무와 문제의 범위

```text
누가 참여하는가?
→ 무엇을 처리하는가?
→ 어떤 순서로 일이 진행되는가?
→ 어떤 규칙과 예외가 있는가?
```

도메인이 아닌 것과 도메인에 해당하는 것을 구분하면 이해하기 쉽다.

| 구분 | 예시 |
|---|---|
| 도메인이 아닌 것 | React, Python, AI, 로그인 화면, 추천 버튼 |
| 도메인에 해당하는 것 | 고객이 메뉴를 선택하는 업무, 음식점이 주문을 접수하는 업무, 결제가 성공하거나 실패하는 과정, 배달원이 음식을 전달하는 과정 |

### 도메인 요소란
- 서비스 안에서 관리하거나 처리해야 하는 핵심 요소

| 구분 | 의미 | 예시 |
|------|------|------------------------|
| 사람·역할 | 서비스를 사용하거나 업무를 수행하는 주체 | 고객, 음식점 운영자, 배달원, 관리자 |
| 핵심 대상 | 정보를 저장하고 관리해야 하는 대상 | 메뉴, 장바구니, 주문, 결제, 배달 |
| 행동 | 사람이나 시스템이 수행하는 일 | 검색, 추천, 주문, 결제, 주문 수락 |
| 규칙 | 반드시 지켜야 하는 업무 조건 | 결제가 완료된 주문만 음식점에 전달 |
| 상태 | 대상이 현재 어느 단계에 있는지 나타내는 값 | 결제 대기, 조리 중, 배달 중, 완료 |
| 이벤트 | 업무에서 중요한 변화가 발생한 순간 | 주문 생성, 결제 실패, 배달 완료 |

엔티티(Entity)는 이 중에서도 고유 번호(`_id`)로 구분해서 저장해야 하는 핵심 대상이다. (예: `order_id`, `menu_id`)

### 도메인 요소가 개발로 연결되는 과정
도메인 요소는 단어를 찾는 것으로 끝나지 않고, 다음 순서로 개발과 연결된다.

```text
도메인 요소
→ 필요한 정보
→ 화면과 기능
→ API와 코드
→ 이벤트와 테스트
→ 개발 작업
```

예를 들어 `주문`이라는 도메인 요소는 다음 내용까지 함께 정해야 한다.

| 연결 대상 | 주문에서 필요한 내용 |
|---|---|
| 데이터 | 주문 번호, 고객, 음식점, 금액, 상태, 주문 시간 |
| 화면 | 주문서, 주문 내역, 주문 상태 |
| API | 주문 생성, 주문 조회, 주문 취소 |
| 코드 | `Order`, `OrderService`, `create_order()` |
| 이벤트 | `order_created`, `order_cancelled` |
| 테스트 | 정상 주문, 결제 실패, 취소 불가 상태 |

### 사용자 역할이란
- 시스템 안에서 특정 책임을 맡는 사람이나 외부 시스템

| 역할 | 주요 책임 | 주요 행동 | 접근 데이터 |
|------|-----------|-----------|-------------|
| 고객 | 메뉴를 선택하고 주문합니다. | 조건 입력, 추천 확인, 주문, 결제, 리뷰 작성 | 자신의 주소, 장바구니, 주문 내역 |
| 음식점 운영자 | 주문을 접수하고 음식을 준비합니다. | 메뉴 관리, 주문 수락, 조리 상태 변경 | 자신의 메뉴와 주문 정보 |
| 배달원 | 음식을 고객에게 전달합니다. | 배달 수락, 픽업, 위치 갱신, 배달 완료 | 담당 배달 정보 |
| 관리자 | 서비스 운영 상태를 관리합니다. | 사용자 관리, 신고 처리, 운영 지표 확인 | 운영에 필요한 제한된 데이터 |
| 결제 시스템 | 결제 결과를 전달합니다. | 승인, 실패, 취소 결과 전달 | 결제 요청 정보와 처리 결과 |

사용자는 실제 사람이나 시스템이고, 역할은 그 사용자가 맡은 책임이다. 고객과 음식점 운영자가 동일 인물일 수도 있지만, 시스템에서는 두 역할의 권한을 구분해야 한다.

### 업무 흐름이란
- 실제 업무가 처리되는 순서

업무 흐름을 작성할 때는 정상 흐름과 예외 흐름을 모두 작성한다.

예외 흐름 작성 순서:
```text
무엇이 실패했는가?
→ 현재 상태를 어떻게 유지하거나 변경하는가?
→ 사용자에게 무엇을 안내하는가?
→ 다시 시도할 수 있는가?
→ 어떤 기록을 남기는가?
```

## 2. 데이터, 상태, 이벤트

### 데이터란
- 시스템이 업무를 처리하거나 결과를 보여 주기 위해 사용하는 정보

데이터 항목(Data Field)은 하나의 대상을 설명하는 개별 정보다. 예를 들어 메뉴라는 대상은 메뉴 번호, 메뉴명, 가격, 음식 종류, 품절 여부, 배달 가능 여부 같은 데이터 항목으로 설명된다.

### 필수 데이터와 선택 데이터
- 필수 데이터는 값이 없으면 해당 업무를 처리할 수 없는 정보
- 선택 데이터는 값이 없어도 기본 업무를 처리할 수 있는 정보

| 데이터 | 구분 | 이유 |
|---------|------|------|
| 예산 | 필수 | 예산 범위에 맞는 메뉴를 찾기 위해 필요 |
| 음식 종류 | 필수 | 원하는 종류의 메뉴를 찾기 위해 필요 |
| 배달 위치 | 필수 | 배달 가능한 음식점을 찾기 위해 필요 |
| 제외 음식 | 선택 | 입력하지 않아도 기본 추천은 가능 |
| 요청 사항 | 선택 | 주문은 가능하지만 추가 전달 사항으로 사용 |

### 식별자란
- 여러 데이터 중 하나를 고유하게 구분하는 값

이름만으로는 같은 이름의 메뉴(예: A 음식점의 김치찌개, B 음식점의 김치찌개)를 구분할 수 없기 때문에, 각 대상에 고유 번호를 부여한다. 프로젝트에서는 식별자 이름 뒤에 `_id`를 붙인다. (예: `customer_id`, `menu_id`, `order_id`)

### 데이터 소스란
- 데이터가 처음 발생하거나 시스템으로 들어오는 곳

| 데이터 | 데이터 소스 |
|---------|------------|
| 예산, 음식 종류, 제외 음식 | 고객 화면 |
| 메뉴명, 가격, 품절 여부 | 음식점 정보 |
| 추천 메뉴, 추천 이유 | 추천 기능 |
| 결제 성공·실패 결과 | 결제 시스템 |
| 배달 상태와 위치 | 배달원 앱 |

데이터 소스와 데이터 저장소는 다르다.

```text
데이터 소스 = 데이터가 처음 발생하는 곳
데이터 저장소 = 전달받은 데이터를 보관하는 곳
```

예: 결제 성공 여부는 결제 시스템(소스)에서 발생 → 우리 서비스가 전달받음 → 주문 데이터(저장소)에 결제 완료 상태로 저장

### 상태란
- 대상이 현재 어떤 단계에 있는지를 나타내는 값 — "지금 어떤 단계인가?"

```text
주문 생성 → 결제 대기 → 결제 완료 → 음식점 접수 → 조리 중 → 배달 중 → 완료
```

실패·취소 상태도 필요하다: `payment_failed`, `restaurant_rejected`, `cancelled`

### 이벤트란
- 업무에서 중요한 일이 발생했다는 기록 — "무슨 일이 발생했는가?"

상태와 이벤트는 다음처럼 연결된다.

```text
recommendation_requested 이벤트 발생 → 추천 전 상태에서 추천 중 상태로 변경
recommendation_created 이벤트 발생 → 추천 중 상태에서 추천 완료 상태로 변경
```

### 도메인 이벤트란
- 서비스의 주요 업무에 의미 있는 변화가 발생한 사건

화면에서 발생하는 모든 클릭이 도메인 이벤트는 아니다.

| 화면에서 발생한 일 | 도메인 이벤트 여부 | 이유 |
|---|---|---|
| 화면을 스크롤함 | 낮음 | 추천이나 주문 상태가 바뀌지 않음 |
| 설명 문구를 클릭함 | 낮음 | 다음 업무가 시작되지 않음 |
| 추천받기 버튼을 누름 | 높음 | 추천 업무가 시작됨 |
| 추천 결과가 생성됨 | 높음 | 사용자에게 결과를 제공할 수 있음 |
| 메뉴를 장바구니에 담음 | 높음 | 주문할 대상이 변경됨 |
| 결제에 실패함 | 높음 | 주문 진행이 중단됨 |

다음 중 하나에 해당하면 핵심 도메인 이벤트로 기록한다.

```text
대상의 상태가 바뀝니다.
다음 업무가 시작됩니다.
중요한 성공 또는 실패 결과가 발생합니다.
다시 처리하거나 원인을 추적해야 합니다.
사용자에게 알림이나 안내가 필요합니다.
```

## 3. 네이밍 컨벤션

### 네이밍 컨벤션이란
- 같은 대상을 같은 이름으로 부르기 위한 약속

컨벤션이 없으면 같은 대상을 문서마다 다르게 부르게 된다.

```text
기획 문서: 추천 결과
화면: AI 추천
데이터: menu_suggestion
코드: recommend_result
```

컨벤션이 있으면 같은 뿌리 단어(`recommendation`)를 유지해서 관련된 데이터와 이벤트임을 쉽게 알 수 있다.

| 공식 한글 용어 | 영문 기준 이름 |
|----------------|----------------|
| 고객 | customer |
| 음식점 | restaurant |
| 메뉴 | menu |
| 추천 결과 | recommendation |
| 장바구니 | cart |
| 주문 | order |
| 결제 | payment |
| 배달 | delivery |

### snake_case란
- 여러 영문 단어를 소문자로 쓰고 단어 사이를 밑줄로 연결하는 방식 (예: `delivery_address`, `payment_completed`)
- 이 프로젝트에서는 데이터 항목, 식별자, 이벤트 이름, 함수 이름의 기준에 snake_case를 사용한다.

### 이벤트 이름을 과거형으로 쓰는 이유
- 이벤트는 이미 발생한 일을 기록하므로, 발생이 완료된 사건으로 표현한다.

```text
create_order() → 주문을 생성하는 함수 (동작)
order_created  → 주문 생성이 완료된 사건 (이벤트)
```

## 4. 데이터 흐름과 아키텍처

### 아키텍처란
- 시스템을 구성하는 주요 요소와 요소 사이의 관계를 설명하는 구조

아키텍처 그림은 박스를 예쁘게 배치하는 그림이 아니라, 다음 내용을 설명하는 그림이다.

```text
누가 시스템을 사용합니까?
데이터는 어디에서 들어옵니까?
어떤 구성요소가 데이터를 처리합니까?
어디에 저장합니까?
어떤 외부 시스템과 연결합니까?
결과는 어디로 전달합니까?
오류와 로그는 어디에 남깁니까?
```

### 업무 흐름과 데이터 흐름의 차이

| 구분 | 의미 | 예시 |
|---|---|---|
| 업무 흐름 | 사람과 시스템이 업무를 처리하는 순서 | 고객이 메뉴를 선택 → 주문 요청 → 결제 → 음식점 수락 → 배달 |
| 데이터 흐름 | 업무가 진행될 때 데이터가 어디에서 어디로 이동하고 어떻게 처리되는지 | 주문 요청 JSON → 주문 API → 입력 검증 → 주문 DB 저장 → 결제 요청 → 결제 결과 수신 → 화면 표시 |

업무 흐름의 한 단계("고객이 결제합니다")가 데이터 흐름에서는 여러 시스템과 처리 단계로 나뉠 수 있다.

### 실습 기능의 구성요소

| 구성요소 | 주요 역할 | 입력받는 정보 | 만들어 내는 결과 |
|---|---|---|---|
| 고객 앱 | 사용자 입력을 받고 추천 결과를 화면에 보여줌 | 위치, 예산, 선호 음식 | 추천 요청 |
| 추천 API | 입력값을 확인하고 AI 추천 기능에 요청 | 위치, 예산, 선호 음식 | 추천 결과 또는 오류 안내 |
| AI 메뉴 추천 | 조건에 맞는 메뉴를 판단 | 사용자 조건, 메뉴 정보 | 추천 메뉴, 점수, 이유 |
| 메뉴 정보 | 추천에 사용하는 음식 정보 제공 | 음식점이 등록한 메뉴 정보 | 조건에 맞는 메뉴 후보 |
| 추천·선택 기록 | 추천과 선택 기록 보관 | 추천 결과, 선택 결과 | 이전 추천·선택 기록 |
| 작업 기록 | 처리 과정과 오류를 시간순으로 기록 | 요청 정보, 처리 결과, 오류 정보 | 문제 확인·분석용 기록 |

## 5. 방법론과 MVP

### 프로젝트 방법론이란
- 프로젝트를 어떤 순서와 방식으로 진행할지 정한 공통 운영 방법

### Waterfall이란
- 요구사항 확정 → 설계 → 개발 → 테스트 → 배포를 순서대로 진행하는 방식
- 요구사항이 명확하고, 후반에 변경하면 비용이 큰 프로젝트에 적합

### Agile이란
- 전체 결과를 작은 단위로 나누고, 짧은 주기로 만들고 확인하며 개선하는 방식
- 불확실성이 큰 프로젝트에 적합

### Waterfall과 Agile 비교

| 비교 기준 | Waterfall | Agile |
|---|---|---|
| 요구사항 | 초기에 비교적 자세히 확정 | 사용해 보면서 보완 |
| 개발 방식 | 큰 단계를 순서대로 진행 | 작은 결과를 반복하여 개발 |
| 결과 확인 | 개발 후반에 전체 결과 확인 | 반복할 때마다 작은 결과 확인 |
| 변경 처리 | 변경 절차와 비용이 큼 | 작은 범위에서 자주 변경 |
| 적합한 프로젝트 | 요구사항이 명확한 프로젝트 | 불확실성이 큰 프로젝트 |

### 혼합형 접근이란
- 프로젝트 상황에 따라 Waterfall과 Agile의 특징을 함께 사용하는 방식

```text
반드시 지켜야 하는 내용 → 미리 정하고 고정
실행해 보기 전에는 알기 어려운 내용 → 작은 결과로 만들고 반복 확인
```

### MVP란
- Minimum Viable Product(최소 기능 제품)의 약자로, 핵심 가정을 확인하기 위해 반드시 필요한 최소 기능만 포함한 제품

올바른 MVP의 특징:
- 사용자가 처음부터 끝까지 사용할 수 있습니다.
- 핵심 문제를 해결하는 흐름이 연결됩니다.
- 성공과 실패 상황을 확인할 수 있습니다.
- 사용자에게 보여 줄 결과가 있습니다.
- 핵심 가정이 맞는지 검토할 수 있습니다.
