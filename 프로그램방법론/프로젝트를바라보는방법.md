# 프로젝트, 프로덕트, 운영 구분하기
## 프로젝트란
-특정 문제를 해결하기 위해 일정 기간 동안 수행하여 고유한 결과물을 만드는 활동

``` text
6주 동안 AI 메뉴 추천 MVP를 만들어
테스트 사용자의 메뉴 선택 시간을 평균 5분에서 3분 이하로 줄입니다
```

## 프로덕트란
-특정 사용자의 문제를 반복적으로 해결하며 지속적으로 가치를 제공하는 제품이
나 서비스

ex) 배달앱

## 운영이란
-프로덕트가 배포된 후에도 안정적으로 가치를 제공하도록 유지하는 반복 업무

``` text
서버 장애 확인
결제 오류 대응
고객 문의 처리
추천 품질 점검
비용과 성능 확인
```

## 정리
-프로젝트는 특정 문제를 해결하기 위한 결과물을 만드는 활동이고,
프로덕트는 프로젝트를 통해 만든 제품이나 서비스이며,
운영은 프로덕트가 잘 작동하도록 유지보수하는 업무이다.

# 문제에서 프로젝트를 시작하는 방법
## 좋은 프로젝트 문장의 작성 구조
``` text
[사용자]가 [상황]에서 겪는 [문제]를
[해결 방식]으로 줄여
[확인 가능한 변화]를 만듭니다.
```
## 예시
``` text
혼자 점심을 주문하는 직장인이 메뉴가 많아 선택에 오래 걸리는 문제를
예산, 거리, 선호 음식 기반 추천으로 줄여
3분 안에 주문 후보를 선택할 수 있도록 합니다.
```

## 기준선이란
-프로젝트를 시작할 때 팀이 합의한 목적, 용어, 데이터, 흐름, 산
출물, 완료 조건을 기록한 기준 문서

### 기준선이 필요한 이유
``` text
프로젝트 목표가 고정됩니다.
팀원들이 같은 용어를 사용합니다.
도메인 요소와 기능의 관계가 보입니다.
데이터가 어디에서 발생하고 이동하는지 확인할 수 있습니다.
기능 구현 순서가 명확해집니다.
테이블, API, 클래스, 함수 이름을 일관되게 작성할 수 있습니다.
브랜치와 산출물 기준이 정리됩니다.
완료 여부를 다른 팀원이 확인할 수 있습니다.
```

### 기준선 필수 항목
``` text
1. 프로젝트 목적
2. 문제 정의
3. 도메인 정의
4. 사용자 역할
5. 업무 흐름
6. 데이터 소스
7. 데이터 유형
8. 도메인 이벤트
9. 데이터 흐름
10. 용어와 네이밍 컨벤션
11. 산출물 기준
12. 완료 체크리스트
```

## WBS란
- 프로젝트의 큰 결과를 실제로 수행할 수 있는 작은 작업으로 나눈 구조
- 큰 기능을 담당자, 예상 시간, 선행작업, 완료 조건을 정할 수 있는 크기로 나누기

### 담당자 예시
| 역할 | 담당 업무 |
|------|-----------|
| **기획 담당** | 기능 범위 정의, 사용자 흐름(User Flow) 설계, 완료 기준(Definition of Done) 수립 |
| **데이터 담당** | 메뉴별 샘플 데이터 작성, 데이터 항목 및 구조 정의 |
| **AI 담당** | 추천 조건 설계, 추천 결과 생성 규칙 및 프롬프트 작성 |
| **프론트엔드 담당** | 사용자 입력 화면 및 추천 결과 화면(UI) 구현 |
| **백엔드 담당** | 주문 처리 로직, 상태 변경, 데이터 저장 및 API 구현 |
| **QA 담당** | 정상 시나리오 및 예외·실패 시나리오 검증, 테스트 수행 |
| **문서 담당** | README 작성, 프로젝트 문서 및 발표 자료 정리 |

### 예상 시간이란
- 작업을 완료하는 데 필요할 것으로 판단한 시간
- 다음 내용을 고려
```text
조사와 설계
코드 작성
테스트
오류 수정
코드 또는 문서 검토
문서 반영
```
### 선행 작업이란
-특정 작업을 시작하기 전에 먼저 끝나야 하는 작업
### 완료 조건이란
- 해당 작업이 어느 상태가 되어야 완료인지 판단하는 기준
```text
예시

예산과 음식 종류를 입력하면 메뉴가 1개 이상 표시됩니다.
각 추천 결과에 메뉴명, 가격과 추천 이유가 표시됩니다.
빈 장바구니에서는 주문이 생성되지 않습니다.
가상 결제 실패 시 주문 상태가 payment_failed로 변경됩니다.
```

## 마일스톤
- 프로젝트에서 중요한 결과가 확인되는 시점

## WBS vs 마일스톤
| 구분 | WBS | 마일스톤 |
|------|-----|----------|
| **목적** | 프로젝트에서 해야 할 일을 작은 작업 단위로 나누어 관리함 | 프로젝트의 중요한 완료 시점이나 목표 달성 지점을 표시함 |
| **질문** | 누가 무엇을 해야 하는가? | 언제 어떤 상태에 도달해야 하는가? |
| **예시** | 추천 조건 필터 기능 작성 | 추천 기능 완성 |

## 현업에서 작업 계획을 관리하는 법
1. Notion
- Notion에서는 같은 WBS 데이터를 표, 보드와 타임라인으로 볼 수 있습니다
```text
표
→ 담당자, 예상 시간, 선행 작업과 완료 조건 확인
보드
→ 시작 전, 진행 중, 검토 중, 완료 상태 확인
타임라인
→ 작업 시작일과 종료일 확인
```
2. Jira
- 현업에서 개발 작업의 담당자, 우선순위, 일정과 진행 상태를 관리하는 도구

| 용어 | 쉬운 설명 |
|------|----------|
| **Issue** | Jira에 등록하는 하나의 작업 단위. 해야 할 일, 개선 사항, 버그 등을 하나의 항목으로 관리하는 것 |
| **Status** | 해당 작업이 현재 어느 단계에 있는지를 나타내는 상태. 예: 시작 전, 진행 중, 검토 중, 완료 |
| **Assignee** | 해당 작업을 담당하고 책임지는 사람. Issue를 실제로 수행하는 담당자 |
